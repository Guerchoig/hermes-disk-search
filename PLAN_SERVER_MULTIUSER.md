# ПЛАН: серверная установка hermes-disk-search на 5 пользователей (Win/macOS) + клиентский пакет

**Статус:** план уточнён по ответам заказчика (07.10.2026); остались уточнения — §7.
**Дата:** 07.10.2026 (обновлён).

**Решения заказчика (07.10.2026):**
1. Корни индексации — в `config.yaml` с заменой из UI; вводится понятие
   **«Проект»** (см. п.8).
2. Периметр — **публикация в интернет через reverse-proxy с TLS**.
3. Идентификация — **локальные токены** (без внешнего IdP).
4. Железо сервера конфигурируемое; для экспериментов — **этот ПК: 2 карты
   (AMD + NVIDIA)**. macOS-сервер — **Apple Silicon (Metal)**, бюджетная
   альтернатива закупке мощных карт.
5. **Всем 5 пользователям нужен `ask_my_files`** (тяжёлый RAG); SLA — **≤5 мин**.
6. **Apple Silicon — целевой сервер** (не только Windows).
7. Клиенты — **только Cline и Hermes**; UI — **только админ**.
8. Модель доступа — **«Проекты»**: пользователю открывают доступ к проектам, и он
   ищет только по их файлам. Схема индекса меняется, **БД можно дропнуть**.
9. Чат-модель для MCP/поиска — **не обязательно локальная** (режим внешней модели).
10. **Запуск/остановка служб — из UI.**

**Уточнения заказчика (07.10.2026, раунд 2):**
11. Проект по умолчанию для корня-диска — **метка диска с двоеточием** (`D:\` → `D:`).
12. Токены — **генерируются автоматически**; у пользователей **логин + пароль**,
    которые выдаёт админ (схема выдачи предложена в W2).
13. **Индексацией занимается только админ**; пользователи — никогда.
14. Отправка данных во внешний API — **допустима**: на следующем шаге данные будут
    **анонимизированы** (см. W9 и §9).
15. Корни — в настройках; **объём индексации не ограничен.**
**Цель документа:** описать доработки, которые превращают проект из инструмента
«на личный десктоп» в **серверный сервис** для одновременной работы до **5
пользователей**, обращающихся к нему **из Cline или Hermes через интернет**, при
**одной мощной ИЛИ нескольких ординарных видеокартах**. Плюс — два пакета установки:
**серверный** и **клиентский**; платформы сервера и клиента — **Windows и macOS**.

## 0. Что уже есть (аудит, опирается на код, а не на предположения)

Проект уже устроен ближе к серверу, чем типичный desktop-tool. Переиспользуем:

| Факт (откуда) | Что это даёт для сервера |
|---|---|
| **Rust-ядро**: `crates/{hds-core,hds-search,hds-index,hds-llama,hds-extract,hds-clip,hds-mcp,hds-ui,hds-cli}` (README, `MIGRATION_PLAN_RUST.md` §2.4) | один воркспейс, отдельные процессы-режимы; Python остаётся только воркером-извлекателем (`sidecar/`) |
| **`llm-host` — единственный владелец GPU** + VRAM-диспетчер по NVML, `gpu.policy: query_priority` (`config.example.yaml` §gpu, `PLAN_W2_LLM_HOST.md`) | конкуренцию за GPU уже арбитрирует один процесс; VRAM-бюджет и вытеснение ролей — готовый фундамент многопользовательности |
| **Параллельные слоты роли**: `n_ctx = llm_server.parallel × ctx_per_slot` (`registry.rs`, `cline.rs::role_ctx_tokens`) | у движка есть `n_parallel` инстанса — задел под **одновременные запросы 5 юзеров** |
| **MCP streamable-http — ОДИН инстанс на машину** (`hds mcp-http`, `crates/hds-mcp/src/http.rs`), клиенты ходят по URL (`config.yaml` §mcp_http) | уже есть серверный транспорт: Cline/Hermes подключаются по сети, а не поднимают свой процесс |
| **HTTP-фасад `:8010/:8011/:8012`** (chat/embedding/rerank), OpenAI-совместимый (`hds-llama/src/facade.rs`) | тонкие клиенты могут ходить напрямую, без движка на клиенте |
| **Настройки хостов из `config.yaml`** (`llm_server.host`, `mcp_http.host`, порты) | смена `127.0.0.1 → 0.0.0.0` — конфигом, без правки кода |
| **`hds cline-sync`** — единый код установки MCP-URL/правил/скиллов Cline (`hds-core/src/cline.rs`) | основа **клиентского** пакета: одна команда подключает Cline к удалённому серверу |
| **Установщики и сборка**: `setup.ps1`/`setup.cmd`, `install_macos.command`, `build_rust_release.ps1`, `build_sidecar.ps1`, CI `.github/workflows/release.yml` | переиспользуемые кирпичи для серверного/клиентского пакетов |
| **Общий рантайм/модели машины** (`%LOCALAPPDATA%\llama-runtime`, macOS `Application Support`) | на сервере — один набор моделей на все роли и всех пользователей |

### Чего сейчас нет (то, что предстоит сделать)

1. **Нет аутентификации/авторизации** нигде: MCP `:8787`, UI `:8765`, фасад
   `:8010–8012` — «для localhost». Единственная защита — CSRF-проверка loopback в
   UI (`csrf_ok`, `crates/hds-ui/src/lib.rs`). Для интернета этого категорически
   мало.
2. **Нет «серверного режима»**: всё завязано на вход пользователя в систему
   (задачи Планировщика/LaunchAgent на логин), UI — ярлык, корни задаются в UI.
   Сервер должен работать **как служба**, без интерактивного входа.
3. **Многопользовательность не спроектирована**: `parallel: 1` по умолчанию; нет
   очередей/квот/приоритетов между *пользователями*, нет учёта «кто сколько
   занял GPU», нет изоляции результатов.
4. **Одна карта — один глобальный `gpu.device_index`** (`device.rs`): все роли
   идут на одно устройство. Размещение ролей/инстансов **по разным картам**
   (`manual_devices_csv`, группы устройств движка) в конфиге не выведено — это
   ручная работа.
5. **Нет TLS / реверс-прокси / публикации наружу** из коробки; нет rate-limit.
6. **БД SQLite — однописательская**: писатель (watcher/index) один; читатели —
   UI/MCP/CLI. Для 5 читателей ок, но нужны WAL и явная политика блокировок.
7. **Нет клиентского пакета**: сейчас клиент = «поставил весь стек локально».
8. **macOS-сервер не проверен** на реальной машине (`MAC_CHECKLIST.md`), а NVIDIA
   на macOS нет. **Решение:** серверный macOS — **Apple Silicon (Metal)** как
   бюджетная альтернатива мощным картам (целевой вариант, см. §1/W4).
9. **Нет понятия «Проект»** в индексе — нет разграничения доступа к файлам.
   Схема `index.db` и `config.yaml index.roots` меняются; **текущую БД разрешено
   дропнуть** (см. W5).
10. **Чат-роль жёстко локальная** (`chat.base_url` → фасад `:8010`): нет режима
    «внешняя/облачная чат-модель» (W9).
11. **Нет управления службами из UI**: UI запускает/останавливает лишь MCP и
    llm-host; watcher и сервис-обёртки — вне UI (W10).

## 1. Целевая архитектура

```
                 ┌──────────────── СЕРВЕР (Windows / macOS Apple Silicon) ───────┐
   интернет      │  reverse-proxy: TLS (:443); наружу только /mcp и /ui          │
 Cline/Hermes ───►  ├── /mcp → hds mcp-http (:8787)  [Bearer-токен → проекты]  │
   (клиент,       │  └── /ui  → hds ui       (:8765)  [только админ]             │
    тонкий)       │                                                              │
                 │  llm-host (служба, владелец GPU): chat|embedding|rerank|whisper
                 │    параллельные слоты; VRAM-диспетчер по картам (CUDA/Vulkan/Metal)
                 │    chat — локальная ИЛИ внешняя (W9); фасад :8010–8012 — localhost
                 │  hds watch/index (служба): обход дисков → index.db (+project, W5)
                 │  sidecar (Python): извлечение/OCR/лемматизация
                 │  управление службами — из админ-UI (W10)
                 └──────────────────────────────────────────────────────────────┘
                                   ▲  один общий рантайм + модели на машину
```

**Клиент** — тонкий: Cline/Hermes + правило/скилл + MCP-URL + токен. Ни движка,
ни моделей, ни индекса локально; **UI локально НЕ ставится** (UI — только админ на
сервере).

**Модель доступа — «Проекты» (ключевое, §2 W5).** Один `index.db`, но у каждого
файла есть **проект** (из корня, где он найден). Токен пользователя сопоставлен
набору разрешённых проектов; MCP-инструменты **фильтруют выдачу по проектам**
пользователя — разграничение доступа **без** мультитенантных БД.

**Прочие решения:** периметр — **интернет через reverse-proxy с TLS**;
аутентификация — **локальные токены**; чат-роль может быть **внешней** (W9);
службами можно управлять **из админ-UI** (W10).

## 2. Доработки (workstreams)

Обозначения: **[S]** — серверный пакет, **[C]** — клиентский пакет, **[обоим]**.

### W1. «Серверный режим» приложения [S]
- **Назначение:** приложение работает без интерактивного входа, как служба.
- Работы:
  - Windows: обернуть `llm_host run`, `hds watch`, `hds mcp-http run`, `hds ui` в
    **Windows-службу** (WinSW/NSSM или `windows-service` crate). Автозапуск не
    «AtLogOn», а «AtStartup».
  - macOS: **launchd daemons** (`/Library/LaunchDaemons`) вместо LaunchAgent-ов
    входа (сейчас `install_macos.command` ставит `~/Library/LaunchAgents`).
  - Разделить «интерактивный десктоп-режим» (как сейчас) и «серверный режим»
    одним профилем конфига (`profile: desktop | server`), чтобы не сломать
    существующих одиночных пользователей.
  - Серверные пути: индекс, логи, PID-файлы — в системный каталог
    (`%ProgramData%\hermes-disk-search`, `/Library/Application Support/...`), а
    не в `%LOCALAPPDATA%`/`~`.
  - Headless: UI на сервере — админский (диагностика/индексация), без ярлыков и
    авто-открытия браузера (`run_ui.ps1`, `shortcuts/*`).

### W2. Безопасность, сеть и разграничение доступа [S] + [C]
**Решение по W2 (принято исполнителем с учётом ответов заказчика).**

**Периметр:** TLS и публикация — на **reverse-proxy** (Caddy/nginx): наружу только
`/mcp` и `/ui`. `llm-host` (фасад `:8010–8012`) наружу **не** публикуется
(localhost) — его вызывают MCP/UI внутри сервера.

**Идентичность — логин/пароль, токены выдаются автоматически.**
- Админ заводит пользователя: **логин + пароль** (пароль — хэш Argon2id/scrypt),
  плюс список проектов и признак `admin`. Хранилище — `data/access.yaml`
  (в `.gitignore`); при желании — SQLite (`data/auth.db`), см. §7.
- Приложение проверяет `Authorization: Bearer <token>` на `hds-mcp` и `hds-ui`
  (прокси — только TLS). Токен — **авто-выданный** по схеме ниже.

**Схема выдачи токенов (login/password → token), предложение:**
1. Админ создаёт учётку (login/password/projects/admin) в админ-UI/CLI (W10).
2. Пользователь на клиенте запускает `hds login` (мастер клиентского пакета, W7):
   вводит логин/пароль → клиент зовёт `POST /auth/login` → сервер проверяет пароль
   (постоянным временем) и **выдаёт персональный токен** (opaque, 256 бит). Сервер
   хранит только **хэш** токена + `user` + `expires`.
3. Клиент кладёт токен в Cline/Hermes (`Authorization: Bearer`).
4. **Ротация/отзыв:** истечение TTL (конфигурируемо, напр. 90 дней) или отзыв
   админом; повторный `login` выдаёт новый токен (опц. refresh-токен).
- Выбор: **opaque-токен + хэш в хранилище** (удобно отзывать), а не JWT.
- Безопасность: TLS на прокси, rate-limit/лок на `/auth/login`, хэши постоянным
  временем, TTL, запрет входа `disabled`-пользователям. Задел под внешний IdP —
  владение `Authorization` в одном месте.

**Авторизация (проекты):** токен → `user.projects`; инструменты
`search_local_files`/`ask_my_files`/`index_status` **фильтруют выдачу по проектам
пользователя** (W5). Без валидного токена — `401`. Управление индексацией
(`start_indexing`/`stop_indexing`/`reindex_path`) — **только admin**.
- **UI — только админ** (пользовательский доступ к UI закрыт).
- **Аудит** — `data/audit.log` (кто/когда/запрос/проекты).
- **Rate-limit/квоты** — лимит одновременных `ask_my_files` на пользователя (W3).
- **CSRF/`csrf_ok` (UI):** за прокси loopback-проверка ломается (`Origin` не
  loopback) — заменить на «валиден админ-токен».

**[C]** клиентский инсталлятор пишет в Cline/Hermes **URL + `Authorization`**
(расширить `cline_mcp_merge.py`/`hds_core::cline::sync` — сейчас пишется только `url`).

### W3. Конкурентность, планирование и квоты [S]
**Вводные:** все 5 пользователей используют `ask_my_files` (тяжёлый RAG);
**SLA — ≤5 мин на ответ**.
- **Параллельные слоты chat:** `llm_server.parallel` подобрать так, чтобы 5
  одновременных RAG укладывались в SLA (KV роли = `parallel × ctx_per_slot`;
  считать VRAM, W4). Ориентир — `parallel: 5–6`.
- **Очередь и fair-share:** у llm-host есть `gpu.policy` и приоритеты ролей;
  добавить приоритеты **по пользователю** и fair-share (один тяжёлый запрос не
  должен морить голодом остальных). Целевая метрика p95 ≤ SLA.
- **Выгрузка чата на внешнюю модель (W9):** при нехватке VRAM/слотов чат-роль
  выносится на внешний OpenAI-совместимый endpoint — GPU занят только
  embedding/rerank/whisper. Ключевой рычаг SLA на слабом железе.
- **Квоты:** лимит одновременных RAG на пользователя; отдельный «индексный»
  приоритет ниже пользовательских.
- **БД:** `journal_mode=WAL` + `busy_timeout`; читатели (MCP/UI/CLI) — пул
  read-only; писатель (watcher/index) — один.
- **Индексация ≠ запрос:** индексация уступает (`gpu.policy: query_priority`,
  `pause_index_on_query`).

### W4. GPU: несколько карт и разные вендоры [S]
**Вводные:** железо конфигурируемое; целевые профили — «1 мощная карта»,
«N ординарных»; на этом ПК — **AMD + NVIDIA**; macOS-сервер — **Apple Silicon (Metal)**.
- Сейчас `gpu.device_index` — **один** глобальный индекс (`device.rs`). Нужна
  схема **per-role / per-instance**:
  - `gpu.devices:` список; `llm_server.<role>.device` / `llm.<role>.device` — какая
    карта (или группа) обслуживает роль;
  - профили: NVIDIA(CUDA) → chat; AMD(Vulkan) → embedding/rerank; либо **split**
    модели по картам (`manual_devices_csv` с несколькими индексами).
- **Смешанные вендоры:** движок грузит CUDA **и** Vulkan бэкенды; нужно
  **эмпирически подтвердить (спайк)**, что на одной машине роли одновременно
  раскладываются на CUDA- и Vulkan-устройства (`llm-host devices` показывает
  `backend=CUDA`/`Vulkan`) и адресация по `bridge_device_index` стабильна.
- **VRAM-проба по вендорам:** NVML — NVIDIA; AMD — DXGI/AMD-smi; Apple Silicon —
  Metal (`recommendedMaxWorkingSetSize`). Бюджет и диспетчер — **по каждой карте
  отдельно** (сейчас бюджет по одному устройству).
- Пресеты: «1 мощная NVIDIA», «AMD+NVIDIA», «Apple Silicon».

> **Открытый технический риск:** одновременная работа CUDA+Vulkan в одном
> `llm-host` движком не гарантирована. Первый шаг Э5 — спайк (`a1_device_probe`/
> `diar_probe`); при неудаче фолбэк — одна карта на все роли.

### W5. «Проекты» — модель данных и разграничение доступа [S]  ← ключевая доработка
Заказчик ввёл понятие **«Проект»**: единица выдачи и разграничения доступа.
- **Корни → проекты.** В `index.roots` у корня опционально задаётся имя проекта;
  если не задано — **проект по умолчанию = имя младшей папки корня** (для корня
  диска — **метка диска с двоеточием**: корень `D:\` → проект `D:`; согласовано).
  Несколько корней могут быть в одном проекте — тогда имя задаётся явно у каждого.
  ```yaml
  index:
    roots:
      - { path: "D:\\Work\\Sales", project: "Sales" }   # явно
      - { path: "E:\\Archive" }                          # "Archive" (по умолчанию)
      - { path: "F:\\Reports", project: "Sales" }        # тот же проект
  ```
  Обратная совместимость: строка вместо объекта = проект по умолчанию.
- **Схема `index.db` (формат меняется — БД можно дропнуть):** добавить
  `files.project` (+ индекс) либо таблицы `projects`/`project_roots`; `chunks`
  наследуют проект через `files`. Миграция не нужна — переиндексация с нуля.
- **Фильтрация выдачи:** `hds-search`/RAG принимают список разрешённых проектов;
  MCP-инструменты подставляют проекты из токена (W2); локальный CLI/десктоп — без
  фильтра (все проекты).
- **UI (админ):** присвоение имён проектов корням; список проектов и назначение
  доступов пользователям.
- **Риск утечки:** фильтр обязан применяться и к FTS, и к векторной ветке, и к
  CLIP, и к RAG-контексту (включая цитаты) — отдельный набор тестов.
- Итог: единый `index.db` + авторизация по проектам (без мультитенантных БД).

### W6. Серверный пакет установки [S]
- Windows: установщик (MSI/EXE либо `setup-server.ps1`) + служба (W1). Скачивание
  рантайма движка/моделей по манифестам (`fetch_engine_runtime.ps1`,
  `fetch_llm_models.ps1`) — **unattended** (параметры вместо `Read-Host`).
- macOS: `.pkg` (либо `install_server.command`) + launchd-daemons.
- Настройка «из коробки»: `profile: server`, `host: 0.0.0.0` за прокси, `parallel`,
  раскладка ролей по картам, корни индексации, автозапуск служб, OCR/транскрипция
  по согласию.
- Обновление: `update.ps1` расширить на серверный профиль; продумать перезапуск
  служб (сейчас резидент держит `*.exe` — «отказано в доступе» при пересборке).
- Поставка примера reverse-proxy: `Caddyfile`/`nginx.conf` + сертификаты
  (Let's Encrypt или self-signed).

### W7. Клиентский пакет установки [C]
- Windows (`setup-client.cmd`/`.ps1`) и macOS (`install_client.command`) — **тонкий**
  клиент:
  - НЕ ставит движок/модели/sidecar/индекс.
  - Пишет Cline-конфиг через `hds cline-sync` (обобщить: URL + токен + правило +
    скилл), опционально Hermes (`install_hermes_*`).
  - Мастер: «адрес сервера + токен» → «проверить соединение» (`GET /health`) →
    «записать настройки» → «перезапустите Cline».
  - Опционально — ярлык на **админ-UI сервера**; локального UI-сервера нет.
- Версия клиента согласуется с сервером (правило/скилл/схема инструментов).

### W8. Эксплуатация [S]
- Логи: единый формат, ротация (`data/logs` есть), уровни.
- Health/metrics: `/health` у MCP/UI; агрегированный `/healthz` (llm-host + БД +
  watcher + дисковое место).
- Бэкап `index.db` через SQLite `.backup` (при WAL), восстановление.
- Обновление сервера с малым простоем, откат.
- Админ-диагностика: расширить `hds check` (службы, карты, свободная VRAM, число
  слотов, очереди, число активных пользователей).

### W9. Внешняя (не локальная) чат-модель [S]
- Сейчас `chat.base_url` → локальный фасад `:8010`; движок сам применяет шаблон.
- Добавить режим `chat.provider: local | remote` (аналогично — задел для реранка):
  ```yaml
  chat:
    provider: remote          # local | remote
    base_url: "https://api.example.com/v1"
    api_key: "<...>"
    model: "gpt-4o-mini"      # OpenAI-совместимый endpoint
  ```
- При `remote`: `llm-host` **не** держит chat-роль в VRAM (экономия под слоты
  embedding/rerank/whisper), RAG ходит напрямую во внешний endpoint.
- Эмбеддинги остаются **локальными** (индекс построен на bge-m3); внешним делается
  только чат (и, опционально, реранк).
- Учесть: латентность/стоимость/приватность внешнего провайдера; таймаут MCP 300 с.
- **Анонимизация (следующий шаг проекта):** данные исходных файлов и индекса будут
  анонимизированы, поэтому внешние сервисы допустимы (подтверждено заказчиком).
  Ограничение: внешние **эмбеддинги** применимы только при совпадении векторного
  пространства с индексом (bge-m3), иначе индекс становится несогласованным.

### W10. Управление службами и доступами из UI [S]

- Сейчас UI управляет MCP и llm-host — расширить на watcher и службы.
- Управление доступом: выдача/отзыв токенов и назначение проектов пользователям
  (W2) — из админ-UI и/или CLI (`hds tokens ...`).

## 6. Риски
| Риск | Митигация |
|---|---|
| **Утечка между проектами** (фильтр применён не ко всем веткам поиска/RAG) | единая точка фильтра + тесты на каждую ветку (FTS/vec/CLIP/RAG-контекст/цитаты) |
| CUDA+Vulkan одновременно в одном `llm-host` | спайк Э5; фолбэк — одна карта на все роли |
| SLA ≤5 мин не держится на слабом железе | внешняя чат-модель (W9), CPU-фолбэк embedding/rerank, fair-share, лимит слотов |
| SQLite single-writer под нагрузкой | WAL + busy_timeout + пул read-only; следить за блокировками при индексации |
| Apple Silicon: Metal-рантайм не проверен | привести на реальной Apple Silicon машине (иначе сервер не оправдан) |
| Смена формата индекса | БД дропается и переиндексируется (согласовано); продумать короткую недоступность при переиндексации |
| Cline/Hermes не ставят заголовок авторизации | проверить версии; fallback — токен на прокси |
| Обновление сервера ломает занятые `.exe` | окно обслуживания/перезапуск служб; версионирование |

## 8. Приложения (наброски, не финальные)

### 8.1. Фрагмент `config.yaml` серверного профиля
```yaml
profile: server
index:
  roots:
    - { path: "D:\\Work\\Sales", project: "Sales" }
    - { path: "F:\\Reports",     project: "Sales" }
    - { path: "E:\\Archive" }                       # project = "Archive"
llm_server:
  host: "127.0.0.1"        # за reverse-proxy
  parallel: 5              # 5 слотов chat под SLA (подобрать по VRAM)
gpu:
  policy: query_priority
  devices:                 # W4: раскладка ролей по картам
    - { index: 1, roles: [chat] }               # NVIDIA (CUDA)
    - { index: 2, roles: [embedding, rerank] }  # AMD (Vulkan)
chat:
  provider: local          # local | remote (W9)
  # base_url / api_key / model — при remote
mcp_http:
  host: "127.0.0.1"        # за прокси
  port: 8787
  path: "/mcp"
ui:
  host: "127.0.0.1"        # только админ, за прокси
  port: 8765
```

### 8.2. `data/access.yaml` (пользователи, пароли, авто-токены, проекты)
```yaml
users:
  - name: admin
    login: admin
    password_hash: "<argon2id>"
    admin: true
  - name: alice
    login: alice
    password_hash: "<argon2id>"
    projects: [Sales, Docs]
# Авто-выданные токены (хранятся хэшем); выдача/ротация — схема W2
tokens:
  - { token_sha256: "<...>", user: alice, expires: "2027-01-05" }
```

### 8.3. Настройка клиента Cline (удалённый MCP)
```json
{
  "mcpServers": {
    "disk-search": {
      "type": "streamableHttp",
      "url": "https://hds.example.com/mcp",
      "headers": { "Authorization": "Bearer <токен пользователя>" },
      "autoApprove": ["search_local_files","ask_my_files","index_status"],
      "timeout": 300
    }
  }
}
```
> Обычному пользователю в `autoApprove` **не** даём управление индексацией
> (`start_indexing`/`stop_indexing`/`reindex_path` — только admin). Поддержку поля
> `headers` у Cline/Hermes проверить (W2); при отсутствии — токен на прокси.

### 8.4. Reverse-proxy (эскиз Caddy)
```
hds.example.com {
    tls you@example.com            # Let's Encrypt
    reverse_proxy /mcp* 127.0.0.1:8787
    reverse_proxy /ui*  127.0.0.1:8765
    # фасад /v1/* (8010–8012) НЕ публикуем — только localhost
}
```
