# ПЛАН: серверная установка hermes-disk-search на 5 пользователей (Win/macOS) + клиентский пакет

**Статус:** черновик к согласованию. Решено: **модель корпуса — В1 «общий корпус»
(07.10.2026)**; остальные открытые вопросы — §7.
**Дата:** 07.10.2026.
**Цель документа:** описать доработки, которые превращают проект из инструмента
«на личный десктоп» в **серверный сервис** для одновременной работы до **5
пользователей**, обращающихся к нему **из Cline или Hermes через интернет**, при
**одной мощной ИЛИ нескольких ординарных видеокартах**. Плюс — два пакета установки:
**серверный** и **клиентский**; платформы сервера и клиента — **Windows и macOS**.

---

## 0. Что уже есть (аудит, опирается на код, а не на предположения)

Проект уже устроен ближе к серверу, чем типичный desktop-tool. Переиспользуем:

| Факт (откуда) | Что это даёт для сервера |
|---|---|
| **Rust-ядро**: `crates/{hds-core,hds-search,hds-index,hds-llama,hds-extract,hds-clip,hds-mcp,hds-ui,hds-cli}` (README, `MIGRATION_PLAN_RUST.md` §2.4) | один воркспейс, отдельные процессы-режимы; Python остаётся только воркером-извлекателем (`sidecar/`) |
| **`llm-host` — единственный владелец GPU** + VRAM-диспетчер по NVML, `gpu.policy: query_priority` (`config.example.yaml` §gpu, `PLAN_W2_LLM_HOST.md`) | конкуренцию за GPU уже арбитрирует один процесс; VRAM-бюджет и вытеснение ролей — готовый фундамент многопользовательности |
| **Параллельные слоты роли**: `n_ctx = llm_server.parallel × ctx_per_slot` (`registry.rs`, `cline.rs::role_ctx_tokens`) | у движка есть `n_parallel` инстанса — задел под **одновременные запросы 5 юзеров** |
| **MCP streamable-http — ОДИН инстанс на машину** (`hds mcp-http`, `crates/hds-mcp/src/http.rs`), клиенты ходят по URL (`config.yaml` §mcp_http) | уже есть серверный транспорт: Cline/Hermes подключаются по сети, а не поднимают свой процесс |
| **HTTP-фасад `:8010/:8011/:8012`** (chat/embedding/rerank), OpenAI-совместимый (`hds-llama/src/facade.rs`) | тонкие клиенты могут ходить напрямую, без движка на клиенте |
| **Настройки хостов из `config.yaml`** (`llm_server.host`, `mcp_http.host`, порты) | смена `127.0.0.1 → 0.0.0.0` — конфигом, без правки кода |
| **`hds cline-sync`** — единый код установки MCP-URL/правил/скиллов Cline (`hds-core/src/cline.rs`) | основа **клиентского** пакета: одна команда подключает Cline к удалённому серверу |
| **Установщики и сборка**: `setup.ps1`/`setup.cmd`, `install_macos.command`, `build_rust_release.ps1`, `build_sidecar.ps1`, CI `.github/workflows/release.yml` | переиспользуемые кирпичи для серверного/клиентского пакетов |
| **Общий рантайм/модели машины** (`%LOCALAPPDATA%\llama-runtime`, macOS `Application Support`) | на сервере — один набор моделей на все роли и всех пользователей |

### Чего сейчас нет (то, что предстоит сделать)

1. **Нет аутентификации/авторизации** нигде: MCP `:8787`, UI `:8765`, фасад
   `:8010–8012` — «для localhost». Единственная защита — CSRF-проверка loopback в
   UI (`csrf_ok`, `crates/hds-ui/src/lib.rs`). Для интернета этого категорически
   мало.
2. **Нет «серверного режима»**: всё завязано на вход пользователя в систему
   (задачи Планировщика/LaunchAgent на логин), UI — ярлык, корни задаются в UI.
   Сервер должен работать **как служба**, без интерактивного входа.
3. **Многопользовательность не спроектирована**: `parallel: 1` по умолчанию; нет
   очередей/квот/приоритетов между *пользователями*, нет учёта «кто сколько
   занял GPU», нет изоляции результатов.
4. **Одна карта — один глобальный `gpu.device_index`** (`device.rs`): все роли
   идут на одно устройство. Размещение ролей/инстансов **по разным картам**
   (`manual_devices_csv`, группы устройств движка) в конфиге не выведено — это
   ручная работа.
5. **Нет TLS / реверс-прокси / публикации наружу** из коробки; нет rate-limit.
6. **БД SQLite — однописательская**: писатель (watcher/index) один; читатели —
   UI/MCP/CLI. Для 5 читателей ок, но нужны WAL и явная политика блокировок.
7. **Нет клиентского пакета**: сейчас клиент = «поставил весь стек локально».
8. **macOS-сервер не проверен** на реальной машине (`MAC_CHECKLIST.md`), а NVIDIA
   на macOS нет — серверный Max/GPU-сценарий возможен только на Apple Silicon
   (Metal) с иными лимитами.

## 1. Целевая архитектура

```
                 ┌───────────────── СЕРВЕР (Win/macOS) ───────────────────┐
   интернет      │  reverse-proxy (TLS, аутентификация на входе)          │
 Cline/Hermes ───►  :443  ──┬── /mcp   → hds mcp-http  (:8787)            │
   (клиент)      │           ├── /ui    → hds ui        (:8765, admin)     │
                 │           └── /v1/*  → фасад llm-host (:8010–8012)      │
                 │                                                          │
                 │  llm-host (служба, единственный владелец GPU):           │
                 │    llama-кластер: chat | embedding | rerank | whisper,   │
                 │    параллельные слоты, VRAM-диспетчер, привязка к картам │
                 │                                                          │
                 │  hds watch/index (служба): обход дисков сервера → index.db│
                 │  hds mcp-http (служба): шлюз MCP для всех клиентов        │
                 │  sidecar (Python-воркер): извлечение/OCR/лемматизация     │
                 └──────────────────────────────────────────────────────────┘
                                   ▲
                    один общий рантайм + модели на машину
```

**Клиент** — тонкий: только Cline (или Hermes) + правило/скилл + запись MCP-URL
сервера с токеном. Ни движка, ни моделей, ни индекса локально.

**Две ключевые оси (см. §7):**
(А) **модель корпуса — РЕШЕНО: В1 «общий корпус»** (все 5 пользователей ищут по
одному индексу дисков сервера); (Б) **периметр** — VPN/Tailscale vs публичный
интернет с SSO/токенами (пока открыт). От них зависит объём работ.

## 2. Доработки (workstreams)

Обозначения: **[S]** — серверный пакет, **[C]** — клиентский пакет, **[обоим]**.

### W1. «Серверный режим» приложения [S]
- **Назначение:** приложение работает без интерактивного входа, как служба.
- Работы:
  - Windows: обернуть `llm_host run`, `hds watch`, `hds mcp-http run`, `hds ui` в
    **Windows-службу** (WinSW/NSSM или `windows-service` crate). Автозапуск не
    «AtLogOn», а «AtStartup».
  - macOS: **launchd daemons** (`/Library/LaunchDaemons`) вместо LaunchAgent-ов
    входа (сейчас `install_macos.command` ставит `~/Library/LaunchAgents`).
  - Разделить «интерактивный десктоп-режим» (как сейчас) и «серверный режим»
    одним профилем конфига (`profile: desktop | server`), чтобы не сломать
    существующих одиночных пользователей.
  - Серверные пути: индекс, логи, PID-файлы — в системный каталог
    (`%ProgramData%\hermes-disk-search`, `/Library/Application Support/...`), а
    не в `%LOCALAPPDATA%`/`~`.
  - Headless: UI на сервере — админский (диагностика/индексация), без ярлыков и
    авто-открытия браузера (`run_ui.ps1`, `shortcuts/*`).

### W2. Безопасность и сетевой доступ [S] + [C]
Это **блокирующая** часть: сейчас любой, дотянувшийся до `:8787`, имеет полный
доступ к поиску по чужим файлам.
- **Вариант A (рекомендуемый, меньше правок кода):** публикация только через
  **reverse-proxy** (Caddy/nginx) с **TLS** и аутентификацией на входе; MCP/UI
  слушают `127.0.0.1` за прокси. Cline/Hermes ходят на `https://host/mcp`.
- **Вариант B:** встроенная аутентификация в `hds-mcp`/`hds-ui`/фасаде:
  bearer-токен на каждый запрос, проверка в `route()`; TLS — свой (`rustls`) либо
  всё равно прокси.
- Workitems (в прокси либо в коде):
  - заголовочная аутентификация для MCP streamable-http (Cline умеет ставить
    кастомные заголовки в `mcpServers.disk-search`);
  - **аудит** вызовов (кто, когда, какой запрос);
  - **rate-limit** и лимит конкурентных `ask_my_files` на пользователя;
  - убрать зависимость от loopback в `csrf_ok` (UI) при работе за прокси — иначе
    админ-UI «сломается» из-за `Origin` не-loopback;
  - «свой/чужой» инстанс на порту (`/health`) — оставить, добавить токен.
- **[C]** клиентский инсталлятор пишет в конфиг Cline **URL + заголовок
  авторизации** (расширить `cline_mcp_merge.py`/`hds_core::cline::sync` — сейчас
  пишется только `url`).

### W3. Конкурентность, планирование и квоты [S]
- **Параллельные слоты ролей:** `llm_server.parallel` поднять под нагрузку
  (обычно 3–6 для chat), `ctx_per_slot` подобрать под VRAM. Это ключевая ручка
  «5 пользователей одновременно»; KV-кэш роли растёт как `parallel × ctx_per_slot`
  — считать VRAM (см. W4).
- **Очередь и приоритеты:** у llm-host есть `gpu.policy` и приоритеты ролей;
  добавить приоритеты **по пользователю/запросу** и fair-share, чтобы один тяжёлый
  `ask_my_files` не блокировал остальных.
- **Квоты:** лимит одновременных RAG-запросов на пользователя; отдельный
  «индексный» приоритет ниже пользовательских.
- **БД:** включить **WAL** (`journal_mode=WAL`) и `busy_timeout`; читатели
  (MCP/UI/CLI) — пул read-only соединений; писатель (watcher/index) — один.
- **Индексация ≠ запрос:** при 5 активных пользователях индексация уступает
  (`gpu.policy: query_priority`, `pause_index_on_query`).

### W4. Несколько GPU: размещение ролей по картам [S]
- Сейчас `gpu.device_index` — **один** глобальный индекс (`device.rs`). Нужна
  схема **per-role / per-instance**:
  - `gpu.devices:` список; `llm_server.<role>.device` / `llm.<role>.device` —
    какая карта (или группа) обслуживает роль;
  - для «нескольких ординарных» карт — либо **разнести роли** (chat на карту A,
    embedding+rerank на карту B), либо **split одной модели** по картам
    (`manual_devices_csv` с несколькими индексами — движок это умеет);
  - **VRAM-бюджет и диспетчер — по каждой карте отдельно** (сейчас бюджет по
    одному устройству; NVML-проба есть — расширить на массив);
  - профили-пресеты: «1 мощная карта» и «N ординарных».
- `llm-host devices` уже печатает устройства — расширить вывод под мультикарту.

### W5. Модель корпуса — **РЕШЕНО: В1 «Общий корпус»** [S]
- **В1 «Общий корпус» (выбрано)**: один `index.db` по дискам сервера, все 5 ищут
  по нему. Это нынешняя схема, перенесённая на сервер — минимум правок.
  - Следствие для W2: авторизация нужна **всем** (доступ к общему корпусу), но
    **изоляция между пользователями не требуется** — упрощает модель прав.
  - Следствие для W3: один писатель (индексатор сервера), читатели — 5 сессий;
    WAL + пул read-only закрывают нагрузку.
  - Следствие для приватности (см. §7 п.8): любой пользователь видит файлы
    общего корпуса — это осознанное решение.
- **В2 «Личный индекс на пользователя» / В3 «Гибрид»** — рассматривались,
  **отложены** (потребовали бы мультитенантности в MCP/UI, пула writer-ов и
  раздельных прав; при смене решения вернуться к этому разделу).

### W6. Серверный пакет установки [S]
- Windows: установщик (MSI/EXE либо `setup-server.ps1`) + служба (W1). Скачивание
  рантайма движка/моделей по манифестам (`fetch_engine_runtime.ps1`,
  `fetch_llm_models.ps1`) — **unattended** (параметры вместо `Read-Host`).
- macOS: `.pkg` (либо `install_server.command`) + launchd-daemons.
- Настройка «из коробки»: `profile: server`, `host: 0.0.0.0` за прокси, `parallel`,
  раскладка ролей по картам, корни индексации, автозапуск служб, OCR/транскрипция
  по согласию.
- Обновление: `update.ps1` расширить на серверный профиль; продумать перезапуск
  служб (сейчас резидент держит `*.exe` — «отказано в доступе» при пересборке).
- Поставка примера reverse-proxy: `Caddyfile`/`nginx.conf` + сертификаты
  (Let's Encrypt или self-signed).

### W7. Клиентский пакет установки [C]
- Windows (`setup-client.cmd`/`.ps1`) и macOS (`install_client.command`) — **тонкий**
  клиент:
  - НЕ ставит движок/модели/sidecar/индекс.
  - Пишет Cline-конфиг через `hds cline-sync` (обобщить: URL + токен + правило +
    скилл), опционально Hermes (`install_hermes_*`).
  - Мастер: «адрес сервера + токен» → «проверить соединение» (`GET /health`) →
    «записать настройки» → «перезапустите Cline».
  - Опционально — ярлык на **админ-UI сервера**; локального UI-сервера нет.
- Версия клиента согласуется с сервером (правило/скилл/схема инструментов).

### W8. Эксплуатация [S]
- Логи: единый формат, ротация (`data/logs` есть), уровни.
- Health/metrics: `/health` у MCP/UI; агрегированный `/healthz` (llm-host + БД +
  watcher + дисковое место).
- Бэкап `index.db` через SQLite `.backup` (при WAL), восстановление.
- Обновление сервера с малым простоем, откат.
- Админ-диагностика: расширить `hds check` (службы, карты, свободная VRAM, число
  слотов, очереди, число активных пользователей).

## 5. Этапы и оценка (инкрементально, каждый этап с тестами)

> Оценки — в идее-днях, порядок зависит от ответов §7. Прим.: проект уже
> проходит `cargo test --workspace` (174 passed / 0 failed) — новые шаги
> добавляют регрессионные тесты.

| Этап | Содержание | Оценка |
|---|---|---|
| Э1 | Серверный профиль конфига + bind/service-режимы (W1), headless UI | 3–5 дн |
| Э2 | Безопасность: прокси-пример + (опц.) токены в MCP/UI/фасаде, аудит, rate-limit (W2) | 4–8 дн |
| Э3 | Конкурентность: parallel-слоты под нагрузку, WAL+BUSY, квоты, fair-share (W3) | 4–7 дн |
| Э4 | Мульти-GPU: per-role/instance устройство, VRAM по картам, пресеты (W4) | 5–9 дн |
| Э5 | Модель корпуса — **решено: В1** (общий корпус, без мультитенантности) | 1–2 дн |
| Э6 | Серверный пакет установки Win/macOS (W6) | 5–8 дн |
| Э7 | Клиентский пакет Win/macOS (W7) | 3–5 дн |
| Э8 | Эксплуатация: healthz, бэкап, диагностика, обновление (W8) | 3–5 дн |
| Э9 | Нагрузочная приёмка: 5 одновременных пользователей, профили 1-карта / N-карт | 4–6 дн |

**Критерии приёмки (черновик):**
- 5 одновременных сессий Cline: поиск отвечает в целевой латентности (задать SLA);
- `ask_my_files` не «залипает» — есть очередь/fair-share, нет голодания;
- доступ извне работает по HTTPS с аутентификацией, без доступа анонимных;
- на профиле «N ординарных карт» роли разложены и VRAM считается по каждой;
- клиентские пакеты поднимают рабочий Cline за один мастер, без локальных моделей.

## 6. Риски
| Риск | Митигация |
|---|---|
| SQLite single-writer под нагрузкой | WAL + busy_timeout + пул read-only; разделить writer/readers; при В2 — очередь записей |
| ВРAM не тянет 5 слотов chat + embedding + rerank | профили под железо; CPU-фолбэк для embedding/rerank (`-ngl 0`); лимит слотов |
| macOS-сервер с NVIDIA невозможен | серверный macOS — только Apple Silicon/Metal; NVIDIA-сервер = Windows/Linux |
| Cline/Hermes не поддерживают нужный remote-транспорт/заголовки | проверить версии клиентов; fallback — reverse-proxy с авторизацией на входе |
| Обновление сервера ломает занятые `.exe` | «окно обслуживания»/перезапуск служб; версионирование (как `install_app_version.ps1`) |
| Утечка данных между пользователями (В2/В3) | строгая авторизация, раздельные БД/права, аудит |
| Отсутствие SLA/латентности | зафиксировать целевые метрики до Э3 |

## 8. Приложения (наброски, не финальные)

### 8.1. Фрагмент `config.yaml` серверного профиля
```yaml
profile: server
llm_server:
  host: "0.0.0.0"          # либо 127.0.0.1 за reverse-proxy (рекомендуется)
  parallel: 4              # одновременные слоты chat (подобрать по VRAM)
gpu:
  policy: query_priority
  devices:                 # W4: раскладка ролей по картам
    - { index: 1, roles: [chat] }              # карта A
    - { index: 2, roles: [embedding, rerank] } # карта B
mcp_http:
  host: "0.0.0.0"          # за прокси; токен — в прокси/коде
  port: 8787
  path: "/mcp"
```

### 8.2. Настройка клиента Cline (удалённый MCP)
```json
{
  "mcpServers": {
    "disk-search": {
      "type": "streamableHttp",
      "url": "https://hds.example.com/mcp",
      "headers": { "Authorization": "Bearer <токен>" },
      "autoApprove": ["search_local_files","ask_my_files","index_status",
                      "start_indexing","stop_indexing","reindex_path"],
      "timeout": 300
    }
  }
}
```
> Точная поддержка поля `headers` у Cline/Hermes **проверяется** (см. §7 п.2/W2);
> при отсутствии — авторизация на входе в reverse-proxy, а `url` указывает на
> прокси без заголовков.

### 8.3. Reverse-proxy (эскиз Caddy)
```
hds.example.com {
    # аутентификация на входе (по выбору): basic/OAuth/JWT
    reverse_proxy /mcp* 127.0.0.1:8787
    reverse_proxy /ui*  127.0.0.1:8765
    reverse_proxy /v1/* 127.0.0.1:8010
}
```
