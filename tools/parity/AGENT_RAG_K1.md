## 1. Что измерялось

1. **Качество самого поиска** по анонимным образам (A0(10), повтор на стенде K1):
   `hds search <вопрос> --limit 30 --json`, `recall@1/5/10/30`, MRR, по типам

2. **Сравнение конфигураций агента** на готовом агенте:

## 5. Правило решения §6 и решение владельца

Правило (дословно): «RAG оставляем включённым, если (А) не хуже (Б) по полноте и
экономит ≥ 25 % токенов на вопрос **или** заметно выигрывает по полноте на вопросах
„поиск по смыслу“. Иначе `agent.mcp.disk_search.enabled: false` по умолчанию (D23)».

Применение к числам:

| Условие | Значение | Выполнено |
|---|---|---|
| (А) не хуже (Б) по полноте | 1,775 ≥ 0,325 | да |
| Экономия токенов ≥ 25 % | **−43,7 %** (А тратит больше) | **нет** |
| Заметный выигрыш на `semantic` (порог +0,5 из 2) | **+1,667** (2,0 против 0,333) | **да** |

Формальный итог по правилу — **`keep`** (срабатывает ветка «заметно выигрывает по
поиску по смыслу»), это же записано в `k1-summary.json → decision.verdict = keep`.

**Решение владельца (22.11.2026): выключить RAG по умолчанию.** Мотивировка:
экономии токенов нет — включённый поиск стоит +43,7 % контекста и дороже по ходу,
а в MVP значение по умолчанию должно быть консервативным; RAG остаётся доступной
опцией (`agent.mcp.disk_search.enabled: true`), и на вопросах «по смыслу» её
преимущество видно из таблиц выше. Решение зафиксировано здесь, в
`RELEASE_NOTES_0.27.0.md`, `AGENT_A6_REPORT.md` и `STATUS.md`.

**Следствия (честно):** с выключенным поиском на таком проекте падает полнота
(0,325 против 1,775), «поиск по смыслу» — 0,333 против 2,0, и 57,5 % ходов упираются
в `--max-iterations`. Если пользователь работает с проектом на десятки документов и
задаёт вопросы «где говорится о…», ему нужно включить поиск (и при необходимости
поднять `--max-iterations`). Это же — аргумент повторить замер на проекте 100+
документов: там ожидается выигрыш и по токенам.

## 6. Ограничения замера

1. **Одна модель** — `~deepseek/deepseek-flash-latest` (быстрая и дешёвая). На более
   сильной модели полнота (Б) может быть выше, а разрыв — меньше; на более слабой —
   больше. Абсолютные числа не переносятся на другую модель, сравнение (А)/(Б) — да.
2. **20 вопросов, 34 документа** — небольшая выборка; по типам — 4–12 прогонов,
   поэтому различия в 1–2 прогона не значимы. Выводы о направлении (полнота, сбои,
   токены) устойчивы, точные проценты — ориентир.
3. **`--max-iterations 12`** — штатный лимит CLI. Без RAG он стал узким местом;
   с другим лимитом числа (Б) изменятся (вероятно, в лучшую сторону по полноте и
   в худшую по токенам).
4. **Токены включают неудачные ходы**: у (Б) 23 из 40 ходов не дошли до ответа,
   но потратили 70–130 тыс. токенов. Поэтому «токенов на ход» — это стоимость
   попытки, а не стоимость готового ответа; для сравнения приведены и успешные ходы
   (121,0 тыс. против 83,1 тыс.).
5. **Точность** считалась как доля имён файлов в ответе, которых нет в проекте
   (выдуманные). Шумные, но существующие ссылки (перечисление всех писем) не
   штрафовались — поэтому точность (Б) 0,956 при покрытии 0,146.
6. **Полнота автоматическая** — по вхождению эталонных имён файлов (образ или
   исходное имя после деанонимизации). Смысловая верность фактов вручную
   выборочно проверена по 8 ответам (даты, номера требований) — расхождений
   с эталоном не найдено; сплошного слепого ревью не было.
7. **Инфраструктурные сбои исключены**: 8 ходов упали на TLS-ошибке корпоративной
   цепочки сертификатов (не поведение агента) и перезапущены; в финальных числах
   остались только сбои по `max-iterations`. Перезапуски — `k1-rerun.log`.
8. **Cloud-провайдер**: ключ и модель задавались только в стендовом
   `secrets.json`/`projects.json`; в отчёт, golden и коммит не попадают. Стоимость —
   из `usage.total_cost`, оценка провайдера.
