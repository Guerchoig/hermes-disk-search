## 0. Задача

### 0.1 Для кого и зачем

Программа `hermes-disk-search` (далее — **hds**) — набор средств ИИ-поддержки
**аналитиков и менеджеров проектов внедрения 1С**. Они работают с **проектными
документами**, а не с кодом: ТЗ и частные ТЗ, обследования, концепции, реестры
требований и gap-анализ (xlsx), коммерческие предложения, уставы, план-графики
(MS Project), протоколы совещаний, письма, презентации, договоры и акты. В этих
документах много персональных и коммерческих данных: ФИО и должности сотрудников
заказчика и исполнителя, наименования организаций, реквизиты, адреса, телефоны,
почта, суммы.

Нужен ИИ-агент на облачной модели, который умеет:
* анализировать документы проекта (сравнение, поиск противоречий, сопоставление
  требований с типовой функциональностью 1С);
* искать сведения в интернете и в базе знаний 1С (ИТС через MCP `1c-buddy`);
* искать по документам проекта (RAG через MCP `disk-search`);
* создавать и изменять документы (протоколы, письма, отчёты, реестры).

При этом **ни облачная модель, ни внешние сервисы не должны получать персональные и
коммерческие данные** пользователя.

### 0.2 Парадигма двух зон

* **Зона пользователя** — оригиналы документов, настоящие имена и реквизиты, вкладка
  чата в браузере.
* **Анонимная зона** — агент, его история и контекст, рабочие файлы и всё, что уходит
  в облако. Вместо персональных данных здесь **метки** вида `[PERSON_3]`, `[ORG_1]`.
* При пересечении границы данные автоматически анонимизируются (пользователь → агент)
  или деанонимизируются (агент → пользователь). Для каждого документа зоны
  пользователя демон поддерживает **образ** в анонимной зоне, и наоборот.

### 0.3 Почему не «анонимизирующий прокси перед обычным агентом»

Если агент работает в зоне пользователя, а анонимизируются только его запросы к
модели, то:
1. агент хранит историю чата в открытом виде и каждый раз отправляет её целиком —
   анонимизировать растущий контекст на лету дорого (NER) и ненадёжно;
2. рассуждения модели пришлось бы отделять от ответа, причём потоковый ответ
   нарезан на произвольные куски;
3. приложенные файлы и ссылки на локальные ресурсы пришлось бы подменять образами на
   лету;
4. прокси не управляет агентом: инструменты агента (файлы, MCP) по-прежнему видят
   оригиналы.

**Решение этого плана:** агент **изначально и целиком живёт в анонимной зоне**. Границу
пересекают только реплики пользователя, показываемые ему события и файлы. Всё это
проходит через код hds, а не через агента.

## 1. Ключевые принципы

**П1. Агент видит только анонимную зону.** История, контекст, рабочие файлы, результаты
инструментов и MCP — только с метками. Отдельно анонимизировать историю не нужно: в неё
изначально попадает только анонимизированное.

**П2. Направления несимметричны.**
* *Агент → пользователь (деанонимизация):* найти метки регуляркой и подставить значения
  из базы. Это дёшево, детерминированно и безопасно: данные движутся к владельцу.
  Поэтому пользователю можно показывать **всё** — рассуждения, вызовы инструментов,
  ответы — с настоящими значениями. Потоковый ответ обрабатывается буфером, который
  удерживает незакрытую `[` на границе куска (готовая реализация —
  `StreamDeAnonymizer` в `sidecar/hds_anonymize/replacer.py`).
* *Пользователь → агент (анонимизация):* NER — дорого и вероятностно. Применяется только
  к новым данным: реплике пользователя и новому или изменённому файлу.

**П3. Контроль всего исходящего — словарём, а не NER.** Всё, что покидает машину
(запросы к облачной модели и вызовы внешних MCP), перед отправкой сканируется словарём
**всех известных значений** из базы меток. Это алгоритм Aho-Corasick: миллисекунды,
модели не участвуют. Найденное заменяется меткой. Так ловятся утечки, которые NER
пропустил при анонимизации, а значение, добавленное в базу позже, вычищается из всех
следующих запросов.

**П4. Границу контролирует код hds, а не модель.** Агент — это экземпляр агентного ядра
Cline (`@cline/sdk`), который запускает и настраивает hds: каталоги, инструменты, MCP,
HTTP-клиент. Модель не может переопределить эти настройки.

**П5. Оригиналы не перезаписываются автоматически.** Новые файлы агента появляются в
зоне пользователя сами, а изменённая версия существующего документа заменяет оригинал
только по явному «Принять».

**П6. «Не умеем надёжно обработать — не отправляем».** Файл, который нельзя надёжно
анонимизировать, в анонимную зону не попадает и получает видимый пользователю статус.

## 3. Решения

### 3.1 Решения владельца

| # | Решение |
|---|---|
| D1 | Интерфейс агента — **своя вкладка-чат «Агент» в `hds ui`**; агент — **Node-процесс на `@cline/sdk`** (headless-ядро Cline без UI), запускаемый и настраиваемый hds |
| D2 | **Проект** = одна папка в зоне пользователя (путь — в `projects.json` вместе с именем). Демон рекурсивно зеркалит её в анонимную зону; структура папок повторяется 1:1, имена файлов и папок — с метками проекта. Плюс разовое «приложить файл» из чата |
| D3 | **Одна база меток, два уровня.** Уровень 0 — глобальные метки (сущности), связанные с исходными значениями. Уровень 1 — метки проекта, связанные с глобальными. В файлы, имена файлов и папок проекта и в облако попадают **только метки уровня 1** |
| D4 | **Совместимость со старой базой не нужна**: `data/anonymize.db` создаётся заново, миграции нет |
| D5 | Новые файлы агента появляются в зоне пользователя **автоматически**. Изменённый образ существующего документа заменяет оригинал **только по кнопке «Принять»** — с проверкой, что оригинал не менялся, и резервной копией |
| D6 | MVP — изоляция средствами агента (набор инструментов, их область действия, своя конфигурация). Отдельная учётная запись Windows — фаза 2 |
| D7 | **Одна сущность — одна метка**: словоформы склеиваются по лемме. Метка на месте исходной формы восстанавливается точно; в новом тексте агента падеж согласуется по суффиксу `[PERSON_1\|дат]`, при сомнении — пометка «проверить» |
| D8 | Агенту разрешены MCP **`tavily`** (интернет), **`1c-buddy`** (база знаний 1С) и **`disk-search`** (RAG по анонимной зоне). Прежний запрет «агент не ходит в сеть» отменён |
| D9 | **Индекс `disk-search` — только по анонимной зоне.** В MVP корень индексации задан жёстко: корень анонимной зоны, служебные папки исключены. Содержимое текущего индекса удаляется |
| D10 | У агента **остаются инструменты чтения и изменения файлов**, их область действия ограничена анонимной зоной |
| D11 | **«Программирующий» Cline владельца (VS Code + Cline) не затрагивается**: ограничения агента анонимной зоны на него не распространяются, на машине две независимые конфигурации |
| D12 | Облачный провайдер выбирается **в настройках агента**: OpenRouter, российский провайдер или любой другой, который поддерживает SDK (в т.ч. прямой Anthropic API). VPN и исключения VPN-прокси настраивает администратор Windows — вне рамок проекта |
| D22 | Просьба изменить `pdf`, `pptx` или `mpp`: оригинал не меняется, правки оформляются новым документом рядом (TR-7.3a). Утверждено 17.11.2026 |
| D23 | RAG (`search_local_files`) остаётся у агента как **поиск фрагментов**; ответ синтезирует облачная модель. Агент выбирает инструмент по правилу TR-3.8a; полезность RAG проверяется замером A0(10) и контрольной точкой K1 (§6). Если выигрыша нет — RAG для агента выключается настройкой `agent.mcp.disk_search.enabled`, без переделки архитектуры. Утверждено 17.11.2026 |

### 3.2 Решения архитектора (обоснование — в §4–§5)

| # | Решение | Почему |
|---|---|---|
| D13 | **Отдельного прокси к облачной модели нет.** Агент подключается к провайдеру обычным путём (настройки провайдера SDK). Фильтр исходящего (П3) встраивается в HTTP-клиент агента через штатную опцию SDK `ClineCore.create({ fetch })` | ответ на вопрос владельца: прокси не обязателен. Опция `fetch` даёт тот же контроль над точными байтами запроса и работает с любым провайдером |
| D14 | Вызовы и результаты внешних MCP (`tavily`, `1c-buddy`) проходят тот же словарный фильтр через хуки `beforeTool` (подмена input) и `afterTool` (подмена result) | П3 для MCP; результаты чистятся, чтобы найденные в интернете настоящие названия не оседали в истории агента |
| D15 | Агент запускается в режиме `backendMode: "local"`, с **собственной закреплённой копией** SDK (`sidecar/hds_agent/node_modules`) и **своими** каталогами конфигурации и состояния; `HOME`/`USERPROFILE` процесса переопределены | так обеспечивается D11: агент не читает `~/.cline` (MCP, правила, скиллы, плагины, ключи программирующего Cline) и не подключается к его hub-демону |
| D16 | Терминал (`run_commands`) в MVP **выключен** | путь в команде оболочки нельзя ограничить анонимной зоной: `type C:\Users\…` прочитает любой файл. Терминал станет возможен с отдельной учётной записью Windows (фаза 2) |
| D17 | Суб-агенты и команды агентов **включаются, если спайк A0 подтвердит**, что на них действуют те же инструменты, хуки, `fetch` и каталоги | принципиального запрета нет; риск — неизвестно, наследуют ли они ограничения |
| D18 | PDF, PPTX и MS Project (`.mpp`) попадают в анонимную зону как **текстовый образ** `<имя>.<ext>.md` (текст извлекает существующий `hds_extract`, затем он анонимизируется как MD). Образ — только для чтения | в проектах 1С много ТЗ в PDF, презентаций и план-графиков; честно пересобрать анонимный PDF/PPTX дорого, а агенту для анализа достаточно текста |
| D19 | **Список «не анонимизировать»** (`agent.keep_terms`): названия продуктов и конфигураций 1С («1С:ERP», «1С:Бухгалтерия», «ЗУП», «УТ 11», «Документооборот» и т.п.), фирма «1С», типовые роли проекта | иначе NER примет «1С:ERP» за организацию, и агент потеряет предмет анализа |
| D20 | Вкладка «Агент» в MVP — только desktop-профиль (в server-профиле — 403 с объяснением) | многопользовательскому агенту нужны отдельные учётные записи и квоты — фаза 2 |
| D21 | Имена каталогов проектов в анонимной зоне — **по id** (`P0001`), а не по имени проекта | имя проекта («Внедрение ERP в …») само по себе содержит данные заказчика |

## 4. Архитектура

### 4.1 Термины

| Термин | Смысл |
|---|---|
| **Проект** (`P`) | папка зоны пользователя + её зеркало в анонимной зоне + своё пространство меток. Id `P0001`, имя видит только пользователь |
| **Папка проекта** | папка документов проекта в зоне пользователя (`projects.json[*].path`) |
| **Workspace** | зеркало папки проекта в анонимной зоне: `<agent.root>\P0001\workspace\` — рабочая папка (`cwd`) агента |
| **Образ** | анонимизированная копия документа папки проекта в workspace |
| **Сущность / глобальная метка** (уровень 0) | один реальный объект (человек, организация, телефон…) со всеми словоформами |
| **Метка проекта** (уровень 1) | `[PERSON_3]` — представление сущности в одном проекте |
| **Вариант агента** | деанонимизированная версия документа, который агент изменил; ждёт «Принять» |
| **Фильтр исходящего** | словарная проверка всего, что уходит из машины (П3) |

```
 папка проекта ◄────────────────► │ hds agent-sync (демон)  ◄──────────────►│ <agent.root>\P0001\workspace\
   (оригиналы)                    │  анонимизация / деанонимизация файлов    │         ▲
                                  │                                         │ hds watch → index.db (только
 data\anonymize.db ◄── только Python-воркер hds_anonymize                   │  workspace всех проектов)
```

| Процесс | Язык | Статус | Роль |
|---|---|---|---|
| `hds ui` + crate `hds-agent` | Rust | расширение | вкладка «Агент», `/api/agent/*`, SSE; держит процесс агента; деанонимизация событий; фильтр исходящего; брокер `host_call` |
| `hds_anonymize` | Python | расширение | база меток v2, `anonymize_text`, файловые акты проекта, office-операции |
| `hds_agent` | Node/TypeScript | **новый** | ClineCore; подключение провайдера и MCP; хуки и `fetch`; события → stdout |
| `hds agent-sync` | Rust | **новый** демон | двустороннее зеркало «папка проекта ↔ workspace» |
| `hds watch`, `hds mcp-http` | Rust | изменение конфигурации | индекс и поиск — только по workspace (D9); маршрут `/mcp/agent/<P>` |

**Где хранятся исходные значения:** в `anonymize.db`, в памяти процессов `hds ui`,
`hds agent-sync`, `hds_anonymize` и в зоне пользователя. Процесс `hds_agent` и всё, что
он запускает (MCP), **не получают ни одного исходного значения**: реплики анонимизирует
Rust до передачи агенту, события деанонимизирует Rust после получения, словарь
фильтра живёт в Rust (`hds_agent` вызывает фильтр через `host_call`).

### 4.3 Канал `hds ui` ↔ `hds_agent`

stdio, NDJSON, JSON-RPC 2.0, как у остальных sidecar'ов. Канал **двунаправленный**:
* hds → агент: `hello`, `start {project, session_id?}`, `send {text}`, `abort`, `stop`,
  `shutdown`;
* агент → hds, нотификации: `event {…}` — события сессии (текст, рассуждения,
  вызовы и результаты инструментов, вопросы, итог);
* агент → hds, запросы `host_call` (id с префиксом `h`), hds отвечает:
  `egress_check {kind: model|mcp_in|mcp_out, body}` → очищенное тело + флаг
  блокировки; `office_read|office_edit|office_create {path, …}` — исполняет Python;
  `ask_user {question}` → ответ пользователя.

Транспорт `hds_extract::Worker` умеет только «запрос → ответ», поэтому в `hds-agent`
пишется свой цикл чтения со встречными запросами (решается в фазе A3).

### 4.5 Два Cline на одной машине (D11, D15)

| | «Программирующий» Cline владельца | Агент анонимной зоны |
|---|---|---|
| Что это | расширение VS Code (и CLI), ставится и обновляется владельцем | Node-процесс `hds_agent` (headless-ядро `@cline/sdk`, **без UI**); запускает `hds ui` |
| Код | своя версия Cline | **своя закреплённая** копия `@cline/sdk` в `sidecar/hds_agent/node_modules` (обновляется только с hds) |
| Конфигурация | `%USERPROFILE%\.cline\…` и `<каталог расширения Cline>` (§2) | `<agent.root>\P0001\agent-config\` (процесс запускается с `HOME`/`USERPROFILE` = этот каталог) |
| MCP | любые, на усмотрение владельца | только `tavily`, `1c-buddy`, `disk-search /mcp/agent/<P>` (их пишет hds) |
| Правила, скиллы, плагины | глобальные `~/.cline/rules`, `skills`, `plugins` | только правила hds (`privacy.md`, `1c-domain.md`); чужие плагины не грузятся |
| Ограничения | **нет** (ничего из этого плана на него не действует) | область файлов, фильтр исходящего, без терминала |
| Hub-демон Cline | как настроит владелец | не используется (`backendMode: "local"`) |

Почему не Cline Desktop: это отдельное приложение с собственным UI (на Windows — бета).
hds не может встроить в него свой `fetch`, хуки и деанонимизацию событий, а его
настройки, вероятно, общие с CLI в `~/.cline` (тогда ограничения задели бы и
программирующий Cline). Headless-ядро в SDK есть, поэтому вторая установка с UI не
нужна: её роль играет вкладка «Агент» в `hds ui`.

**Единственное общее** у двух Cline — это MCP-серверы как программы: исполняемый файл
`1c-buddy` из `%USERPROFILE%\.cline\mcp\1c-buddy\` и пакет `tavily-mcp`. Запись о них в
конфигурации агента hds создаёт свою; конфигурацию программирующего Cline hds **не
меняет**. Пакет `tavily-mcp` закрепляется версией в `sidecar/hds_agent/package.json`
(не `npx tavily-mcp@latest`: незакреплённый код из сети получал бы анонимные данные).

**Следствие D9 для программирующего Cline:** его MCP `disk-search` (маршрут `/mcp`)
после переключения индекса тоже будет искать **только** по анонимной зоне (по всем
проектам, без фильтра). Поиск по оригиналам на этой машине пропадает — так решил
владелец (D9). Правило `~/.cline/rules/disk-search.md` при этом остаётся верным по
форме.

### 4.6 Почему нет прокси к облачной модели (D13)

В редакции 1 агент обращался к модели через локальный HTTP-шлюз hds. Цели было две:
(а) видеть точные байты каждого запроса и чистить их словарём;
(б) держать ключ облака вне процесса агента.

Цель (а) достигается без прокси: `ClineCore.create({ fetch })` — штатная опция SDK,
через которую идут **все** HTTP-запросы провайдеров локальной сессии. Наш `fetch`
вызывает `host_call egress_check`, получает очищенное тело и отправляет запрос
провайдеру напрямую. Провайдер подключается обычным путём: OpenRouter, российский
OpenAI-совместимый, Anthropic — что выбрано в настройках агента.

Цель (б) заменяется так: ключ облака находится в процессе агента, но (1) модель не
получает его в контексте; (2) у агента нет терминала, а значит, нет доступа к
переменным окружения; (3) ключи провайдера и MCP входят в **словарь блокировки**
фильтра исходящего: если ключ появится в тексте запроса или вызова MCP (попытка
вывести его через prompt-injection), запрос не уйдёт.

Остаточный риск: если какой-то код SDK пошлёт запрос **мимо** переданного `fetch`.
Это проверяется в спайке A0 для каждого разрешённого провайдера (запросы считаются
заглушкой). Провайдер, у которого запросы идут мимо `fetch`, в список разрешённых не
попадает. В фазе 2 правило брандмауэра Windows для отдельной учётной записи агента
превращает это в жёсткую гарантию.

**Сеть и VPN.** VPN настраивает администратор Windows, это вне рамок проекта. Но
встроенный `fetch` Node **не использует** системный прокси Windows автоматически. Если
VPN работает как локальный прокси (например, `127.0.0.1:10809`), а не как системный
туннель, агенту нужен явный маршрут. Поэтому `agent.network.proxy: auto | none | <url>`:
`auto` читает системные настройки прокси Windows (WinINet) и передаёт их нашему
`fetch` (undici `ProxyAgent`) и MCP-процессам (`HTTP(S)_PROXY`, `NO_PROXY`). Сам VPN мы
не настраиваем.

### 4.7 Ответы на частые вопросы об архитектуре

* **Кто выполняет агентский цикл — плагин или наше приложение?** Ни тот, ни другое.
  Цикл «запрос к модели → вызовы инструментов → результаты → снова модель → … →
  итог» целиком выполняет **ядро SDK** (`ClineCore`, внутри — класс `Agent` из
  `@cline/agents`): это тот же цикл, что у Cline в VS Code, вместе со сжатием контекста
  (compaction), повторами при ошибках, встроенными инструментами и подключением MCP.
  Наш Node-процесс `hds_agent` только **настраивает** ядро (провайдер, `cwd`, MCP,
  `fetch`, политики инструментов) и передаёт события наружу; кода цикла в hds нет.
  Плагин `hds-guard` — пассивные **хуки**: ядро вызывает их в определённых точках
  цикла (перед вызовом инструмента, после него), а они разрешают, запрещают или
  подменяют данные. Сам плагин цикл не ведёт и без ядра ничего не делает.
* **Агент работает только внутри VS Code?** Нет. «Плагин» в этом плане — объект-расширение
  `@cline/sdk` (хуки `beforeTool`/`afterTool`), загружаемый **в наш Node-процесс**
  `hds_agent`. К VS Code и расширению Cline он отношения не имеет. Агент работает
  везде, где запущен `hds ui`; пользователь общается с ним во вкладке «Агент» браузера.
* **Почему выключен терминал?** См. D16: путь в команде оболочки нельзя ограничить
  анонимной зоной.
* **Суб-агенты?** См. D17: включаются, если A0 подтвердит, что на них действуют те же
  ограничения.

**TR-x.y** — требование; всё перечисленное входит в MVP, если не сказано «фаза 2».

### 5.1 База меток v2 (`anonymize.db`)

**TR-1.1.** Доступ к базе — **только** через Python-модуль
`sidecar/hds_anonymize/vault.py` (заменяет `mapping_store.py`). Rust и Node к файлу не
обращаются. Путь — `anonymize.db_path` (по умолчанию `data/anonymize.db`).

**TR-1.2. Схема** (SQLite WAL, `busy_timeout`, выдача номеров в `BEGIN IMMEDIATE`):

```sql
meta(key PK, value)               -- schema_version=2; rev — растёт при любой записи
-- уровень 0: глобальные метки = сущности (исходные значения живут ТОЛЬКО здесь)
entities(id INTEGER PK, type TEXT, n INTEGER, norm_key TEXT, ts REAL,
         UNIQUE(type, n), UNIQUE(type, norm_key))
forms(id INTEGER PK, entity_id → entities, value TEXT, gram TEXT NULL,
      origin TEXT CHECK(origin IN ('seen','derived')), UNIQUE(entity_id, value))
global_counters(type PK, last INTEGER)
-- уровень 1: метки проектов, связаны с глобальными
projects(id TEXT PK, ts REAL)
labels(project_id, entity_id → entities, type, n INTEGER, ts REAL,
       PRIMARY KEY(project_id, entity_id), UNIQUE(project_id, type, n))
counters(project_id, type, last INTEGER, PRIMARY KEY(project_id, type))
aliases(project_id TEXT NULL, type, n, entity_id)  -- след «Объединить метки» (TR-2.6)
keep_terms(value TEXT PK)                          -- «не анонимизировать» (D19)
```

* Имя проекта в базе **не хранится** (оно в `projects.json` зоны пользователя).
* Глобальные метки `[PERSON_7]` используют карточка «Анонимизация» и `hds anon` —
  их поведение не меняется. Метки проекта используются только в анонимной зоне.
  Синтаксически метки уровней одинаковы; уровень определяется контекстом акта.

**TR-1.3. Старая база не переносится** (D4): при первом запуске v2 файл
`anonymize.db` схемы v1 переименовывается в `anonymize.db.v1-<дата>.bak`, создаётся
новая база. Файлы, обработанные карточкой 0.23.x, этой версией не деанонимизируются;
факт фиксируется в RELEASE_NOTES.

**TR-1.4. Синтаксис метки** — `[TYPE_n]` или `[TYPE_n|падеж]` (TR-2.3). Регулярное
выражение `\[([A-Z_]+)_(\d+)(?:\|([а-яё,]+))?\]` — единое для Python (`vault.py`,
`replacer.py`, `handlers.py::PLACEHOLDER_TOKEN_RE`) и Rust.

**TR-1.5. Несвязываемость проектов.** Номера меток проекта выдаются счётчиками
проекта в порядке первого появления в проекте и не выводятся из глобального номера.
Глобальные метки и id сущностей **никогда** не попадают в анонимную зону.

**TR-1.6. Снимок для Rust:** RPC `vault_snapshot {project_id}` →
`{rev, labels: [{label, type, forms: [{value, gram, origin}]}], others: [value…],
keep: [value…]}`. Здесь `labels` — метки проекта, `others` — формы всех прочих
сущностей базы (для фильтра), `keep` — список D19. Ответ содержит исходные значения;
Rust держит его **только в памяти** и не пишет в журналы. `vault_rev` — дешёвая
проверка актуальности. Объявляется в `hello.capabilities`.

**TR-1.7. Новые RPC воркера:** `anonymize_text {project_id, text}` (реплики и
вложения-тексты: NER + regex + словарь известных форм проекта + `keep_terms`;
результат — текст с метками и список меток), `label_for_value {project_id, value,
type}` («Скрыть ещё…»), `merge_entities {project_id, keep, drop}`,
`vault_drop_project {project_id}`, файловые акты с `project_id` и `mode: "agent"`
(TR-6.3), `office_read/office_edit/office_create` (TR-3.5).

### 5.2 Морфология и сущности (D7)

**TR-2.1. Склейка словоформ.** `norm_key` — нормальная форма значения:
* `PERSON` — разбор Natasha `NamesExtractor` → `фамилия|имя|отчество` в именительном
  падеже, нижний регистр; инициалы — `и.`;
* `ORG`, `LOC` и прочие словесные типы — леммы слов (pymorphy2); текст в кавычках
  («Ромашка») и латиница не лемматизируются;
* шаблонные типы (`PHONE`, `EMAIL`, `INN`, `KPP`, счета, номера документов, `MONEY`,
  `DATE`) — каноническая запись (только цифры; почта в нижнем регистре); словоформ
  нет.

**TR-2.2. Порождённые формы.** Для `PERSON` и однословных `ORG`/`LOC` при создании
сущности pymorphy генерирует все падежи (`origin='derived'`). Они нужны фильтру
исходящего (узнавать формы, которых ещё не было в текстах) и подстановке падежа.

**TR-2.3. Падежный суффикс.** В режиме проекта метка получает суффикс по граммемам
исходной формы, если это не именительный падеж единственного числа: `род`, `дат`,
`вин`, `твор`, `пред`, для множественного числа — `,мн`. Пример: «передать Иванову
И. И.» → «передать [PERSON_3|дат]». В карточке «Анонимизация» суффиксов нет. В
**именах файлов и папок** суффикса нет: символ `|` в именах Windows запрещён.

**TR-2.4. Обратная подстановка** `[T_n|g]`: форма `seen` с граммемами `g` → форма
`derived` с `g` (пометка «проверить» в отчёте) → именительная форма с пометкой
«падеж не согласован». Многословные `ORG` подставляются в нужном падеже, только если
такая `seen`-форма есть в базе; иначе — именительный падеж и «проверить». Терпимый
разбор: `[person_3]`, `[PERSON 3]`, `[PERSON-3]` распознаются с пометкой «проверить».

**TR-2.5. Правила для агента** (`agent-config\rules\privacy.md`) объясняют синтаксис
меток и суффикса и просят ставить суффикс в собственном тексте. Метку без суффикса
подстановка считает именительным падежом.

**TR-2.6. «Объединить метки».** NER не склеивает частичные упоминания: «Иванов»,
«Иванов Иван Иванович» и «И. И. Иванов» могут стать **тремя** сущностями, у агента —
`[PERSON_3]`, `[PERSON_5]`, `[PERSON_8]`. Слово «ручное» означало: склейку выполняет
**пользователь** — во вкладке «Агент» есть панель **«Метки проекта»**: таблица «метка →
значение (формы) → число упоминаний». Пользователь отмечает несколько строк и
нажимает кнопку **«Объединить»** (это не команда чата). Результат:
1. в базе формы младших сущностей переносятся в старшую, младшие номера остаются
   псевдонимами (`aliases`), поэтому уже выпущенные файлы с `[PERSON_5]`
   по-прежнему деанонимизируются;
2. демон пересоздаёт образы, где встречаются младшие метки: в workspace остаётся
   только `[PERSON_3]`;
3. агенту отправляется служебное сообщение: «метки [PERSON_5], [PERSON_8] теперь
   обозначаются [PERSON_3]».
Там же доступны **«Разъединить»** (отменить ошибочную склейку) и **«Не скрывать»**
(значение уходит в `keep_terms`). Автоматическая склейка частичных упоминаний — фаза 2.

### 5.3 Агент `sidecar/hds_agent` (Node/TypeScript)

**TR-3.1. Рантайм и поставка.** Node ≥ 22. Портативный Node ставит установщик
(`installers/build_agent_sidecar.ps1`) в `sidecar/node/`, как портативный CPython;
зависимости — `npm ci` по `package-lock.json` с **закреплёнными** версиями
`@cline/sdk`, `tavily-mcp`, undici. Код — TypeScript, собирается в
`sidecar/hds_agent/dist/worker.mjs` (esbuild). Протокол — §4.3.

**TR-3.2. Окружение процесса** (D15). `hds-agent` запускает Node с очищенным
окружением: `HOME`, `USERPROFILE`, `APPDATA`, `LOCALAPPDATA` → подкаталоги
`<P>\agent-config`; без унаследованных ключей провайдеров; `HTTP(S)_PROXY` — только
из `agent.network.proxy` (§4.6). `ClineCore.create({ backendMode: "local",
clientName: "hds-agent", fetch: egressFetch, toolPolicies })` без телеметрии и
feature-flags (no-op по умолчанию). Сессия: `cwd = workspaceRoot = <P>\workspace`,
каталог данных SDK — `<P>\agent-state`. Плагины — **только** из списка, переданного
hds; каталог `~/.cline/plugins` не просматривается (проверка — TR-3.10).

**TR-3.3. Провайдеры и модели** (D12). Вкладка «Агент» → «Настройки» задаёт провайдера
и модель из списка, поддерживаемого SDK: `openrouter`, OpenAI-совместимый
(российские провайдеры — по `base_url`), `anthropic` и другие, прошедшие проверку A0
(§4.6). Ключи хранятся в `data\agent\secrets.json` и передаются в `config.apiKey` при
старте сессии.

**TR-3.4. Файловые инструменты** (D10). Встроенные инструменты SDK `read_files`,
`search_codebase`, `editor`, `apply_patch`, `ask_question`, `submit_and_exit`
**включены**; `run_commands` **выключен** (D16); встроенный `fetch_web_content`
выключен (интернет — через `tavily`). Область действия ограничивает хук `beforeTool`
плагина `hds-guard`: каждый путь в аргументах канонизируется (абсолютизация от `cwd`,
разрешение `..`, junction/symlink через `realpath`; отказ для UNC, `\\?\`,
альтернативных потоков `file:stream`, имён устройств `CON`/`NUL`) и должен лежать
внутри `<P>\workspace`, иначе `{skip: true, reason}`. Для `search_codebase` без пути
подставляется `cwd`. Хук работает в режиме fail-closed: ошибка хука блокирует вызов
(точное значение `hookErrorMode` — по итогам A0).

**TR-3.5. Документы Office.** Встроенный `editor` правит текстовые файлы (`md`, `txt`,
`csv`, `json`). Для `docx`/`xlsx` hds регистрирует инструменты (`extraTools`),
которые выполняются через `host_call` в Python. `python-docx`/`openpyxl` уже есть в
venv анонимизации; операции — порт `office_ops.py` из прежнего проекта
`anonymizer_proxy`:
* `office_read(path)` — текстовое представление: абзацы с номерами, таблицы в
  markdown, листы и ячейки с адресами;
* `office_edit(path, ops[])` — `replace_text`, `set_cell`, `add_row`, `add_column`,
  `insert_paragraph`, `delete_paragraph`; форматирование, числа, даты и формулы
  сохраняются;
* `office_create(path, kind, content)` — новый docx (из markdown), xlsx (из таблиц) или
  pptx (слайды «заголовок + тезисы» без оформления; `python-pptx` добавляется в venv
  анонимизации — в venv извлечения он уже есть).
Править бинарные `docx`/`xlsx` встроенным `editor` хук не даёт; `read_files` для
`docx`/`xlsx` перенаправляется на `office_read`.

**TR-3.6. MCP агента** (D8). hds сам пишет список MCP в `<P>\agent-config`:

| MCP | Транспорт | Доступ | Фильтр (П3) |
|---|---|---|---|
| `disk-search` | streamable HTTP `http://127.0.0.1:8787/mcp/agent/<P>` с токеном проекта | `search_local_files`, `index_status`; `ask_my_files` и управление индексацией — **нет** (TR-4.4) | не нужен: данные анонимны и не покидают машину |
| `1c-buddy` | stdio; исполняемый файл из `%USERPROFILE%\.cline\mcp\1c-buddy\` (путь — `agent.mcp.onec_buddy.command`), env и ключ — из `secrets.json` | все инструменты | **да**: input (`beforeTool`) и result (`afterTool`) |
| `tavily` | stdio; закреплённая версия `tavily-mcp` из `sidecar/hds_agent/node_modules` | `tavily_search`, `tavily_extract` (`crawl`/`map` — по настройке) | **да**: input и result |

Другие MCP добавляются только через настройки hds (белый список
`config.yaml: agent.mcp.*`, у каждого — признак «внешний → фильтр»). MCP из `~/.cline`
агент не видит.

**TR-3.7. Суб-агенты** (D17): `enableSpawnAgent` и `enableAgentTeams` берутся из
`agent.subagents` (по умолчанию `false` до подтверждения A0). Условие включения — тест
A0: суб-агент наследует `fetch`, `hds-guard`, MCP и каталоги, а его вызовы
инструментов видны в событиях.

**TR-3.8. Правила агента.** `privacy.md`: метки и суффиксы, «не угадывать значения»,
«docx/xlsx — только office-инструментами», «изменить документ = править его образ в
workspace», «`*.pdf.md`, `*.pptx.md`, `*.mpp.md` — только чтение; правки оформлять по
TR-7.3a», «выбор инструмента поиска — по TR-3.8a». `1c-domain.md`: предметная
область (§0.1), типовые артефакты проекта внедрения, когда идти в `1c-buddy`
(функциональность типовых конфигураций, стандарты), а когда — в `tavily`. Правила не
содержат путей пользователя и имён.

**TR-3.8a. Правило выбора инструмента поиска по документам проекта** (D23; текст — в
`1c-domain.md`). Цель — не тратить контекст: всё прочитанное остаётся в истории и
отправляется модели на каждом следующем шаге.

| Что нужно найти | Инструмент | Почему |
|---|---|---|
| точная строка, метка (`[PERSON_3]`, `[ORG_1]`), номер договора или требования, код | `search_codebase` (поиск по строке / regex внутри workspace) | точно и мгновенно; RAG по точным строкам хуже |
| «где говорится о…», «какие требования про…», поиск по смыслу или с любыми словоформами по всей папке проекта | `search_local_files` — 2–3 формулировки (синонимы, термины 1С), `limit` 10–30 | находит по смыслу и словоформам, возвращает фрагменты с файлом и страницей, а не документы целиком |
| документ уже найден, нужен раздел | `office_read` / `read_files` с диапазоном (номера абзацев, листы, строки) | дочитать только нужное |
| документ нужен целиком (сверка, правка, реестр) или в проекте мало документов (≈ до 15–20 небольших) | `office_read` / `read_files` целиком | поиск не нужен — дешевле прочитать |
| `index_status` показывает, что индекс не готов, или `search_local_files` вернул предупреждение о неиндексированных файлах (TR-4.7) | `search_codebase` + список файлов + чтение | RAG ещё не видит часть документов |

Сначала поиск, потом чтение: не открывать подряд все документы папки, чтобы найти
один абзац.

**TR-3.9. Жизненный цикл.** Один процесс `hds_agent` на проект (у каждого проекта своё
окружение: `HOME`, `cwd`, список MCP с токеном проекта, словарь фильтра; смешивать их в
одном процессе — риск перепутать проекты). Процессы **не убиваются** при переключении:
живут до `agent.max_live_projects` (по умолчанию 2) последних проектов и выгружаются
по простою `agent.idle_unload_min` (по умолчанию 30 мин). Вкладка открывает проект
**заранее**, при выборе его в списке, не дожидаясь первой реплики. Возобновление
разговора — `start {session_id}` по `sessionId` из `<P>\agent-state`.

Цена запуска (оценка, уточняется замером в A0): старт Node и импорт SDK — 1–2 с; запуск
MCP `tavily` (Node) и `1c-buddy` (Python) — 1–3 с, параллельно; `disk-search` — HTTP,
без запуска; чтение истории сессии с диска — доли секунды. **Модель при возобновлении
не вызывается.** Итого — несколько секунд один раз при открытии проекта; для
переключения между двумя активными проектами — мгновенно. Это нормально: дорогая
часть работы агента — не запуск, а каждый запрос к модели, который **всегда**
отправляет всю (сжатую) историю. Так устроены облачные API: они не хранят состояние
между запросами, и перезапуск процесса этого не меняет.

**TR-3.10. Тесты изоляции** (mock-провайдер со скриптованными ответами):
(а) `read_files` с `..\..\`, абсолютным путём, junction внутри workspace, UNC → отказ;
(б) в событиях нет путей вне workspace; (в) окружение процесса не содержит профиля
пользователя Windows; (г) плагин, положенный в `%USERPROFILE%\.cline\plugins`, не
загружен; (д) ни одного HTTP-запроса мимо `egressFetch` (счётчик заглушки); (е) MCP
из `~/.cline` в сессии отсутствуют.

### 5.4 `disk-search` по анонимной зоне (D9)

**TR-4.1. Переключение индекса (MVP, жёстко).** При `agent.enabled: true` индексатор
(`hds watch`/`hds index`) **игнорирует** `index.roots` и индексирует один корень —
`agent.root`. Каждый `P*\workspace` автоматически становится проектом индекса с
именем `P0001` (механизм `index.roots: [{path, project}]` из M1). `agent-config` и
`agent-state` исключены неявно (как `anonymize.output_dir` в
`pipeline.rs::implicit_excludes`). Вкладка «Настройки» UI показывает «корни заданы
агентом» и не даёт их менять.

**TR-4.2. Сброс индекса.** Переход выполняет команда `hds agent init`: останавливает
`hds watch`, удаляет `index.db` (вместе с `-wal`/`-shm`; путь — `db_path`) и
`data/anonymized` (выход прежней карточки), создаёт пустую базу и запускает
индексацию. Команда идемпотентна и перед удалением спрашивает подтверждение (`--yes`
для установщика).

**TR-4.3. Изоляция проектов в поиске.** Маршрут `POST /mcp/agent/<P>` в `hds mcp-http`
принимает токен проекта (хэш — в `data\agent\secrets.json`) и **всегда** применяет
фильтр `projects = [P]` в `hds_search::search` — независимо от `access.enabled`.
Неверный токен или чужой `P` → 401. Инструментов управления индексацией на этом
маршруте нет. Так агент проекта P0001 не находит фрагменты P0002: их метки не
связаны, и смешивание сбило бы агента.

**TR-4.4. На маршруте агента — только поиск, без локальной генерации.** У `disk-search`
два инструмента поиска, и они устроены по-разному:

| Инструмент | Что делает | Кто «думает» | Скорость | Для агента |
|---|---|---|---|---|
| `search_local_files` | ищет фрагменты: слова (FTS5, лемматизация) + смысл (векторы bge-m3) + переранжирование (bge-reranker) | **никто**: модели только кодируют текст, генерации нет | доли секунды – секунды | **да** |
| `ask_my_files` | тот же поиск + **ответ локальной чат-модели** по найденному (`llm_host`, 9B-модель на RTX 3060: ~15–20 токенов/с, ответ до 600 токенов, 1–3 мин) | слабая локальная модель | минуты, занимает видеокарту | **нет** |

Опасение верное: `ask_my_files` был бы слабым звеном. Сильная облачная модель получила
бы вместо фрагментов готовый пересказ от слабой модели (с её ошибками и обрезанным
списком), ждала бы минуты и занимала бы GPU, нужный для анонимизации. Поэтому
**`ask_my_files` на маршруте `/mcp/agent/<P>` не публикуется**. Агент вызывает
`search_local_files` (несколько формулировок, `limit` до 30), получает фрагменты с
путями и страницами, при необходимости дочитывает файл (`read_files`/`office_read`) и
сам синтезирует ответ облачной моделью. Слабого звена в цепочке нет: локально
работают только модели поиска (эмбеддинг и реранкер), их качество для русского текста
достаточное, генерации нет. Правило агента (TR-3.8) говорит то же. Заодно отпадает
вопрос `chat.provider: remote` для этого маршрута.

**TR-4.6. Поиск по меткам.** Метка `[PERSON_3]` должна искаться как **одно слово**:
стандартный токенизатор FTS5 режет её на `person` и `3`, и запрос «[PERSON_3]» находил
бы любые фрагменты с «person» и цифрой 3. При индексации и в запросе метка
нормализуется в единый токен (`person_3` → `xperson3x`), а векторный поиск
получает текст как есть. Тест: поиск по `[PERSON_3]` возвращает только фрагменты с этой
меткой.

**TR-4.5. Пути в выдаче** — абсолютные пути workspace, т.е. внутри `<agent.root>`. Это
согласуется с TR-3.4: агент может открыть найденный файл.

**TR-4.7. Отставание индекса.** Образ становится доступным агенту сразу, а в индекс
попадает позже (очередь `hds watch`, эмбеддинги). Чтобы агент не считал выдачу
полной, когда она неполная:
1. Демон хранит в реестре (TR-7.2) поле `indexed: pending | done | error`: `pending` —
   при записи образа; `done` — когда в таблице `files` базы `index.db` есть запись с
   путём образа, тем же `content_hash` и успешным статусом. `content_hash` — отпечаток
   индекса (`hds-index/src/hash.rs`, blake2b-16 по размеру, голове и хвосту файла), а не
   sha256 реестра: демон вычисляет его той же функцией. Проверка — периодически, только
   чтение `index.db`.
2. `index_status` на маршруте `/mcp/agent/<P>` отвечает **по проекту**: всего образов,
   проиндексировано, в очереди, ошибки; плюс признак первичного построения индекса.
3. `search_local_files` на этом маршруте, если в проекте есть `pending`, добавляет к
   выдаче предупреждение: «N файлов проекта ещё не проиндексированы (в т.ч. недавно
   изменённые: …); для них используйте `search_codebase` или чтение файла». Список —
   до 10 путей образов.
4. Панель «Файлы проекта» показывает у каждого файла отметку «в индексе / в очереди /
   ошибка индексации».
Тест: образ записан → выдача содержит предупреждение; после индексации —
предупреждения нет.

### 5.5 Шлюз реплик и событий (crate `hds-agent` в `hds ui`)

**TR-5.1. Реплика пользователя** → `anonymize_text {project_id, text}`. Предпросмотр
(`agent.preview_outgoing`, по умолчанию **включён**) показывает ровно то, что получит
агент (метки подсвечены). Кнопки: «Отправить»; «Скрыть ещё…» (выделить фрагмент →
`label_for_value` → пересчёт); «Не скрывать» (снять ложное срабатывание; можно
добавить в `keep_terms`).

**TR-5.2. Пути и вложения.** Файл из папки проекта → в реплику подставляется путь его
образа (по реестру). Файл вне папки проекта → разовая анонимизация в
`workspace\_attachments\`. Абсолютные пути Windows/UNC, набранные в тексте,
распознаются регуляркой и заменяются путём образа или меткой `[PATH_n]`.

**TR-5.3. События агента → пользователю.** Все события (текст, рассуждения, вызовы
инструментов с аргументами, результаты инструментов и MCP, вопросы, итог)
деанонимизируются потоково (порт `StreamDeAnonymizer` на Rust): метки → значения
(TR-2.4), пути workspace → пути папки проекта (по реестру). Ссылка «открыть» ведёт на
оригинал или вариант агента. Переключатель «как видит модель» показывает событие без
подстановки. Неизвестная метка показывается как есть, с пометкой.

### 5.6 Фильтр исходящего (П3, D13, D14)

**TR-6.1. Точки применения:**
* `model` — тело **каждого** HTTP-запроса провайдеру через `egressFetch` (все
  `messages`, system, `tools`, аргументы `tool_calls`); ответ модели не фильтруется;
* `mcp_out` — аргументы вызова внешних MCP (`tavily`, `1c-buddy`) в `beforeTool`
  (подмена `input`);
* `mcp_in` — результат внешних MCP в `afterTool` (подмена `result`).

**TR-6.2. Словарь** (Aho-Corasick; крейт `aho-corasick` уже есть в `Cargo.lock`):
(а) формы сущностей с меткой в проекте → замена меткой проекта с падежным суффиксом;
(б) формы прочих сущностей базы (`others`) → новая метка проекта через
`label_for_value` или блокировка (`agent.filter.unknown: label | block`, по умолчанию
`label`);
(в) системные строки: имя пользователя Windows, имя компьютера, профиль, путь папки
проекта и её подпапок, имена проектов из `projects.json` → `[SYS_n]`;
(г) **секреты**: ключи провайдеров и MCP, токены `/mcp/agent`. В точках `model` и
`mcp_out` запрос с секретом **блокируется** (ошибка агенту, событие пользователю).
Значения из `keep_terms` в словарь не входят. Сравнение — без учёта регистра, по
границам слова, с нормализацией `ё→е`, неразрывных пробелов, типографских кавычек и
дефисов. Значения короче 3 символов в словарь не входят.

**TR-6.3. Особенность `mcp_in`** (результаты интернета и ИТС). Из найденного в сети
вычищаются только значения, **уже известные** базе. Новые настоящие названия
(например, контрагент из статьи) не анонимизируются: агент получил их из открытого
источника, это не утечка. Если агент вставит такое значение в документ, при
деанонимизации оно останется как есть.

**TR-6.4. Аудит.** Каждое срабатывание пишется в аудит (`hds-core::audit`, событие
`agent_egress_redacted`: проект, точка, тип, метка, источник словаря а/б/в/г — **без
значения**) и показывается уведомлением в ленте UI. Срабатывание (а) в точке `model`
означает: значение уже лежит в **истории** агента в открытом виде — NER пропустил его
при анонимизации файла или реплики (см. TR-6.6).

**TR-6.5. Fail-closed.** Нет снимка vault, фильтр упал или снимок старше
`agent.filter.max_stale_sec` → запрос не отправляется, `egressFetch` возвращает агенту
ошибку `privacy_filter_unavailable`. Перед каждым запросом снимок сверяется по
`vault_rev`.

**TR-6.6. «Очистить историю»** (в редакции 1 — «пересобрать историю»). При
срабатывании (а) в точке `model` фильтр чинит **каждый** запрос, но сохранённая
история в `<P>\agent-state` остаётся с открытым значением. Кнопка «Очистить историю» в
уведомлении: hds останавливает сессию, прогоняет файлы истории в `agent-state` через
тот же словарь (значения → метки) и возобновляет сессию. В MVP — **да**: операция
дешёвая (без NER) и убирает «грязный» хвост на диске. Формат файлов истории SDK
уточняется в A0; если менять их небезопасно — новая сессия с кратким пересказом
(фаза 2).

**TR-6.7. Журнал исходящего** (`agent.egress_log`, по умолчанию выключен): тела
запросов после фильтра пишутся в `<P>\agent-state\egress\`. Это проверяемая проекция
«что ушло в облако».

### 5.7 Демон `hds agent-sync` — двустороннее зеркало (D2, D5)

**TR-7.1. Структура.** Папка проекта и `<P>\workspace` — **одно дерево в двух видах**:
относительные пути совпадают, только каждое имя файла и папки анонимизировано
(`Протоколы\Встреча с Ивановым.docx` → `Протоколы\Встреча с [PERSON_3].docx`). Обход
рекурсивный. Служебные папки `.hds-agent`, `~$*`, `*.tmp`, `Thumbs.db` пропускаются.
Служебные папки workspace — `_attachments\` (вложения из чата) и `_conflicts\`
(TR-7.6, случай 2) — в папку проекта **не выпускаются**.

**TR-7.2. Реестр** `data\agent\registry\<P>.db` (SQLite, пишут только демон и кнопки
UI): `artifacts(id, orig_rel, anon_rel, kind: image|text_image|agent_new|attachment,
orig_sha256, anon_sha256_issued, anon_sha256_seen, status, ts)`. Статусы: `synced`,
`unsupported`, `too_big`, `agent_new`, `agent_changed`, `pending_accept`, `accepted`,
`conflict`, `orphan`, `error`.

**TR-7.3. Прямой путь (пользователь → анонимная зона).** Новый или изменённый
оригинал (`wait_stable`) →
* `docx`, `xlsx`, `txt`, `md`, `xml` → `anonymize {project_id, mode:"agent"}` → образ
  того же формата;
* `pdf`, `pptx`, `mpp` → текстовый образ `<имя>.<ext>.md` (D18): `hds_extract` →
  текст со страницами/слайдами/задачами → `anonymize_text` → md; образ только для
  чтения (запись агентом блокирует `hds-guard`);
* прочие форматы и файлы больше `max_file_mb` в workspace **не попадают**
  (`unsupported`/`too_big`; видно в панели «Файлы проекта»).
Удалённый оригинал → образ удаляется, если агент его не менял, иначе `orphan`.
Переименованный или перемещённый оригинал → переименование образа.
**Изменённый оригинал, у которого есть непринятый вариант** (`pending_accept`), образ
**не перезаписывает**: статус → `conflict` (TR-7.6, случай 2).

**Снимок основания.** Когда демон впервые видит изменение образа агентом, он копирует
текущий оригинал в `.hds-agent\base\<отн. путь>`, если sha256 оригинала ещё равен
основанию. Этот снимок нужен для восстановления метаданных и картинок (TR-7.5) и для
трёхстороннего «Сравнить» при конфликте. Снимок удаляется вместе с вариантом.

**TR-7.3a. Просьба изменить `pdf`, `pptx` или `mpp`** (утверждено владельцем
17.11.2026, D22). Общий принцип: **оригинал такого файла агент не меняет, а
правки оформляет новым документом рядом с ним**. Новые файлы агента сами появляются в
папке проекта (TR-7.5), так что пользователь получает результат без лишних действий.

| Формат | Почему не править «на месте» | Что делает агент (MVP) | Фаза 2 |
|---|---|---|---|
| `pdf` | в проекте это почти всегда **выходной** документ: выгрузка из Word, подписанное ТЗ, акт. Правка PDF ломает вёрстку и юридический смысл | 1) ищет в папке проекта **исходник** (docx с тем же или похожим именем) и, если он есть, предлагает править его; 2) иначе создаёт **лист замечаний** `<имя> — замечания.docx` (таблица: раздел/страница, было, предлагается, обоснование) или новую редакцию документа в docx | — (править PDF не планируется) |
| `pptx` | в MVP образ PPTX текстовый: собрать из него анонимную презентацию с сохранением оформления нельзя | создаёт **лист правок** `<имя> — правки.docx` (слайд, элемент, было, стало); новую презентацию с нуля — `office_create(kind: pptx)` по шаблону без оформления оригинала | настоящий образ PPTX (замена текста в объектах через `python-pptx`, как в docx) и `office_edit` для слайдов — правка на месте с «Принять» |
| `mpp` | двоичный формат; `mpxj` его читает, но записывать не умеет | создаёт **таблицу изменений плана** `<имя> — изменения плана.xlsx` (ID задачи, название, поле, было, стало, причина), которую РП переносит в MS Project | образ в формате **MS Project XML** (`mpxj` конвертирует mpp → MSPDI xml; формат `xml` анонимизатор уже поддерживает с обратным преобразованием). Агент правит XML, результат открывается в MS Project и сохраняется как mpp |

Как это работает технически:
1. Текстовые образы `*.pdf.md`, `*.pptx.md`, `*.mpp.md` защищены от записи: хук
   `hds-guard` блокирует `editor`/`apply_patch`/`office_edit` по ним и возвращает модели
   объяснение — «текстовый образ PDF только для чтения; ищи исходник docx или создай
   лист замечаний `<имя> — замечания.docx`». Модель видит причину и меняет план
   действий: так работает отказ инструмента в SDK.
2. То же сказано в правилах агента (TR-3.8), поэтому обычно до блокировки дело не
   доходит.
3. В ленте пользователь видит, какой файл создан и почему не изменён оригинал.

**TR-7.4. Режим `mode: "agent"`** в файловых актах: метки проекта с суффиксами;
исправление «слипшихся» ФИО — **только в образе**, оригинал демон не меняет никогда;
картинки в теле документа по умолчанию вырезаются (`agent.images: strip`, вместо
картинки — метка `[IMAGE_n]`); метаданные — `scrub_metadata`; маркер
`hds-agent/<P>/<artifact_id>`.

**TR-7.5. Обратный путь (анонимная зона → пользователь).**
* **Новый файл агента** (`agent_new`) → деанонимизация (имя и содержимое) → файл
  появляется **на соответствующем месте в папке проекта** (решение D5 — автоматически).
  Если там уже есть файл с таким именем, добавляется суффикс `(агент)`. Реестр
  запоминает пару, поэтому демон не делает обратного образа этого файла (TR-7.7).
* **Изменённый образ существующего документа** (`agent_changed`) → деанонимизация
  с восстановлением из основания: `docProps` и вырезанные картинки (по сохранившимся
  `[IMAGE_n]`) берутся из снимка `.hds-agent\base\` (TR-7.3). Результат кладётся в `<папка проекта>\.hds-agent\pending\<отн.
  путь>`, статус `pending_accept`; оригинал **не трогается**.
* **Удалённый агентом образ** → оригинал не удаляется; в панели «Файлы» —
  предложение «удалить оригинал?».

**TR-7.6. Решение пользователя по варианту изменённого документа.**

*Термины.* **Основание** — версия оригинала, из которой демон сделал образ, который
изменил агент; в реестре хранится её sha256. **Вариант** — деанонимизированный
изменённый образ в `.hds-agent\pending\`. Если агент правит тот же документ несколько
раз, вариант перезаписывается: в `pending` всегда лежит **последний** вариант, основание
остаётся прежним.

В панели «Результаты» у варианта четыре кнопки: «Сравнить», «Принять», «Отклонить» и
«Поручить агенту» (последняя — только при конфликте). Возможны четыре ситуации:

| # | Ситуация | Что видит пользователь | Что делает hds | Итог |
|---|---|---|---|---|
| 1 | **«Принять», оригинал не менялся** с момента создания образа (sha256 оригинала = основание) | вариант с отчётом валидатора (TR-7.8) | 1) копирует оригинал в `.hds-agent\backup\<дата-время>\<отн. путь>`; 2) атомарно заменяет оригинал вариантом; 3) статус `accepted`; 4) пересоздаёт образ из нового оригинала: в workspace теперь «официальная» версия, а не правка агента; 5) удаляет вариант из `pending` | оригинал = вариант агента; прежняя версия — в backup (восстановление — кнопкой «Вернуть» в журнале результатов) |
| 2 | **Конфликт: оригинал изменился**, пока агент работал (пользователь сам правил документ или коллега прислал новую версию) | метка «конфликт», обе версии, «Сравнить» | автоматически — **ничего**: оригинал не трогается, образ агента не перезаписывается. Пользователь выбирает: **«Оставить вариант агента»** (то же, что случай 1, но правки, внесённые в оригинал после основания, будут потеряны — hds предупреждает; копия в backup); **«Взять новую версию»** (как случай 4); **«Поручить агенту»** — образ пересоздаётся из нового оригинала, анонимная копия прежнего варианта кладётся рядом как `_conflicts\<имя> (вариант агента).docx`, агенту уходит сообщение «документ обновлён; перенеси свои правки из `_conflicts\…` в новую версию» → новый вариант с новым основанием | пользователь сам решает, чьи правки важнее; молча ничего не теряется |
| 3 | **«Принять», но оригинал открыт** в Word/Excel (Windows не даёт заменить файл) | сообщение «файл занят: закройте его и повторите» | ничего не меняет: backup не создаётся, вариант остаётся в `pending` | после закрытия файла — снова «Принять» |
| 4 | **«Отклонить»** | — | 1) удаляет вариант из `pending`; 2) возвращает образ в workspace к состоянию оригинала (пересоздаёт его), иначе агент продолжал бы работать со своей отвергнутой правкой; 3) отправляет агенту служебное сообщение «изменения документа `<имя>` отклонены пользователем; образ восстановлен» | оригинал не менялся; агент знает, что правка не принята |

**«Сравнить»** (во всех случаях): для docx — запуск встроенного сравнения Word (оригинал
↔ вариант; при конфликте — основание ↔ оригинал ↔ вариант), для xlsx — список
изменённых ячеек в UI, для md/txt — текстовый diff в UI.

**TR-7.7. Петли.** Демон не реагирует на собственную запись: в реестре есть
`anon_sha256_issued`, изменение = `seen != issued`, а для файлов, выпущенных в папку
проекта, хранится `orig_sha256` выпуска. Принятый вариант порождает новый образ, но не
новый «результат».

**TR-7.8. Валидатор результата** (отчёт к каждому выпуску, не блокирует): метки,
которых нет в проекте (агент выдумал или исказил); метки с несогласованным падежом;
непомещённые `[IMAGE_n]`; доля текста оригинала, пропавшая в варианте («документ
пересобран с нуля»). Такие результаты UI помечает «проверить».

**TR-7.9. Ответ на вопрос редакции 1 об «Inbox»:** отдельной папки «Входящие» **нет**.
Новые файлы агента сразу появляются в папке проекта на своём месте; в служебную
`.hds-agent\pending\` попадают только **варианты изменённых документов**: их нельзя
положить на место оригинала до «Принять», а копия рядом с оригиналом снова
зеркалилась бы в анонимную зону.

**Методика оценки RAG «с RAG / без RAG»** (D23). Выполняется в две ступени, потому что
агента до фазы A3 нет:
* **A0(10) — поиск сам по себе.** Стенд и эталон (ниже) готовятся в A0. Образы для
  стенда делаются прототипно: текущей анонимизацией (`hds anon`) во временный
  каталог в `tools/parity/out/`, индексация — отдельной базой (`db_path` во временном
  конфиге, боевой `index.db` не трогается). Метрики — `recall@k` и MRR по эталонным
  источникам через `hds search --json`. Цель — убедиться, что поиск по анонимным
  образам (метки вместо имён) находит нужные фрагменты.
* **Контрольная точка K1 — после A3, до A5.** На готовом агенте — сравнение
  конфигураций (А) и (Б) по правилу решения ниже. По итогам K1 фиксируется значение
  `agent.mcp.disk_search.enabled` по умолчанию.

* **Стенд:** вымышленный проект внедрения 1С на 30–50 документов (устав, ТЗ в pdf,
  реестр требований xlsx, протоколы docx, план-график mpp, письма) — тот же набор,
  что для приёмки §7.
* **Вопросы:** 15–20 типовых вопросов аналитика и РП с эталонным ответом и списком
  файлов-источников, составленных вручную: поиск факта («какой срок сдачи этапа 2?»),
  поиск по смыслу («где обсуждали интеграцию с банком?»), сверка («какие требования
  реестра не отражены в ТЗ?»), противоречия между документами, вопросы по метке
  («что поручено [PERSON_3]?»).
* **Конфигурации (K1):** (А) агент с `search_local_files` и правилом TR-3.8a; (Б) агент без
  `disk-search`, только `search_codebase` и чтение файлов. Одна облачная модель, по
  2 прогона на вопрос.
* **Метрики:** полнота ответа против эталона (найдены ли все источники, оценка
  0/1/2), точность (нет выдуманного), входные и выходные токены и стоимость за
  вопрос, число шагов агента, время до ответа.
* **Инструменты:** скрипт `tools/parity/agent_rag_eval.py` (сценарии через
  протокол `hds_agent` на тестовом проекте; токены — из `getAccumulatedUsage` SDK)
  и для отдельной оценки самого поиска — `recall@k`/MRR по эталонным источникам через
  `hds search --json` (идеи и формат golden-набора — как в `tools/eval_retrieval.py`).
  Результаты — в `tools/parity/out/` (данные вымышленные, но в репозиторий не идут).
* **Правило решения (K1):** RAG оставляем включённым, если (А) не хуже (Б) по полноте и
  экономит ≥ 25 % токенов на вопрос **или** заметно выигрывает по полноте на
  вопросах «поиск по смыслу». Иначе `agent.mcp.disk_search.enabled: false` по
  умолчанию (D23). Решение фиксируется вместе с владельцем в отчёте
  `tools/parity/AGENT_RAG_K1.md`; трудоёмкость K1 — 1–2 дня, входит в оценку A3.

**Итого:** ~32–42 рабочих дня (с K1). Критический путь: A0 → A1 → A3 → A5; A2 и A4 идут
параллельно с A3 после A1.

## 7. Приёмка MVP

1. Автотесты инвариантов I1–I8 зелёные.
2. **Живой сценарий** на вымышленном проекте внедрения 1С:ERP. Папка проекта: устав
   (docx), реестр требований (xlsx), ТЗ (pdf), план-график (mpp), протоколы (docx) с
   ФИО в разных падежах, организациями, ИНН, телефонами, логотипом и автором в
   свойствах. Шаги:
   * создать проект → образы появились, структура папок повторена, имена — с метками;
   * реплика «Сверь реестр требований с ТЗ, найди требования без покрытия в типовой
     1С:ERP, подготовь письмо Иванову с вопросами» → в предпросмотре — метки, в т.ч.
     `[PERSON_1|дат]`, а «1С:ERP» не скрыт (D19);
   * агент читает образы, ищет по проекту через `disk-search`, уточняет
     функциональность через `1c-buddy`, ищет в интернете через `tavily`, дописывает
     столбец в реестр (`office_edit`) и создаёт письмо (`office_create`);
   * в ленте видны рассуждения, вызовы инструментов и MCP с **настоящими** значениями;
   * письмо появилось в папке проекта («Иванову» в правильном падеже или с пометкой
     «проверить»); вариант реестра — в `pending`, с метаданными и логотипом
     оригинала; «Принять» заменяет оригинал, копия — в `backup`.
3. Журнал исходящего (`egress_log: true`) за сценарий не содержит ни одной формы
   значений fixtures; `<agent.root>` — тоже (I1, I2).
4. Файлы `%USERPROFILE%\.cline\` и настройки расширения Cline в VS Code после сценария
   не изменились; программирующий Cline работает как прежде (I4).
