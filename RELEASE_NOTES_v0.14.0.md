# RELEASE_NOTES v0.14.0 — MCP: инструкции сервера, лимит вывода и правило для Cline

## Новое

### MCP-сервер отдаёт «системный промпт» (`instructions` в `initialize`)

Спека MCP разрешает серверу вернуть инструкции при `initialize` — клиент может подмешать
их в системный промпт модели. У disk-search такого поля не было вовсе: модель видела
только описания отдельных инструментов, и на «найди технические задания» делала ОДИН
запрос, получала первые 8 фрагментов и объявляла их полным списком. Теперь сервер
объясняет: одна выдача — это фрагменты, а не список файлов; на обзорные вопросы нужно
несколько запросов разными формулировками (рус/англ/транслит) и объединение результатов;
обход диска терминалом (`dir /s`, `find`) не заменяет индекс.

Важно: **Cline 0.0.43 поле `instructions` игнорирует** (в репозитории Cline это открытый
feature request о конформности спеке). Для Cline та же суть продублирована
`install_cline.ps1` / `installers/install_cline_macos.sh`:

| Что | Куда ставится | Когда доходит до модели |
|---|---|---|
| Правило `cline-rules/disk-search.md` | `~/.cline/rules/disk-search.md` | **всегда** — правила инжектятся в системный промпт каждой сессии |
| Скилл `hermes-skill/disk-search.md` | `~/.cline/skills/disk-search/SKILL.md` | лениво — только после вызова `use_skill` |

Именно правило решает исходную проблему: локальная агентная модель скилл сама не
активирует, а правила видит всегда.

### `hds cline-sync`: синхронизация настроек Cline (UI, CLI и инсталляторы)

Настройки агента лежат ВНЕ проекта (`~/.cline/...`) и легко рассинхронизируются с
`config.yaml`. Один и тот же код (`hds_core::cline::sync`) теперь применяют:

* кнопка **«Синхронизировать настройки Cline»** в веб-интерфейсе (`POST /api/cline/sync`);
* команда `hds cline-sync [--json] [--dry-run]`;
* инсталляторы релиза: Windows — `setup.ps1` → `install_cline.ps1`; macOS —
  `installers/install_macos.command` → `installers/install_cline_macos.sh`.

Что синхронизируется:

1. **окна контекста моделей** в `~/.cline/data/settings/models.json`: `contextWindow` и
   `maxInputTokens` моделей нашего провайдера (`baseUrl` = `chat.base_url`) приравниваются
   реальному слоту `llm-host` (`llm_server.<role>.ctx_per_slot`, иначе `llm.<role>.n_ctx`).
   Алиасы разводятся по ролям: `chat`/`chat-think` → чат, `embedding*`, `rerank*`.
   Раньше там стояло 16384 при слоте 65536 — Cline сжимал историю раньше заполнения
   слота, и агент терял контекст поиска;
2. **MCP-сервер** disk-search в `data/settings/cline_mcp_settings.json` и `mcp.json`
   (URL из `mcp_http.*`, `autoApprove` на 6 инструментов, `timeout: 300`); чужие MCP-серверы
   (например, tavily) сохраняются;
3. **правило** `cline-rules/disk-search.md` → `~/.cline/rules/disk-search.md` и
   **скилл** `hermes-skill/disk-search.md` → `~/.cline/skills/disk-search/SKILL.md`.

Отчёт (список шагов `[ok]`/`[--]`/`[!!]`, `--json` для скриптов, `--dry-run` — только показать)
явно **предупреждает о необходимости перезапустить Cline**, когда менялись `models.json` или
настройки MCP. Python-хелпер `installers/cline_mcp_merge.py` оставлен только для совместимости
(помечен устаревшим), инсталляторы его больше не вызывают. В релизный стейджинг добавлен каталог
`cline-rules` (без него инсталлятор не нашёл бы источник правила).

### `ask_my_files`: параметр `limit` (глубина выборки)

Раньше глубина была жёстко 8 фрагментов — обзорные вопросы («какие есть ТЗ/проекты»)
получали заведомо неполную картину. Теперь `limit` — параметр инструмента (1–30,
по умолчанию 8). `search_local_files` при упоре в `limit` добавляет в результат явную
подсказку, что выдача не полная.

## Исправления

### Терпимый разбор `<tool_call>`: агент больше не «теряет» вызовы инструментов

Симптом (03.10.2026): в чате Cline на вопрос «найди на этом компе технические задания»
модель выдала вызовы как ТЕКСТ —
`<tool_call>{"name": disk-search__ask_my_files", "arguments": {...}}</tool_call>` — и чат
завершился без ответа. В логе сессии видно причину: у значения `name` потеряна
открывающая кавычка, то есть JSON невалиден.

Фасад `hds-llama` разбирал блок тела строгим `serde_json::from_str`, при ошибке оставлял
блок ТЕКСТОМ и отдавал обычный текстовый ответ — `tool_calls` до клиента не доходили, и
агент молча заканчивал ход. Теперь `parse_tool_calls` терпим к типовым сбоям локальных
моделей:

* «голое» строковое значение (`"name": foo"` → `"name": "foo"`) — починка затрагивает
  только `:` **вне** строк, поэтому текст аргументов (`"какие есть ТЗ: требования"`)
  не портится;
* висячие запятые перед `}`/`]`;
* отсутствие закрывающего `</tool_call>` (блок читается до следующего `<tool_call>`
  или до конца ответа);
* аргументы строкой и обёртка `{"function": {...}}` (форма OpenAI);
* плейсхолдеры шаблона (`<function-name>`, `<args-json-object>`) распознаются как «не
  вызов» — такой блок сохраняется текстом, а не превращается в мусорный tool_call.

Проверки: новый тест `tool_calls_survive_broken_json` (боевой случай с потерянной
кавычкой, отсутствующий закрывающий тег, аргументы строкой, плейсхолдеры); живой прогон
`chat` и `chat-think` на `:8010` с `tools` → `finish_reason=tool_calls`, вызов разобран.

### Ответы агента больше не обрываются на полуслове

Потолок вывода роли `chat` — `chat.max_tokens` — был 600 токенов. У агента (Cline,
модель `chat-think`) в этот потолок входят И размышления, поэтому ответ обрывался
посреди списка (в логе сессии — «4. **Т» и `outputTokens: 600`).

- `chat.max_tokens` по умолчанию — **2048** (дефолт llm-host для клиентов, которые не
  присылают свой `max_tokens`);
- ответ `ask_my_files` получил **отдельный** бюджет `chat.rag_max_tokens` (**600**):
  его ждёт MCP-клиент с таймаутом 300 с, а генерация на локальной модели идёт ~15–20 ток/с.

## Требования к обновлению

- Переиндексация не требуется (схема БД не менялась).
- Изменения MCP-сервера применяются после перезапуска общего инстанса:
  `hds mcp-http restart` (инсталляторы делают это сами).
- `chat.max_tokens` / `chat.rag_max_tokens` читаются llm-host при старте: перезапустите
  резидент — `bin\llm_host.exe stop` (задача Планировщика поднимет его заново) либо
  `bin\llm_host.exe run`.
- Правило и скилл Cline ставятся повторным запуском `install_cline.ps1`
  (на macOS — `installers/install_cline_macos.sh`); новая сессия Cline подхватит правило.
- Ключи необязательны: без `chat.max_tokens` поведение прежнее (600), без
  `chat.rag_max_tokens` RAG-ответ использует `chat.max_tokens`.

## Рекомендация (не обязательно, но заметно улучшает выдачу)

- **Согласуйте окно контекста Cline с сервером.** В `~/.cline/data/settings/models.json` у
  моделей провайдера `openai-compatible` стоит `contextWindow: 16384`, тогда как слот чата
  поднят с `llm_server.chat.ctx_per_slot: 65536`. Cline сжимает историю раньше времени, и
  агент теряет контекст поиска — приведите `contextWindow`/`maxInputTokens` к реальному
  значению слота.
- Для обзорных вопросов в Cline предпочтителен алиас без размышлений (`chat`): у
  `chat-think` размышления входят в тот же потолок `chat.max_tokens`.
- Провайдер `openai-compatible` в Cline имеет `timeout: 120000`: при `chat.max_tokens: 2048`
  и ~15–20 ток/с один длинный ответ может приблизиться к минуте-двум — при таймаутах
  поднимите его (в настройках MCP-сервера `timeout: 300` уже стоит для `ask_my_files`).
