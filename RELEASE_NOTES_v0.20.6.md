# RELEASE_NOTES v0.20.6 — наполнение базы на серверном стенде и единый генератор серверных настроек

> PATCH: схема базы, формат настроек и поиск **не менялись**, переиндексация не требуется.
> Исправлены два дефекта, найденные при разборе «на серверном стенде стоит наполнение базы»:
> **(1)** Python-воркер извлечения на серверной установке не находил файл настроек и падал на первом
> же файле — дальше **каждый** файл получал ошибку «Идёт закрытие канала» (на стенде 43 537 записей
> `error` за один прогон); **(2)** серверный конфиг собирали два разошедшихся генератора, и в нём не
> было списка служебных каталогов `index.exclude_dirs` — в базу попадали файлы из корзины
> (`D:\$RECYCLE.BIN`) и `System Volume Information`.

## Что нового и что исправлено

### Наполнение базы на серверной установке работает

* **Причина.** Служебная программа чтения документов (Python-воркер `sidecar/hds_extract/worker.py`)
  искала настройки **только** в папке установки (`app\<версия>\config.yaml`), а на серверном стенде
  файла там нет: настройки лежат в служебной папке сервера (`%ProgramData%\hermes-disk-search`,
  на Mac — `/Library/Application Support/hermes-disk-search`), и путь к ним закреплён за службами
  переменной `HDS_CONFIG`. Первый же запрос на чтение файла падал с `FileNotFoundError`, процесс
  завершался, и **все последующие** файлы получали «воркер: запись: Идёт закрытие канала
  (os error 232)». В базе это выглядит как 43 537 записей `error` за один прогон и замерший
  признак «последнее наполнение».
* **Что сделано.** Воркер ищет настройки тем же порядком, что и ядро: `HDS_CONFIG` → файл в папке
  установки → служебная папка сервера. Одна неожиданная ошибка больше не убивает процесс — она
  возвращается как ошибка файла, а чтение продолжается.
* **Защита от повтора.** Клиент (`hds-extract`) теперь поднимает упавший или убитый воркер заново и
  **повторяет** запрос один раз: раньше один сбой отравлял весь прогон (закрытый канал навсегда).
  Таймаут по-прежнему даёт ошибку только этому файлу — повтор удвоил бы ожидание.

### Серверные настройки собираются одним генератором из шаблона

* **Один вход — шаблон `server_config.example.yaml`** (лежит в папке установки рядом с
  `config.example.yaml`). В нём с пояснениями все серверные значения, включая список служебных
  каталогов `index.exclude_dirs` (корзина `$RECYCLE.BIN`, `System Volume Information`, `Windows.old`,
  `WindowsApps`, `node_modules`, `.git` и т. д. — тот же набор, что в одиночном шаблоне).
* **Новая подкоманда `hds config init`** — единственное место, где строится серверный файл настроек
  (раньше это делали по-своему Windows- и macOS-установщик, и они разошлись):
  ```powershell
  hds config init --path "%ProgramData%\hermes-disk-search\config.yaml" --merge-defaults
  hds config init --path <файл> --print            # только показать, ничего не меняя
  ```
  * существующий файл **не перезаписывается**; `--merge-defaults` дописывает только недостающие
    значения по умолчанию (пояснения и ваши правки остаются);
  * `--print` — режим предпросмотра (его использует `install-server.cmd -WhatIf`);
  * `--force` — переписать файл целиком из шаблона;
  * результат **проверяется как YAML до записи**: испорченный шаблон или значение останавливают
    установку, а не оставляют полурабочий файл.
* **Оба установщика больше не пишут YAML сами:** `install_server.ps1` и `install_server.command`
  только передают значения в генератор. Поэтому `-WhatIf`/`--whatif` показывает ровно то, что будет
  записано.
* **Уже работающие стенды** получают `index.exclude_dirs` при повторном запуске установщика
  (`install-server.cmd`) — либо вручную командой `hds config init … --merge-defaults`.

## Требования к обновлению

* Обновление обычное: `update.cmd` от администратора на Windows, `sudo bash installers/update.command`
  на macOS. Версия меняется по `version.txt` и в ответе `/health` — `0.20.6`.
* **Переиндексация не требуется**, но файлы, записанные прошлым прогоном как `error`, не считаются
  обработанными: после обновления служба слежения пересмотрит их сама при старте (сверка с дисками).
* **Уже работающий стенд** получает список служебных каталогов так: повторный запуск
  `install-server.cmd` (он ничего не перезаписывает, только дописывает недостающее) либо вручную
  `hds config init --path <файл настроек> --merge-defaults`. Чтобы файлы корзины,
  попавшие в базу раньше, ушли из индекса, после этого нужен обычный проход
  `hds index` (или `hds index --full`, если нужно пересмотреть всё заново).
* Если в папке установки остался посторонний `config.yaml` — поведение не изменилось: установщик
  по-прежнему отводит его в сторону (`config.desktop.yaml.bak`), службы читают служебный файл.
* Настройки, схема базы и формат поиска не менялись: старые конфиги и базы подходят без правок.

## Проверено перед выпуском

* **Воспроизведение дефекта (1)** на макете серверной раскладки: до исправления воркер падал на
  первом `extract` (`FileNotFoundError: …\app\<версия>\config.yaml`), после — отвечает на все запросы
  при трёх вариантах настроек (`HDS_CONFIG`, без него — поиск в служебной папке, испорченный путь —
  ошибка файла без смерти процесса).
* **Сквозной прогон конвейера** на раскладке «корень без файла настроек + `HDS_CONFIG`»:
  `hds index --limit 3` → `{'indexed': 3}`, ошибок 0; в возможностях воркера появился `ocr`.
* **Установщик Windows:** `install_server.ps1 -WhatIf` печатает валидный YAML (20 исключений, папки,
  видеокарта, доступ, адреса); прогон без ролей на копии боевого конфига — «config exists (not
  overwritten)» + «index.exclude_dirs: 20 names (added)», diff ровно одна строка.
* **Установщик macOS:** `bash -n` чистый; `--whatif` печатает валидный YAML; полный прогон в Git Bash
  на копии боевого конфига — тот же diff в одну строку, `ocr_*` и `roots` сохранены.
* **Тесты:** `cargo test -p hds-cli` (включая новый `config_init.rs` — 9 тестов и переписанный
  `install_server_parity.rs`), `cargo test -p hds-extract -p hds-mcp` (включая
  `worker_autorestart.rs` — падение воркера на первом запросе с автоматическим перезапуском),
  `cargo fmt --check`, `cargo clippy --all-targets -D warnings` — зелёные.
* **Не проверено:** живые службы после переустановки стенда (владелец делает отдельно) и сборка для
  macOS (best-effort, как и раньше).
