## 1. Цель

Повысить качество результатов индексации (релевантность и полноту выдачи по
локальным файлам, в первую очередь русскоязычным), оставаясь в рамках «всё
локально, без облака» и без требования мощного GPU.

**Критерий успеха**: измеримый рост recall@5 / recall@10 / MRR на собственном
eval-наборе (Фаза 0) — отдельно по ветвям поиска (FTS / векторная / гибрид) и по
типам файлов (текст, docx, pdf, транскрипты).

6. **Управление** — `hds/cli.py` (`index`, `search`, `ask`, `status`, `watch`,

## 3. Диагностика: слабые места (с привязкой к коду)

1. **FTS5 не знает русской морфологии.** `chunks_fts` создана с `unicode61`
   (`hds/db.py`); Porter-стемминг в SQLite только для английского; `fts_query`
   (`hds/search.py`) делает `OR` из сырых токенов. «настройки» не находит
   «настройка», «скрипта» — «скрипты»: ключевая ветка гибрида для русского
   работает вполсилы.
2. **Чанкинг произвольный.** Границы — по ближайшему `\n` внутри окна (часто
   посреди предложения/абзаца); overlap — «хвост 200 символов», дублирующий текст
   и в FTS, и в векторах (`hds/chunker.py`).
3. **Нет учёта структуры.** Заголовки markdown/DOCX не попадают в текст чанка; для
   PDF чанк может склеиваться из нескольких страниц, а `page` берётся от первого
   сегмента — ссылка на страницу часто неверна (`hds/chunker.py`,
   `hds/extractors.py`).
4. **Слияние RRF без настройки.** Равные веса FTS и векторов, нет префиксного
   матчинга, нет AND→OR fallback, сниппет может резать предложение (`hds/search.py`).
5. **bge-m3 используется только в dense-режиме.** sparse (learned lexical weights)
   и ColBERT недоступны через LM Studio (`/embeddings` — только dense; `/rerank`
   в LM Studio не реализован, открытые issue lmstudio-ai#162, lms#521).
6. **Нет реранкера.** top-N после RRF отдаётся как есть, хотя cross-encoder —
   самый стабильный источник прироста точности.

Инструменты (в репозитории, `tools/`): `diag_a1_tokens.py` (токены в чанках),

(первый прогон `a3b` скачивает `BAAI/bge-m3` ~2,3 ГБ в кэш HF).

**Результаты:**

- **A1 (токены):** см. таблицу в §2 — медиана 484 токена, p90 829, max 2114;
  44.8 % чанков длиннее 512 токенов.
- **A2 (усечение):** при загруженном контексте 8192 текст в 15 644 токена дал
  вектор, **равный вектору первых ~8192 токенов** (косинус 1.000000 начиная с
  24 000 символов), ответ — HTTP 200 без ошибки: LM Studio **молча усекает** вход.
  Сырой `llama-server --ctx-size 512` на то же отвечает явной ошибкой
  `400 exceed_context_size_error` («input (1115 tokens) is larger than the max
  context size (512 tokens). skipping»).
- **A3 (слой сервинга):** LM Studio vs сырой llama.cpp с тем же GGUF:
  `--pooling cls` → косинус min 0.9987 / mean 0.9996; `--pooling mean` → 0.53–0.66
  ⇒ LM Studio применяет **правильный для bge-m3 CLS-пулинг**.
- **A3b (эталон):** PyTorch bge-m3 (fp32, CLS + L2) vs LM Studio GGUF Q8_0 на
  6 реальных чанках → косинус min 0.99890 / mean 0.99904 ⇒ **квантизация и
  GGUF-конвертация векторы не искажают**.

**Вывод:** смена инструмента ради «качества векторов» не нужна — на этой машине
векторы совпадают с эталоном. Единственный подтверждённый риск — **тихое усечение**
при загруженном контексте меньше целевого.

## 5. План работ по фазам

Общие правила: каждая фаза — отдельный коммит; перед коммитом
`python -m unittest discover -s tests`; измеримые эффекты подтверждаем на
eval-наборе Фазы 0 («до/после»), релиз — по `releasing.md` отдельным PATCH/MINOR.

### Фаза 0 — измерительная инфраструктура (делать первой)

- **Что**: `tools/eval_retrieval.py` — генерация golden-set и замер качества.
  - набор: 50+ вопросов, сгенерированных локальной чат-моделью по случайным чанкам
    (чанк = ground truth); сохранять в `eval/golden.jsonl` (**в репозиторий не
    коммитить**: персональные пути/содержимое; добавить в `.gitignore`);
  - метрики: recall@5, recall@10, MRR — **раздельно** для веток «только FTS»,
    «только вектор», «гибрид RRF», плюс медиана времени ответа;
  - baseline сохранять в `eval/baseline.json` для сравнения после каждой фазы.
- **Файлы**: `tools/eval_retrieval.py` (новый), `.gitignore`.
- **Стоимость**: генерация набора — один прогон LLM по 50 чанкам (~5–15 мин),
  замеры — секунды (читает существующую БД).
- **Приёмка**: скрипт печатает таблицу «ветка × метрика» и сохраняет baseline.

### Фаза 1 — русская морфология в FTS (наибольший ожидаемый эффект)

- **Что**: в `chunks_fts` писать **лемматизированный** текст (отображаемый текст
  остаётся в `chunks.text`), а запрос лемматизировать тем же способом.
  - `hds/lemmatizer.py` (новый): лемматизация RU/EN через `pymorphy3`; при
    отсутствии зависимости — graceful fallback (стеммер/без нормализации) и явное
    предупреждение в `check`;
  - `hds/db.py::add_chunk` — писать нормализованный текст в `chunks_fts`;
  - `hds/search.py::fts_query` — лемматизировать токены запроса;
  - `hds/cli.py` — новая команда **`reindex-fts`**: перестройка только FTS из
    `chunks.text` (без эмбеддингов, без OCR/транскрипции), прогресс через
    `hds/progress.py`;
  - `requirements.txt`: `pymorphy3`, `pymorphy3-dicts-ru`; `setup.ps1` /
    `install_macos.command` — ставятся как обычные зависимости.
- **Стоимость**: только CPU; ~553 тыс. чанков → ориентировочно 30–90 мин.
  Переэмбеддинг НЕ требуется.
- **Приёмка**: рост recall@10/MRR на eval-наборе против baseline; тесты на
  лемматизацию и на `fts_query` (разные словоформы находят друг друга).

### Фаза 2 — структурный чанкер + контроль бюджета токенов

- **Что**:
  - `hds/chunker.py`: рекурсивное разбиение «абзац → предложение → слово»; цель
    `chunk.size` ≈ 700–800 символов (сейчас медиана 1369 — вдвое больше нужного для
    точечных запросов); `chunk.overlap` — по **целым предложениям** (10–20 %)
    вместо «хвоста 200 символов»;
  - `hds/extractors.py`: для md/docx — «путь заголовков» (например
    `# Раздел / ## Подраздел`) в начало чанка; для PDF — чанк в пределах страницы,
    `page` — фактическая страница каждой части (сейчас берётся от первого сегмента);
  - `hds/indexer.py`: явный контроль бюджета токенов (не длиннее
    `EMB_CONTEXT - запас`) — резать/логировать, а не надеяться на сервер
    (обоснование — §4, A2);
  - `hds/cli.py`: режим **`index --rechunk`** — перечанковать без OCR и
    транскрипции (текст/офис), чтобы не гонять Whisper/OCR по 67 тыс. файлов.
- **Стоимость**: полный переэмбеддинг затронутых файлов (553 тыс. чанков → часы);
  планировать ночной прогон; тест на маленькой папке перед общим.
- **Приёмка**: доля чанков > 512 токенов → ≈0; метрики на eval-наборе не хуже, чем
  до фазы; тесты: границы по предложениям, точные номера страниц PDF, заголовки md.

### Фаза 3 — слияние веток и обработка запроса

- **Что** (`hds/search.py`): веса `search.fts_weight` / `search.vec_weight` (вместо
  жёсткого RRF с равными весами); префиксный матчинг последнего токена
  (`токен*`); режим «сначала AND, при пустом результате OR»; сниппет не режет
  предложение. Новые ключи — в `config.yaml`, в белый список `_CONFIG_FIELDS`
  (`hds/ui_server.py`) и в UI-группу «Параметры обработки» (`assets/ui.html`).
- **Стоимость**: правки + подбор весов на eval-наборе (минуты).
- **Приёмка**: лучшие веса зафиксированы в конфиге; на eval-наборе гибрид не хуже
  отдельных ветвей; тесты на префикс/AND-fallback/сниппет.

### Фаза 4 — качество RAG-ответов (`ask_my_files`)

- **Что**: реранкер и/или HyDE — включаются флагами, по умолчанию выключены.
  - **Реранкер**: `bge-reranker-v2-m3` (GGUF Q8_0, ~600 МБ) в отдельном процессе
    `llama-server --reranking --pooling rank` (LM Studio `/rerank` не умеет);
    новый `hds/rerank.py` (клиент `/v1/rerank`), в `hds/rag.py` — реранк top-20 →
    top-8 перед генерацией; конфиг `rerank.enabled`, `rerank.url`, `rerank.model`,
    `rerank.timeout`; авто-отключение, если латентность превышает лимит (слабый CPU).
  - **HyDE** (альтернатива/дополнение): перед поиском локальная LLM генерирует
    «гипотетический ответ», его вектор используется для векторной ветки; конфиг
    `search.hyde: false|true`. Дешевле реранкера по железу, дороже по времени ответа.
- **Файлы**: `hds/rerank.py` (новый), `hds/rag.py`, `hds/search.py`,
  `hds/ui_server.py` + `assets/ui.html` (кнопка/статус), `config.yaml`,
  `installers/` (скачивание GGUF реранкера), README, тесты.
- **Стоимость**: реранк 20 фрагментов на CPU — единицы секунд; приемлемо только для
  `ask_my_files` (не для интерактивного `search`).
- **Приёмка**: на eval-наборе растёт точность попадания нужного фрагмента в контекст
  (recall@8 в промпте); тесты — клиент реранка на моках, деградация при недоступности.

### Фаза 5 — опционально, позже

- Полный bge-m3 (sparse + ColBERT) через ONNX Runtime/DirectML (AMD iGPU) или
  FlagEmbedding — только если после Фаз 1–4 качества всё ещё не хватает.
- Отдельная trigram-таблица FTS для артикулов/кодов (подстрочный поиск).
- Contextual Retrieval: LLM-префикс контекста на каждый чанк при индексации
  (дорого по времени на слабом железе — только флагами и выборочно по корням).

## 6. Порядок работ и оценки

1. **Фаза 0** — eval-набор и baseline (полдня, без риска).
2. **Фаза 1** — морфология FTS + `reindex-fts` (1–2 дня; CPU-прогон 30–90 мин).
3. **Фаза 3** — веса слияния и запрос (0.5–1 день; подбор на eval).
4. **Фаза 2** — структурный чанкер + `index --rechunk` (1–2 дня + ночной
   переэмбеддинг).
5. **Фаза 4** — реранкер/HyDE (1–2 дня, флаги).
6. **Фаза 5** — по результатам замеров.

После Фаз 1 и 2 — релизы по `releasing.md` (PATCH/MINOR) с заметками и указанием
необходимых действий пользователя (`reindex-fts` / `index --rechunk`).

## 7. Риски, ограничения, откат

- **Дорогая переиндексация** — 553 тыс. чанков: полный `index --full` с OCR и
  Whisper нереалистичен; поэтому в Фазе 2 обязателен режим `--rechunk` без OCR/AV.
- **Размер индекса** — лемматизированный текст в FTS увеличивает БД (сейчас
  4676 МБ); следить за диском.
- **`pymorphy3` — новая зависимость** (чистый Python, словари ~10 МБ); при
  отсутствии — деградация без падения (fallback), предупреждение в `check`.
- **Слабое железо** — реранкер только как опция; HyDE увеличивает время ответа;
  всё измеряем на eval-наборе до включения по умолчанию.
- **Совместимость векторов** — переэмбеддинг обязателен только в Фазе 2;
  бэкенд эмбеддингов остаётся LM Studio (замена на `llama-server` даёт не качество,
  а явные ошибки вместо тихого усечения + путь к реранку — см. §4).
- **Откат** — обычный `git revert` по фазам; схема БД меняется только добавлением
  (FTS-таблица перестраивается командой), `config.yaml` совместим.
