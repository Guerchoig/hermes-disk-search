## 1. Мотивация и решение о переходе на Rust

### 1.1. Зачем: проблемы текущей архитектуры

Система работает и развивается, но стоимость её резидентного слоя на Python стала
ограничивающим фактором (проверено по коду и на рабочей машине — Приложение А):

**1. Память в простое.** Резидентно живут несколько Python-процессов:

| Компонент | Чем занят постоянно | Почему дорого |
|---|---|---|
| MCP-сервер (`hds/mcp_server.py`, `:8787`) | соединение с `index.db`, клиент эмбеддингов, лемматизатор (pymorphy3), CLIP-энкодер запроса | ~250 МБ на инстанс; при stdio-транспорте процесс порождается **каждым** агентом и каждой его сессией |
| Watcher (`hds/watcher.py`) | следит за ФС (`watchdog`), обрабатывает события, пишет в БД | постоянно в памяти, плюс подгружаемые библиотеки извлечения |
| UI (`hds/ui_server.py`) | HTML + 20 эндпоинтов, чтение `config.yaml` каждые 2 с | ещё один интерпретатор Python с зависимостями |
| llama-server × 3 (`:8010/:8011/:8012`) | держат chat/embedding/rerank в VRAM | ~9 ГБ VRAM и сотни МБ RAM, а управление загрузкой неявное |

**2. Сироты процессов.** По протоколу MCP при stdio-транспорте сервер запускает сам
клиент; долгоживущие hub-демоны агентов не закрывают stdin, и старый сервер не выходит.
В проекте уже есть чистка (`mcp-http stop-stdio`) и режим «один http-инстанс на машину» —
это вынужденная мера, вызванная ценой каждого инстанса (~250 МБ).

**3. Зоопарк бэкендов.** Транскрипция: faster-whisper (CTranslate2, CPU/CUDA),
whisper.cpp CLI (Vulkan — единственный путь на AMD/Intel), mlx-whisper (Metal). CLIP через
`sentence-transformers` тянет torch (~2,5 ГБ на диске), `.mpp` — jpype с JVM внутри
Python-процесса. У каждого компонента свои установка, версии и способы отказа.

**4. Тяжёлая установка и обновление.** Нужны Python 3.10+ (с борьбой против Store-заглушки),
venv, winget/brew для ffmpeg и Tesseract, Java для `.mpp`, три набора моделей; обновление =
замена исходников и перезапуск нескольких Python-процессов.

**5. Нет измерений.** Мотивация «снизить память» до сих пор опиралась на оценки, а не на
замеры — поэтому в план включён этап измерений и точка принятия решения (W0, §13.1).

**Чего хотим достичь:**

| Цель | Метрика |
|---|---|
| Радикально меньше памяти в простое | ≤ 150 МБ суммарно на watcher + MCP + UI + LLM-хост (§13.2) |
| Один предсказуемый владелец GPU | явные `load/unload` моделей, приоритет «запрос важнее индексации» (§8.6) |
| Один рантайм вместо двух-трёх | движок `openresearchtools/engine` покрывает LLM и ASR (§8, §9) |
| Нет дублей MCP и сирот | один инстанс на машину независимо от числа агентов (§2.3) |
| Установка без Python и без сборки C++ | один архив + скрипт установки, рантайм скачивается готовым zip (§10, §11) |
| Данные пользователя не меняются | `index.db`, `config.yaml`, `data/`, модели — читаются как есть (§3, Приложение Б) |
| Качество не хуже | паритет с текущей версией на контрольных запросах и пилотных папках (§13.3) |

**Не-цели (вне плана сознательно):** Linux и Intel Mac; покупка сертификатов подписи и
нотаризации; диаризация совещаний; перенос извлечения PDF/DOCX/XLSX/PPTX на нативные
крейты; расширение покрытия форматов сверх `.xls`; кластерный/RPC-режим движка.

### 1.2. Решение о переходе на Rust

**Решение (принято 29.09.2026).** Резидентное ядро переводится на Rust, извлечение
документов остаётся на Python-воркере, llama-server заменяется встроенным рантаймом
движка с явным управлением моделями. Целевые платформы — `windows-x64` и `macos-arm64`.

| Компонент | Решение |
|---|---|
| watcher, индексатор, чанкер, БД, поиск/RAG/реранк, MCP, UI, диагностика | **Rust** — резидентные процессы дают основное потребление памяти |
| llama-server (chat/embedding/rerank) | **удаляется**; вместо него процесс `llm-host` на движке (`load/unload_instance`, `memory_free`) |
| ASR | **движок** `openresearchtools/engine` + `whisper-large-v3-turbo-GGML` (как в `transcribeoffline`); внешний `whisper-cli` — аварийный путь |
| CLIP (картинки) | **Rust + ONNX Runtime** — vision и мультиязычный text-энкодер |
| Лемматизация (русская морфология) | **остаётся Python** (воркер `normalize`): зрелого эквивалента pymorphy3 нет, а смена алгоритма обесценивает FTS-индекс |
| PDF/DOCX/XLSX/PPTX + OCR | **остаётся Python** (воркер `hds-extract`, JSON-RPC по stdio) — зрелость библиотек и паритет извлечения |
| `.mpp` | отдельный **Java-процесс** (mpxj), без jpype |
| Модели GGUF | **сохраняются** в общем каталоге; `shared:<role>`/`current.json` продолжают работать |

**Рассмотренные альтернативы и почему отклонены:**

| Альтернатива | Почему не выбрана |
|---|---|
| Оставить всё на Python, ограничиться оптимизациями | Не решает ни память (~250 МБ на MCP-инстанс), ни сирот, ни отсутствия контроля VRAM; установка остаётся тяжёлой |
| Перевести только MCP/UI (резидентный слой), ядро оставить на Python | Даёт быстрый эффект и сохранено как **первая волна** (W1), но watcher и индексатор — самое дорогое и хрупкое звено |
| Транскрипция через `whisper-rs` | Нужны `cmake` + CUDA Toolkit/Vulkan SDK на каждой сборочной платформе и отдельные бэкенд-артефакты; у движка это готовые zip |
| Заморозка Python-воркера (PyInstaller/Nuitka) | Bootloader — главный триггер ложных срабатываний антивирусов, а подписи нет; выбран relocatable CPython + `uv` (§5.3) |
| Купить сертификат/нотаризацию | Azure Artifact Signing — организации US/CA/EU/UK, Apple Developer Program — не во всех регионах; EV не даёт мгновенного доверия SmartScreen (§10.5) |
| Сохранить llama-server основным путём | Не даёт явного управления VRAM (требование диспетчеризации) и тянет второй рантайм |
| Всё в одном процессе (`llm-host` вместе с индексацией) | Падение индексации ломало бы поиск и наоборот; сохранено разделение ролей-процессов (§2.3) |

**Технические находки аудита, определившие архитектуру** (каждая учтена в конкретном разделе):

| # | Находка | Почему важно | Где учтено |
|---|---|---|---|
| F1 | **CLIP нельзя оставлять в Python-воркере** | `hds/search.py:165-194` вызывает `clip_index.embed_text(query)` **внутри каждого поискового запроса**: воркер тогда не засыпает по простою, на каждый запрос поднимает torch (~1,5–2,5 ГБ RSS), латентность поиска растёт на секунды | CLIP целиком переезжает в Rust через ONNX Runtime (`ort`): vision — на индексации, text — в поиске. Обязательно **сохранить мультиязычный text-энкодер** (`dim=512`, `images_vec` уже создана под 512); англоязычный `Qdrant/clip-ViT-B-32-text` сломал бы запросы «найди изображения цветов». Fallback — §7 |
| F2 | **Русская лемматизация — не Rust-задача** | `hds/lemmatizer.py` вплетён в три места: индексация (`db.add_chunk` → `normalize()` в `chunks_fts`), поиск (`search._fts_tokens`/`fts_query`, `make_snippet`) и диагностика (`diag.py`, проверка `fts-norm`). Без неё `chunks_fts MATCH` перестаёт совпадать с существующим индексом | Лемматизация **не портируется в Rust** (нет зрелого крейта: `rsmorphy` — WIP 2018 г., `morph-rs` — 2024 г. почти без пользователей; `tantivy-stemmers` — Snowball-стемминг, это другая нормализация и сломает совместимость). Решение — §6 |
| F3 | **Контракт воркера должен быть сегментным, а не «блочным»** | `hds/chunker.py` принимает **сегменты** с полями `text/page/t_start/t_end/head`; `head` («# Раздел / ## Подраздел») попадает в начало каждого чанка секции и учитывается в бюджете (`hbudget`); плюс запрет смешивать разные `page`/таймкоды и перекрытие целыми предложениями. Плоский список `blocks` с `type/level` эту информацию теряет | Контракт воркера возвращает **сегменты 1:1 как `hds/extractors.seg()`** — с `head`, `page`, `t_start`, `t_end`. Заголовки, таблицы и OCR-текст — это уже готовые сегменты, а не отдельные сущности протокола. См. §5 |
| F4 | **Один бинарник ≠ один процесс** | Сегодня процессы разделены намеренно: `watcher` запускается Планировщиком/LaunchAgent независимо от UI; MCP живёт один на машину и перезапускается отдельно (`mcp-http restart-if-stale`), при обновлении проекта watcher не трогается; llama-server отвязан и переживает перезапуск UI/MCP/CLI; падение UI не убивает индексацию; `db-move` останавливает именно watcher/index, а не UI | Один **бинарник** — несколько **режимов-процессов**: `hds watch`, `hds mcp-http run`, `hds ui`, `hds index`, `hds llm-host` (плюс отдельный `hdsw.exe` с `windows_subsystem="windows"` вместо `pythonw.exe`, §10.1). Общий код — в библиотечном крейте воркспейса |
| F5 | **Замена faster-whisper на `whisper-rs` — не «просто замена»** | (1) `BatchedInferencePipeline` в whisper.cpp нет — «батчинг x3–5» не переносится; (2) `vad_filter=True` переносится лишь частично — границы сегментов/таймкоды будут другими; (3) `whisper-rs-sys` компилирует C++ на месте: нужен C++ toolchain и cmake, для GPU — CUDA Toolkit / Vulkan SDK, артефактов получается несколько | Решением заказчика (§8) взят **ASR-движок `openresearchtools/engine`** по образцу `transcribeoffline`: готовые рантаймы cuda/vulkan/metal + модель `whisper-large-v3-turbo`; сборка C++ исключена; официальный fallback — внешний `whisper-cli.exe` (уже работает в проекте) |
| F6 | **`.mpp` через jpype внутри воркера — хрупко** | Сейчас это `jpype.startJVM()` в процессе Python (`hds/extract_static.py:45-85`); в замороженной сборке JVM + JPype + поиск `jvm.dll` — источник трудноуловимых падений. Java на машине уже есть (`%LOCALAPPDATA%\jdk-21\jdk-21.0.12.1+1\bin\java.exe`), а mpxj — обычная библиотека с `main` | §9: `.mpp` выносится в отдельный **Java-процесс** (`java -cp mpxj.jar;hds-mpp.jar …`), jpype исключается; поиск JDK остаётся прежним (JAVA_HOME → `%LOCALAPPDATA%\jdk-21` → `/opt/homebrew/opt/openjdk` → `/Library/Java/JavaVirtualMachines`) |

| F7 | **Подпись кода в 2026 г., скорее всего, недоступна** | На 2026 г.: EV-сертификаты **больше не дают** мгновенного доверия SmartScreen (Microsoft убрал это поведение в 2024 г.); Azure Trusted/Artifact Signing (~$9.99/мес.) доступен **только организациям США, Канады, ЕС и Великобритании, физлицам — только США/Канада**; Apple Developer Program ($99/год, нужен для нотаризации) — «enrollment may not be supported in certain regions … due to sanctions». Для проекта из РФ обе подписи, скорее всего, **недоступны** | §10: стратегия «низкий AV-риск без подписи» + честная деградация UX. ## 2. Целевая архитектура

### 2.1. Принципы

1. **Резидентное — на Rust, извлечение — на Python.** Всё, что живёт между запросами
   (watcher, MCP, UI, `llm-host` на движке, клиент эмбеддингов, CLIP-энкодер запроса,
   лемматизация запроса), работает в Rust. Python вызывается только на время
   извлечения текста из документов.
2. **Один бинарник — несколько процессов-ролей.** Как сегодня `python/pythonw` +
   `-m hds.cli <режим>`: разделение процессов сохраняет независимый перезапуск,
   изоляцию падений и совместимость с автозапуском (§2.3).
3. **Контракт выше реализации.** Экстрактор говорит с ядром по версионированному
   контракту «сегментов» (§5), поэтому позже любой формат можно перевести на
   нативный крейт, не трогая ядро.
4. **Деградация вместо падения.** Отсутствие любого необязательного компонента
   (LLM, OCR, whisper, CLIP, Java, sidecar) не должно ломать индексацию и поиск.
5. **Никаких изменений в существующих данных.** `index.db`, `config.yaml`, `data/`,
   общий llama-рантайм, настройки Hermes/Cline читаются как есть (§3).

### 2.2. Схема

```
   ФС (notify) ─┐
   UI  :8765 ───┼──►  hds.exe / hdsw.exe   (один бинарник, разные режимы-процессы)
   MCP :8787 ───┤        watch | index | mcp-http | ui | llm-host | check | db-move
   CLI ─────────┘                        │
                                         ├─ клиент ─────► llm-host (единственный владелец GPU):
                                         │                 llama_server_cluster + инстансы
                                         │                 chat | embedding | rerank | whisper
                                         │                 (load/unload_instance, memory_free)
                                         ├─ HTTP ──────► фасад :8010 / :8011 / :8012
                                         │                 (chat | chat-think | embedding | rerank)
                                         ├─ stdio ─────► hds-extract (Python): сегменты + normalize
                                         ├─ subprocess ► ffmpeg / ffprobe (аудио → WAV 16 кГц;
                                         │                 у движка есть свой ffmpeg — §8)
                                         ├─ subprocess ► java -cp mpxj.jar (MS Project → строки задач)
                                         └─ в процессе ► ONNX Runtime: CLIP vision (индексация)
                                                                        CLIP text   (поиск)

   Хранилище: index.db = SQLite (rusqlite, bundled) + vec0 (sqlite-vec 0.1.9) + FTS5
   Модели:    llama-runtime/models/<role>/ (GGUF) + current.json  — общий каталог, без бинарников
```


### 2.3. Процессы, роли и владение ресурсами

| Процесс | Кто запускает | Живёт | Владеет | Почему отдельный процесс |
|---|---|---|---|---|
| `hds watch` | Планировщик (Win) / LaunchAgent (mac) | постоянно | `watch.lock`, БД (RW), индексный конвейер, heartbeat | автозапуск и перезапуск независимо от UI/MCP; сегодня так же |

`hds` (консольный) и `hdsw` (без консоли) — два `[[bin]]` одного воркспейса над общим
`lib`: ровно та же схема, что сегодня у `python.exe`/`pythonw.exe`, только без интерпретатора.

**Диспетчер GPU-ресурсов** — реализуется **внутри `llm-host`** поверх cluster API движка
(§8.6): загрузка/выгрузка инстансов, приоритеты «запрос важнее индексации», отчёт о нехватке
VRAM (без авто-деградации — модель меняет пользователь). Остальные процессы выступают
клиентами `llm-host` (внутрипроцессно или
через `cluster_instance_name`); сигнальные файлы (`index.stop`, `index.pause`,
`index.heartbeat.json`) остаются только для управления индексацией.

## 3. Контракты совместимости (что НЕ меняется)

### 3.1. Данные

1. **`index.db`** — схема байт-в-байт: `files`, `chunks`, `chunks_fts` (FTS5),
   `chunks_vec` (vec0, `float[dim]`), `images_vec` (vec0, `float[512]`), `meta`;
   индексы; `PRAGMA journal_mode=WAL`, `synchronous=NORMAL`, `foreign_keys=ON`,
   `busy_timeout=30000`.
2. **`content_hash`** — `blake2b(digest_size=16)` от `size.to_string()` + первые
   256 КБ + последние 256 КБ (если `size > 256 КБ`). В Rust — `Blake2b<U16>`
   (обязательно с параметром длины 16, не усечение BLAKE2b-512!). **Паритет-тест на
   фиксированных векторах обязателен** — иначе полная переиндексация всей БД.
3. **`meta.vec_dim`** и логика смены размерности: если `meta` не подтверждает
   текущий `embedding.dim`, делается **проба вставкой с `SAVEPOINT`/`ROLLBACK`**, и
   только при реальном несовпадении таблица `chunks_vec` пересоздаётся, а `meta`
   обновляется (никаких записей в БД при обычном `connect()`).
4. **Бэкфилл `indexed_at`** для строк со статусом `indexed` и `indexed_at IS NULL`
   (`mtime + 10`), один раз, молча.
5. **`chunks_fts.text`** — лемматизированный текст; **`chunks.text`** — отображаемый.
   Запрос лемматизируется тем же способом (§6), FTS-запросы: сначала `AND`, при пустом
   результате — `OR`, последний токен — с префиксом `*`, экранирование кавычек
   удвоением, `ORDER BY bm25(chunks_fts)`, `kinds` пробрасывается в SQL (pushdown).
6. **Инварианты файлов**: атомарный коммит на файл (фаза «извлечение» → фаза «запись»),
   статусы `new|indexed|error`, `chunk_count`, `indexed_at`, `error`.
7. **Пропуски**: файлы `~$*` (Office-локи), отсутствующие корни, `exclude_dirs` (по
   имени любого компонента пути) и `exclude_paths` (по границе компонента, регистр и
   разделители нормализуются как `normcase(normpath()) + нижний регистр`, `\` → `/`),
   лимиты `max_file_mb` (200) / `max_media_mb` (2500) / `max_chunks` (3000, обрезка с
   предупреждением), «корзина» и системные каталоги.
8. **`prune`** удаляет записи исчезнувших файлов; при исчезновении >20 % от общего
   числа — **блокировка** с сообщением и требованием `--confirm-delete`.

### 3.2. Конфигурация

* `config.yaml` — все секции читаются как есть (`index`, `chunk`, `embedding`, `chat`,
  `llm_server`, `mcp_http`, `search`, `rerank`, `watch`, `db_path`); устаревшие и
  «мягкие» ключи (`whisper_device: cuda|vulkan|metal|cpu`, `whisper_compute`,
  `whisper_cpp_dir`, `whisper_dir`, `whisper_mlx_repo`, `hf_token`,
  `ocr_tesseract_cmd`, `clip`, `max_chunks`, `exclude_paths`, `clip_weight`) продолжают
  приниматься и по возможности действовать.
* **Секция `llm_server` остаётся, но меняет смысл**: `bin`/`extra_args`/`ctx_per_slot`
  больше не «аргументы llama-server», а **источник для параметров инстанса кластера**
  (`llm_server.<role>.model` → `instance_params.model_path`, `ctx_per_slot` → `n_ctx`,
  `parallel` → `n_parallel`, `extra_args` разбираются на поддерживаемые ключи
  `-ngl/--n-gpu-layers`, `--batch-size`, `--ubatch-size`, `--no-kv-offload`, `--kv-unified`,
  `--cache-ram`, `--main-gpu`, `--tensor-split`; неподдерживаемое — предупреждение
  в `hds check` и лог, а не молчаливое игнорирование). Добавляются `llm_server.mode` и
  секция `llm`/`gpu` (§8.6.2, §8.7).
* **Сохранение файла из UI — с сохранением комментариев и inline-вида** (`_set_roots`,
  `_set_exclude_paths`, `_set_simple_config`, `db-move` перезаписывают YAML
  текстовыми подстановками, а не сериализацией). Это надо перенести один-в-один —
  `serde_yaml` для этого **не** подходит (убивает комментарии), нужны те же
  regex-подстановки; в §12 — паритет-тесты на реальном `config.yaml`.
* Атомарная запись через временный файл + `replace` **с ретраями на `PermissionError`**
  (Windows: UI читает конфиг каждые 2 с из соседнего потока).
* `HDS_CONFIG` — переопределение пути конфига; `LLAMA_RUNTIME_DIR` — переопределение рантайма.

### 3.3. Интерфейсы

* **Порты и протоколы**: MCP `:8787` + `mcp_http.path` (`/mcp`, streamable-http),

## 4. Стратегия и волны миграции

### 4.1. Почему волнами, а не «всё за один релиз»

Вариант «одним релизом в конце» (водопад) занял бы 4–4,5 месяца и поздно оплачивал бы
основную цель (память), а всё это время требовал бы двойной поддержки. Правильная
декомпозиция здесь — по **типу процесса**:

* **Резидентный слой** (MCP-сервер, UI, поиск/RAG, CLIP-энкодер запроса, менеджер
  llama-server) — именно он даёт стабильные ~350–450 МБ RSS в простое и ~250 МБ
  на MCP-инстанс. Его можно перенести на Rust **не трогая** watcher и индексатор:
  MCP/UI работают с той же `index.db` (WAL) и с тем же llama-server по HTTP.
* **Конвейер** (watcher, индексатор, чанкер, запись в БД) — дороже всего в переносе
  из-за паритета чанкера, лемматизации и файловых сигналов, и именно здесь в Python
  сосредоточена выстраданная логика. Переносим вторым.
* **Медиа** (whisper) — самая рискованная часть (другой движок, другие таймкоды) и
  наименее нужная для экономии памяти: whisper живёт только во время индексации
  медиафайлов. Переносим третьим и **без права ухудшить качество**.

Такая последовательность даёт ранний измеримый эффект, позволяет остановиться на любой
волне без «полуфабриката» и сохраняет работающий Python-режим как страховку.

### 4.2. Волны, задачи, критерии приёмки, оценка

Легенда оценок — «человеко-недели» одного разработчика, знакомого с проектом.

## 5. Контракт sidecar-экстрактора (детально)

### 5.1. Транспорт и жизненный цикл

* **Транспорт: stdio + JSON-RPC 2.0**, кадрирование — по строкам (NDJSON: один
  JSON-объект на строку, UTF-8, без вложенных переводов строк). Аргумент — `--root <путь проекта>`,
  чтобы воркер не искал `config.yaml` сам.
* **Родитель владеет процессом**: `hds`/`hdsw` запускает воркер лениво (при первом файле,
  требующем Python), закрывает **stdin** для штатного выхода, убивает процесс при
  собственном завершении (`kill_on_drop`, Job Object на Windows / process group на macOS).
  Это решает проблему сирот, с которой проект уже боролся на MCP-stdio.
* **Простой**: воркер завершается сам после `N` секунд без запросов (по умолчанию 60 с,
  настраивается `extract.idle_timeout`). В ожидании — 0 процессов и 0 МБ.
* **Устойчивость**: пер-файловый таймаут (убить и перезапустить воркер), перезапуск
  воркера после `M` файлов или после «подозрительного» поведения, ограничение по RSS
  (наблюдение из родителя). Ошибка воркера никогда не роняет индексацию: файл получает
  статус `error` с текстом (как сейчас).
* **Версия протокола**: метод `hello` → `{"protocol": 1, "python": "3.12.x",
  "capabilities": ["pdf","docx","xlsx","pptx","text","ocr","clip","normalize"]}`.
  Родитель сверяет `protocol` и, при необходимости, набор возможностей (нет OCR-модуля —
  работает без OCR, как сейчас).

### 5.2. Методы

```jsonc
// 1) hello → capabilities (при старте)
{"id":1,"method":"hello","params":{"protocol":1}}
{"id":1,"result":{"protocol":1,"python":"3.12.10",
                  "capabilities":["pdf","docx","xlsx","pptx","text","ocr","normalize"]}}

// 2) extract — извлечение сегментов
{"id":2,"method":"extract",
 "params":{"path":"D:\\отчёты\\отчёт.pdf",
           "kind":"pdf",                        // как в hds.extractors.kind_for_ext
           "opts":{"ocr":true,"ocr_lang":"rus+eng",
                   "ocr_tesseract_cmd":"C:\\Program Files\\Tesseract-OCR\\tesseract.exe",
                   "clip":false},               // CLIP выполняет ядро (Rust), не воркер
           "timeout":600}}
{"id":2,"result":{"kind":"pdf",
  "segments":[
    {"text":"Итоги квартала","page":3},                       // заголовок — часть сегмента
    {"text":"...","page":3},
    {"text":"...","page":4},
    {"text":"OCR: ...","page":5},
    {"text":"1 2 3 | a b c","head":"# Раздел / ## Таблица","page":6}
  ],
  "warnings":["страница 7: пустой текст"],
  "elapsed_ms":812}}
// ОШИБКА (структурированная, чтобы ядро решало судьбу файла):
{"id":2,"error":{"code":-32001,"message":"pdf повреждён: cannot open","hint":"файл пропущен"}}

// 3) normalize — лемматизация (пакетная, для индексации и запросов)
{"id":3,"method":"normalize","params":{"texts":["настройки прокси","скрипта нет"]}}
{"id":3,"result":{"lemmas":["настройка прокси","скрипт нет"]}}

// 4) clip_image — векторы картинок (fallback, если CLIP останется в Python, см. §7)
{"id":4,"method":"clip_image","params":{"paths":["D:\\фото\\1.jpg","D:\\фото\\2.jpg"]}}
{"id":4,"result":{"vectors":[[0.01,-0.02,"...512 значений..."],["..."]]}}

// 5) shutdown
{"id":5,"method":"shutdown"}
```

**Ключевое требование к контракту**: ответ — **список сегментов** того же вида, что
возвращает `hds/extractors.py:seg()` (`text`, `page`, `t_start`, `t_end`, опционально
`head`), а не «блоки». Никакой трансформации в ядре не требуется: Rust кладёт сегменты в
свой порт чанкера 1:1, и паритет чанков проверяется механически.

Правила соответствия для каждого формата (переносятся из текущего кода без изменений
логики):

| Формат | Как формируются сегменты (сегодня) |
|---|---|
| `text`/код | один сегмент целиком; декодирование utf-8 → cp1251 → utf-8 с `ignore`, удаление `\x00` |
| `md` | сегменты по секциям, `head` = путь заголовков (`# Раздел / ## Подраздел`), уровень ≥ 6 обрезается |
| `pdf` | сегменты по страницам (`page` = номер с 1); текстовая страница; если страница пустая и `ocr` включён — OCR-текст той же страницы |
| `docx` | абзацы с учётом стилей Heading 1–6/Title/`заголовок N` → `head`; таблицы — отдельными сегментами `ячейка \| ячейка` |
| `xlsx` | лист = сегмент (`page` = номер листа), строки через ` \| `, обрезка после 5000 строк с пометкой «... (лист обрезан)» |
| `pptx` | слайд = сегмент (`page` = номер), текст фигур + таблицы |
| `image` | один сегмент: «Изображение: WxH px, формат …», «папка: …», EXIF (дата/камера/автор/описание), затем «Текст на изображении (OCR): …» |
| `media` | первый сегмент — метаданные (`ffprobe`), далее сегменты транскрипции с `t_start`/`t_end` |
| `mpp` | сегменты по 200 строк задач (см. §9) |

### 5.3. Как поставляется воркер

Наивное решение — «один замороженный бинарник» (PyInstaller/Nuitka). Проблема: ложные
срабатывания антивирусов у PyInstaller — известная и системная (bootloader + распаковка
в temp — типовые признаки для эвристик), а подписи у нас, скорее всего, не будет (§10.5).

Предлагаемая поставка — **три варианта, один из которых выбирает установщик**:

| Вариант | Как | Плюсы | Минусы |
|---|---|---|---|
| **A. relocatable CPython** (рекомендуемый) | `uv python install 3.12` (python-build-standalone), `uv pip install --target sidecar/vendor -r sidecar/requirements.lock`, запуск `sidecar/python.exe sidecar/run.py` | нет bootloader'а → нет характерных AV-эвристик; воркер — обычный процесс; легко обновлять зависимости; тот же приём работает на macOS | ~120–180 МБ на диске (интерпретатор + пакеты) |
| **B. PyInstaller one-folder** | сборка в CI, архив с exe + `_internal` | один `.exe` | AV-риски, +30–60 МБ, сложнее с нативными либами |
| **C. системный Python** (fallback) | берём найденный Python 3.10+ и создаём venv, как сейчас | нулевой вес в архиве | требует Python у пользователя (то, от чего хотели уйти) |

Установщик по умолчанию ставит **A**; если распаковка/запуск не удались — предлагает
**C** (понятное сообщение, как сейчас в `setup.ps1` про Store-заглушку). Вариант **B**
остаётся доступен как отдельный артефакт для тех, кому нужен именно exe.

Состав зависимостей воркера после миграции резко уменьшается: уходят `sentence-transformers`
(+ torch, ~2,5 ГБ), `nvidia-*`, `ctranslate2`, `watchdog`, `requests`, `mcp`, `sqlite-vec`,
`pymorphy3` остаётся, `mpxj`/`jpype1` заменяются Java-путём (§9). Итого — PDF/DOCX/XLSX/PPTX
+ OCR + pymorphy3.

## 6. Лемматизация (русская морфология)

### 6.1. Почему нельзя просто «переписать на Rust»

`hds/lemmatizer.py` определяет содержимое `chunks_fts` (индексация), запрос FTS
(`search._fts_tokens`) и сниппеты. Значит:

* если нормализация в Rust будет **другой** (например, Snowball-стемминг из
  `tantivy-stemmers`), то **весь существующий FTS-индекс станет невалидным**: запросы
  перестанут находить старые чанки, потребуется `reindex-fts` на 612 тыс. чанков (по
  документации проекта — 30–90 минут только CPU, но с проверками и рисками — это часы
  работы), и всё равно качество морфологии изменится;
* если нормализация будет **отсутствовать** (искать по точным словам) — деградация
  поиска, которая в этом проекте уже однажды лечилась (диагностика `fts-norm` в
  `hds/diag.py` существует именно для этого);
* крейтов-эквивалентов pymorphy2/pymorphy3 с нужным качеством нет: `rsmorphy` (последний
  релиз 2018 г., статус WIP), `morph-rs` (2024 г., единицы загрузок), `tantivy-stemmers`
  (Snowball) — не тот алгоритм. Порядок разборов pymorphy (какой из омонимов первый)
  вообще нестабилен между реализациями.

### 6.2. Два допустимых решения (выбор — за заказчиком)

**Вариант A — воркер нормализации (минимальный риск, рекомендуется на W1).**
Лемматизация остаётся функцией Python-воркера (`normalize`, пакетно). Свойства:

* потребление: отдельный процесс, только когда нужно; `pymorphy3` + словари ~10 МБ
  словарей и ~60–90 МБ RSS; кэш разобранных словоформ (`_CACHE_MAX = 50000` — как сейчас);
* латентность: при тёплом воркере — единицы миллисекунд на пакет из десятков строк;
  при холодном — ~1–2 с (загрузка словарей). Для MCP-поиска это допустимо, для
  1000-строчных батчей индексации — незаметно;
* можно объединить с воркером извлечения (одна точка входа, один процесс) или держать
  отдельный «лёгкий» воркер без PDF/OCR — решается по замерам W0;
* риск: воркер нужен и на «горячем» поисковом пути → если воркер недоступен, деградация
  до нормализации «как есть» (как сегодня при отсутствии pymorphy3) с предупреждением.

**Вариант B — выгруженная таблица лемм (быстрее и без Python на запросе).**
`lemmatize_token` — чистая функция словоформы (pymorphy2 без контекста): результат
зависит только от формы токена. Значит, можно один раз выгрузить отображение
`форма → лемма` (лучший разбор + признак «неизвестное слово») и положить его рядом с БД:

* источник слов: (1) все токены, встречающиеся в `chunks_fts`, (2) словари pymorphy3
  (полный список форм), объём — единицы миллионов строк, при сжатии (sorted array +
  mmap) порядка 30–60 МБ; загрузка через `mmap` — без расхода RSS на весь словарь;
* для неизвестных слов нужно воспроизвести поведение текущего кода (сейчас берётся
  `parses[0].normal_form`, что может отличаться от «вернуть слово как есть»), поэтому
  таблица должна содержать и запись «неизвестное» — тогда строки `chunks_fts` для старых
  чанков и запросы совпадут точно;
* артефакт генерируется **тем же** Python-кодом (`lemmatizer.normalize`) и версионируется;
  при обновлении pymorphy меняется версия таблицы — и это видно в `hds check`.

Рекомендация: **A на W1** (быстро, низкий риск), **B — как оптимизация в W3/W4**, если
замеры покажут, что лемматизация на запросе заметна. В обоих случаях обязателен
паритет-тест: 100 000 случайных токенов из реального `chunks_fts` + 1 000 запросов —
`normalize` из Rust-пути совпадает с Python-эталоном строка-в-строку.

## 7. CLIP: поиск картинок по содержанию

### 7.1. Почему CLIP не может жить в Python-воркере

Наивный вариант — оставить CLIP в Python-sidecar. Но CLIP нужен **в двух разных местах с
разными требованиями**:

| Место | Когда нужен | Требование |
|---|---|---|
| Vision-энкодер (`clip_index.store_for_file`) | при индексации картинки | пиковая нагрузка, приемлемо «через воркер» |
| Text-энкодер (`clip_index.embed_text(query)`) | **на каждом текстовом поиске** (`hds/search.py:165-194`) | резидентный, миллисекунды, без загрузки torch |

Плюс `sentence-transformers`+`torch` — самая тяжёлая зависимость в проекте (~2,5 ГБ на
диске, сотни МБ RSS при загрузке). Держать её ради одной ветки поиска — плохой обмен.

### 7.2. Решение: оба энкодера — в Rust через ONNX Runtime

1. **Экспорт моделей** (одноразовый скрипт `tools/clip_export.py`, результат кладём в
   релизный артефакт, а не в git): vision — `sentence-transformers/clip-ViT-B-32`
   (или `openai/clip-vit-base-patch32`; для vision это одна и та же модель),
   text — `sentence-transformers/clip-ViT-B-32-multilingual-v1` (мультиязычный,
   50+ языков, включая русский). Формат — ONNX, при желании `int8`-квантование
   (векторы сверяются с эталоном: косинус ≥ 0,999).
2. **Запуск** — крейт `ort` (ONNX Runtime) внутри процессов ядра: vision — в процессе
   `hds index`/`watch` (создаётся только при появлении картинки), text — в процессе
   `hds mcp-http run` (загружается лениво, при первом поиске с CLIP-веткой).
3. **Совместимость с текущим индексом**: `dim = 512`, таблица `images_vec` не меняется,
   векторы сравнимы с уже построенными — при условии, что мы используем **те же веса**
   (именно поэтому нельзя подменять text-энкодер на англоязычный
   `Qdrant/clip-ViT-B-32-text`: это другая модель, и русские запросы будут мусором,
   хотя технически dim совпадёт).
4. **Проверка в W0 (спайк 4)**: сравнение эмбеддингов Rust-пути и Python-пути на 200
   картинках и 50 запросах; критерий — топ-10 совпадает, косинус ≥ 0,999.
5. **Деградация**: нет ONNX-моделей или `onnxruntime` не собрался для платформы —
   CLIP-ветка отключается с предупреждением (как сейчас при отсутствии
   `sentence-transformers`), ключевой и векторный поиск работают.
6. **Fallback (если спайк не удастся)**: text-энкодер в отдельном **маленьком**
   Python-воркере на `onnxruntime` (без torch) — 100–200 МБ RSS, но только на время
   запроса, и с честным измерением латентности; либо `clip_index` временно отключается
   по умолчанию (`index.clip: false`) с явным сообщением в `hds check`.

### 8.3. Как вызывается движок (референс — `transcribeoffline`)

Канонический путь у них — **in-process**, не CLI:

```rust
// libloading → llama-server-bridge.dll (подмножество C-API; адаптация bridge.rs из
// transcribeoffline, MIT — с атрибуцией проекта-источника)
let api = BridgeApi::load(&runtime_dir)?;           // + configure_runtime_dll_search(dir)
let response_json = api.run_audio_raw(&shared, &AudioRunParams {
    audio_bytes, audio_format,                      // содержимое файла как есть
    metadata_json: json!({
        "mode": "speech",                            // speech | subtitle | transcript
        "custom": "default",
        "output_dir": <каталог результата>,
        "audio_source_path": <путь аудио>,
        "whisper_model": <путь к whisper-large-v3-turbo-GGML.bin>,
        "whisper_word_time_offset_sec": 0.73,        // дефолт их приложения
        "whisper_gpu_device": <индекс GPU>,          // либо "whisper_no_gpu": true
        "transport": "audio_raw_bytes"
    }),
    ffmpeg_convert: true,                            // декодирование встроенным ffmpeg
})?;                                                 // ответ: /output/path → читаем текст
```

Три вещи, которые обязательно переносим (у них это уже отлажено):

1. **ASCII-стейджинг путей.** На Windows не-ASCII путь в metadata приводит к испорченному
   имени файла результата; они копируют аудио и `output_dir` в ASCII-временный каталог и
   переносят готовый транскрипт к исходному имени. **У нас все индексные пути русские
   («D:\НИНА\…»), поэтому без этого шага транскрибация сломается** — это требование W3 и
   отдельный паритет-тест (файл с русским именем в не-ASCII каталоге).
2. **Выбор устройства**: `whisper_gpu_device` при выбранном GPU, иначе явный
   `whisper_no_gpu: true` (иначе рантайм может выбрать недоступный бэкенд).
3. **Поиск DLL рантайма** до загрузки моста (`SetDllDirectory`/`AddDllDirectory` на
   Windows; rpath/`DYLD_*` на macOS).

### 8.4. VRAM и очередь: обязательная политика

На этой машине (12 ГБ VRAM) все модели одновременно на GPU не помещаются:

| Роль | Модель | VRAM |
|---|---|---|
| chat | Qwen3.5-9B-Q6_K + KV q8_0 | ~7,5–8 ГБ |
| embedding | bge-m3 Q8_0 | ~1,2 ГБ |
| rerank | bge-reranker-v2-m3 | 0 (сейчас `-ngl 0`) |
| транскрипция (turbo) | whisper-large-v3-turbo | ~1,6–2,5 ГБ |

Чат + embedding ≈ 9 ГБ, свободно ~3 ГБ — турбо-виспер влезает на грани. Политику
разрешения конфликтов задаёт **диспетчер GPU** (§8.6), а не отдельные «магические» флаги:

* `gpu.policy: query_priority` (по умолчанию) — запрос важнее индексации: при нехватке
  VRAM индексация встаёт на паузу, вытесняются индексные роли (whisper → rerank →
  embedding), поднимается chat; после запроса всё возвращается по потребности;
* при индексации без запросов чат-роль может быть выгружена — **только если HDS ею
  владеет** (иначе инстанс переиспользует `anonymizer_proxy`, и его нельзя трогать);
* `index.whisper_gpu: auto | off`, `gpu.reserve_mb`, `gpu.evict_idle_sec` — тонкая
  настройка; при нехватке памяти — автоматический CPU-fallback с сообщением
  (как сейчас работает `whisper_load_timeout`-fallback на CPU);
* параллелизм транскрипций — 1–2 одновременно, чтобы не раздувать VRAM;
* всё это документируется в README (как сейчас про `-ngl 0`).

### 8.6. Диспетчер GPU-ресурсов (VRAM-арбитр)

Требование заказчика: **диспетчеризация с приоритетами** — запрос важнее индексации.
При запросе и нехватке VRAM: остановить индексацию, вытеснить наименее используемую
модель индексации, загрузить чат-модель. При индексации без запроса и нехватке VRAM:
разрешается выгрузить чат-модель. Внешний ИИ-агент должен иметь доступ к чат-модели
**с включёнными размышлениями**, а MCP — с выключенными (§8.7). `anonymizer_proxy` из
рассмотрения исключён (заказчик переводит его на движок отдельно), поэтому диспетчер
строится сразу на схеме «единый владелец GPU» (§8.6.2).

  бинарников общего рантайма больше нет.
* Остальные процессы (`index`/`watch`, `mcp-http`, `ui`) — **клиенты**: адресуют инстансы
  кластера (внутрипроцессно либо через `cluster_instance_name`). Точный механизм
  кросс-процессной адресации проверяется спайком W0 (какой DLL экспортирует cluster API —
* Точный механизм кросс-процессной адресации: `multi-node-server.dll` экспортирует cluster API
  (спайк 6а, LOAD_OK) — проверяется тестом A3 в W2; при неудаче гарантированный путь —
  клиенты через наш фасад `:8010–8012` (см. `PLAN_W2_LLM_HOST.md` §4 A3).
* Артефакты: `data/llm-host.pid`, `data/logs/llm-host.log` (вместо четырёх ллama-логов).

**Правила приоритетов** (реализуются в `llm-host`):

| Событие | Действие |
|---|---|
| Запрос (`ask`/`search` из MCP/UI или от внешнего агента), `memory_free` < потребности | 1) поставить индексацию на паузу (`index.pause`); 2) выгрузить индексные инстансы по приоритету: `whisper` → `rerank` → `embedding` (`unload_instance`); 3) `load_instance(chat)`; 4) обслужить запрос |
| Запрос завершён | Снять паузу; индексные инстансы вернутся сами (`LOAD_ON_DEMAND` при первом вызове) |
| Индексация без запросов, VRAM не хватает | Разрешить выгрузку `chat` (ограничений владения больше нет) |
| Простой роли | `GRACE` + `load_on_demand_grace_seconds` (встроено), плюс `gpu.evict_idle_sec` как внешний предохранитель |
| Загрузка упала (`FAILED` / `last_error`) | Не ретраить бесконечно: деградация (меньший квант, `n_gpu_layers`, CPU) + запись в лог и `hds check` |

**Политика при нехватке VRAM** (решение заказчика 29.09.2026): `llm.model_policy: fixed`.
Арбитр сравнивает реальную свободную VRAM (NVML) с оценкой «модель + KV» и при нехватке
**сообщает точные цифры** (лог, UI «GPU и модели», `hdsw check`), после чего ждёт, пока
пользователь выберет другую модель в UI (`models/chat/current.json` → перезагрузка инстанса
`chat`). Автоматических переходов кванта, уменьшения `n_ctx` и частичного офлоада **нет** —
это осознанный выбор в пользу предсказуемости («не деградировать молча»).

**Конфиг** (все ключи необязательные):

```yaml
gpu:
  policy: query_priority      # query_priority | indexing_priority | manual
  devices: "CUDA0"            # ОБЯЗАТЕЛЬНО (R32): без явного устройства движок считает на CPU
  n_gpu_layers: 99            # 99 = все слои на GPU
  # vram_source: nvml         # источник истины по свободной VRAM (R29); memory_free движка не использовать
  reserve_mb: 1024            # не выедать под ноль
  evict_idle_sec: 600         # внешний предохранитель к grace движка
  pause_index_on_query: true  # запрос важнее индексации
  priorities: { chat: 100, embedding: 40, rerank: 30, whisper: 20 }
  # vram_budget_mb: 11000     # опционально; иначе считаем по NVML
  # external_vram_mb: 0       # вычет на чужих потребителей GPU (например, anonymizer_proxy)
llm:
  host: 127.0.0.1
  chat:      { model: "shared:chat",      retention: keep,      n_ctx: 32768 }
  embedding: { model: "shared:embedding", retention: on_demand, n_ctx: 8192 }
  rerank:    { model: "shared:rerank",    retention: on_demand, n_ctx: 8192 }
  whisper:   { model: whisper-large-v3-turbo, retention: on_demand }
  model_policy: fixed          # fixed (по умолчанию): без авто-деградации, только отчёт о нехватке
```

#### 8.6.3. Что из прежнего дизайна отменяется

* **PID-файлы ролей, `probe /props` для проверки владения, `gpu.state.json`/`gpu.lock`/
  `gpu.request.json`, lease-таймауты** — не нужны: состояние ролей и счётчики запросов
  видны через `list_instances()`, а загрузка/выгрузка — это вызовы кластера.
* **llama-server целиком**: остановка/запуск ролей, `data/llama_<role>.pid`, логи по ролям,
  `llm_server.bin`, `--cache-type-k/v`/`-fa`/`--jinja`-аргументы, `ensure_llama_runtime.*`,
  `projects.json` — **удаляются** (решение заказчика: «меньше кода и установки»).
  Файлы GGUF и разбор `shared:<role>` → `models/<role>/current.json` **сохраняются**
  (это пути к моделям, а не бинарники); UI-переключатель чат-модели теперь переписывает
  `current.json` и перезагружает инстанс `chat`.
  ⚠️ **Требование из W0 (SPIKES §14.7):** разрешение `shared:<role>` обязано смотреть в
  **общий рантайм** (`%LOCALAPPDATA%\llama-runtime` / `~/Library/Application Support/llama-runtime`),
  а не в `<project>/models/<role>`: текущий менеджер ролей ищет модель в каталоге проекта и
  падает с «GGUF-модель роли 'chat' не найдена», хотя файл есть в общем рантайме. Воспроизведение
  и следствия (в т.ч. требование к `hds check` показывать «где искали/что нашли») — там же.
* Сигнальные файлы остаются только для управления индексацией (`index.stop`,
  `index.pause`, `index.heartbeat.json`) и для клиентов `llm-host`.

### 8.7. Фасад OpenAI-совместимого HTTP (порты 8010–8012) и режимы thinking

Решение заказчика: **порты сохраняем через фасад**, переключатель
`llm_server.mode: embedded | facade | off`, и внешний ИИ-агент должен подключаться к
чат-модели **с thinking ON**, тогда как MCP использует ту же модель **с thinking OFF**
(разные режимы размышлений на разных потребителей).

| `llm_server.mode` | Что происходит |
|---|---|
| `embedded` | Только внутрипроцессные вызовы кластера; HTTP-портов нет |
| `facade` (по умолчанию) | `llm-host` дополнительно поднимает HTTP: `:8010` — `/v1/chat/completions`, `/v1/models`, `/health`, `/props`; `:8011` — `/v1/embeddings`; `:8012` — `/v1/rerank` (плюс опционально `/v1/audio/transcriptions`) |
| `off` | Ни инстансов, ни портов (HDS работает без LLM: только FTS-поиск) |

**Управление thinking** (поля чат-запроса кластера — `reasoning`, `reasoning_budget`,
`reasoning_format`, см. §8.6.1):

| Кто/как | Маппинг |
|---|---|
| MCP/`ask_my_files` внутри HDS | прямой вызов инстанса `chat` с `reasoning="off"` (движок принудительно ставит `reasoning_budget=0`) — быстрые ответы в таймаут клиента, как сейчас |
| Внешний агент, алиас `model: "chat"` | `reasoning="off"`, `reasoning_budget=0` |
| Внешний агент, алиас `model: "chat-think"` | `reasoning="on"`, `reasoning_budget=-1`, `reasoning_format="none"` (видимые размышления) |
| Тело запроса: `reasoning`, `chat_template_kwargs.enable_thinking`, `think` | прозрачно маппится в те же поля (совместимость с OpenAI-клиентами, которые не знают алиасов) |
| `max_tokens` / `temperature` / `top_p` / `top_k` / `min_p` / `seed` / `repeat_*` / `presence_penalty` / `frequency_penalty` / `dry_*` | соответствующие поля `chat_request` (поддерживаются все) |

Дополнительно: `/v1/models` отдаёт список инстансов (`chat`, `chat-think`, `embedding`,
`rerank`), `/health` и `/props` — совместимость с внешними проверками (сегодняшний
`probe /props` из `hds/llama_server.py` заменяется нашим же ответом). Режим thinking по
умолчанию для фасада задаётся `llm.facade.thinking_default: off|on` (по умолчанию `off` —
чтобы случайный клиент не получал медленные ответы).

Обязательная проверка в спайке W0: что `reasoning="off"` для Qwen3.5 даёт эквивалент
текущего `chat_template_kwargs.enable_thinking=false` (у движка нет jinja-флага), а
`reasoning="on"` действительно показывает размышления внешнему агенту.

## 9. MS Project (.mpp)

**Сейчас**: `hds/extract_static.py` стартует JVM через `jpype`, вызывает
`org.mpxj.reader.UniversalProjectReader`, печатает задачи строками
`имя; начало=…; окончание=…; ресурсы: …`, по 200 строк на сегмент.

**Целевое**: тот же результат, но без `jpype` и без JVM внутри Python-воркера:

1. В репозитории появляется `sidecar/mpp/Main.java` (~50 строк, повторяет текущую логику
   вывода) и собранный `hds-mpp.jar` + mpxj (берётся из Maven Central в CI или кладётся
   в артефакт релиза).
2. Ядро запускает `java -cp mpxj.jar;hds-mpp.jar …Main <файл>` (`;` на Windows, `:` на
   macOS) и получает строки задач; сегменты по 200 строк формируются в ядре — **тот же
   формат**, что сейчас.
3. Поиск JDK — тот же алгоритм, что сейчас: `JAVA_HOME` → `%LOCALAPPDATA%\jdk-21\*`
   (на этой машине есть: `jdk-21.0.12.1+1`) → `/opt/homebrew/opt/openjdk*` →
   `/Library/Java/JavaVirtualMachines/*`. Java не в PATH — это нормально, ищем по путям.
4. Нет Java / нет jar → сегмент-заглушка с прежним смыслом: «Файл MS Project %s. Текст не
   извлечён: установите пакет mpxj (нужна Java 11+)…»
5. Таймаут и убийство процесса — как у любого внешнего вызова (`ffmpeg`), с
   `CREATE_NO_WINDOW` на Windows.

Побочная выгода: `jpype1` (нативный модуль, источник проблем при заморозке) исчезает из
зависимостей воркера.

4. Как только появится Apple Silicon машина (после проекта) — mac-фаза выполняется по

### 10.2. Windows: установка (`setup.ps1`, он же `installers\setup.ps1`)

1. **Снятие MotW** (`Get-ChildItem -Recurse | Unblock-File`) — как сейчас, плюс
   `setup.cmd` с `-ExecutionPolicy Bypass`.
2. **Проверка артефакта**: есть ли `bin\hds.exe`; если нет — понятное сообщение (архив
   исходников = старая установка, см. §10.3).
3. **Системные зависимости через `winget`** (winget есть: 1.29.380): `ffmpeg`
   (`Gyan.FFmpeg`) — автоматически; `Tesseract OCR` (`UB-Mannheim.TesseractOCR`) — по
   согласию (как сейчас); **VC++ Redistributable** — только если сборка не static-CRT (§14).
4. **Проверка воркера**: `sidecar\python.exe sidecar\run.py --self-test` (импорт
   PDF/DOCX/XLSX/PPTX/OCR/pymorphy3 + печать JSON-capabilities). Не работает →
   предложить вариант C (системный Python) с прежней логикой «найди рабочий Python 3.10+
   и понятно поругайся на Store-заглушку».
5. **Миграция настроек**: если рядом старая установка (`config.yaml` и/или `index.db`) —
   сохранить `config.yaml` (с путями и комментариями), `db_path`, `data/` (PID/логи),
   `models/whisper-cpp` (GGML-веса); сохраняется и полезная эвристика текущего
   `setup.ps1` — проверка существования дисков из `config.yaml`.
6. **Рантайм движка (обязателен)** — он же LLM-хост и ASR: если не найден, скачать сборку по
   бэкенду из `engine-manifest.json` (CUDA при NVIDIA, иначе Vulkan), проверить `sha256`,
   выполнить `Unblock-File` по всем DLL/EXE (как `unblock-unsigned-runtime.ps1` в
   `transcribeoffline`). **llama.cpp не устанавливается вообще** (решение заказчика) —
   `ensure_llama_runtime.*` и `llama-server` из установки исключены.
7. **Модели GGUF**: переиспользовать найденные в общем каталоге
   (`%LOCALAPPDATA%\llama-runtime\models\…`) — chat/embedding/rerank; при отсутствии —
   скачать по `llm.*` (§8.6.2); `whisper-large-v3-turbo-GGML.bin` — из общего каталога
   моделей движка (§8.5). UI-переключатель чат-модели работает с `current.json`.
8. **Задачи Планировщика**: `HermesDiskSearchWatch` → `...\bin\hdsw.exe watch`,
   `llm-host` → `...\bin\hdsw.exe llm-host run` (автозапуск), `mcp-http run` — по желанию.
   Старые задачи со `pythonw.exe -m hds.cli watch` **удаляются** (иначе два watcher'а).
9. **Интеграции Hermes/Cline**: `install_hermes.ps1` / `install_cline.ps1` правятся
   минимально: stdio-команда `mcp_start.py` → `bin\hds.exe serve`; URL-вариант
   (`http://127.0.0.1:8787/mcp`) остаётся прежним. После установки —
   `hds.exe mcp-http restart-if-stale`.
10. **Ярлык**, иконка (`assets/icon.ico`); `run_ui.ps1` → `hdsw.exe ui`,
    `run_index.ps1` → `hdsw.exe index`.
11. **Диагностика**: `hds.exe check` + человекочитаемый отчёт (в том числе: найден ли
    рантайм движка, какие инстансы загружены, `memory_free`, режим `llm_server.mode`).
12. **Опциональный smoke-тест**: мини-индекс `test_data` (`-SmokeTest`).

**Обновление** (не первая установка): `hds.exe update --from <zip>` или повторный
`setup.ps1`: graceful-остановка (`index.stop` → ожидание → kill по таймауту), распаковка
в новый каталог `app\<ver>\`, переключение указателя `app\current`, перезапуск задач.
Подмена работающего `hds.exe` на Windows невозможна (файл занят) — поэтому версии в
каталогах + указатель, а не запись «поверх».

### 10.4. macOS: установка (`installers/install_macos.command`) — **не проверено (§10.0)**

   `tessdata` в `/opt/homebrew/share/tessdata` и `/usr/local/share/tessdata` — это лечит
   «Tesseract OCR не найден» при запуске из `.app`/LaunchAgent.
4. **Рантайм движка (Metal, обязателен)** — он же LLM-хост и ASR: скачать

   `xattr -dr com.apple.quarantine` и ad-hoc `codesign` к dylib/бинарникам рантайма.
   Модели GGUF — из общего каталога (`~/Library/Application Support/llama-runtime/models/…`)
   либо скачать; `whisper-large-v3-turbo-GGML` — по §8.5.
5. Приложение «HDS Индексация»: `.app`-обёртка запускает `bin/hdsw watch`; копия в
   `~/Applications` подписывается ad-hoc (как сейчас).
6. LaunchAgent `~/Library/LaunchAgents/local.hds.watch.plist` → `<root>/bin/hdsw watch`
   (`RunAtLoad`, `KeepAlive`) и `local.hds.llmhost.plist` → `<root>/bin/hdsw llm-host run`
   (владелец GPU); отдельный plist для `mcp-http run` при необходимости.
7. Интеграции: `install_hermes_macos.sh` / `install_cline_macos.sh` — правка только
   stdio-команды (как на Windows).
8. Диагностика `bin/hds check`; в выводе — явное «Python пользователю не нужен» и состояние
   инстансов (какие загружены, `memory_free`, режим `llm_server.mode`).
9. **Intel-маки и Linux — вне поддержки** (решение заказчика): артефакт для macOS только
   arm64. Для уже существующих установок на Intel Mac обновление до гибридной версии не
   предусмотрено — они остаются на Python-версии v0.12.0; в README добавляется явная
   строка об этом (вместе с тем, что инструкция `-ngl 0` для Intel остаётся актуальной
   только для старой версии).

### 10.5. Подписи и блокировки (честная позиция)

| ОС | Проблема | Что делаем |
|---|---|---|
| Windows | SmartScreen «Windows protected your PC»; политика RemoteSigned для скриптов | 1) `setup.cmd` + `Unblock-File` (снятие MotW) — как сейчас; 2) **никакого PyInstaller-bootloader'а по умолчанию** (вариант A воркера) — снимает главный источник ложных детекций; 3) опционально — блок «Добавить исключение в Защитник Windows» в инструкции (действие пользователя, осознанно); 4) подпись — только если появится доступный способ: Azure Artifact Signing требует организацию в US/CA/EU/UK, OV/EV — деньги + токен, причём мгновенного доверия SmartScreen они больше **не** дают |
| macOS | Gatekeeper: «повреждён / не удаётся открыть» | 1) `xattr -dr`; 2) ad-hoc `codesign` (бесплатно, всегда); 3) инструкция «ПКМ → Открыть» для запуска вне Терминала; 4) нотаризация — только при наличии Apple Developer Program ($99/год); регистрация недоступна в части регионов → **в план как обязательный шаг не закладываем** |

В README появится честный раздел «Почему Windows/macOS могут показать предупреждение и
что делать»: anti-MotW + ad-hoc подпись **не равно** подпись кода.

### 10.6. Почему нельзя просто «подменить exe»

* Windows: работающий `hds.exe`/`hdsw.exe` нельзя перезаписать → версии в отдельных
  каталогах + указатель `app\current` + перезапуск задач; обновление делает **отдельный**
  процесс (`hds.exe update`), потому что себя обновить нельзя.
* macOS: то же + `launchctl unload/load` для LaunchAgent и переустановка `.app`-обёртки.
* Скрипты установки остаются идемпотентными (как установка рантайма движка): повторный
  запуск ничего не ломает и ничего не перекачивает.

## 13. Память: как измеряем и чего ожидаем

### 13.1. Методика (W0)

`tools/measure_rss.ps1` (Windows) и `tools/measure_rss.sh` (macOS) + замеры W0:

* выбирают процессы по командной строке (`hds.cli watch`, `mcp_start.py`, `ui`, `index`,
  `llama-server`, а после миграции — `hdsw.exe llm-host`);
* **пишут три метрики**, а не две: `WorkingSet`, **`WorkingSetPrivate` (резидентная, основная
  для сравнения)** и `PrivateBytes` (коммит), плюс занятую VRAM (`nvidia-smi`). Это
  обязательное следствие W0: у llama-server chat WS 1,5 ГБ против commit 13,3 ГБ —
  по одной метрике выводы получаются противоположными (`tools/parity/sample_procs.ps1`);
* сценарии: (1) простой с работающим watcher, (2) индексация 500 файлов, (3) транскрипция
  1 видео, (4) первый поисковый запрос. Реализация — `tools/parity/measure_run.py`
  (изолированные конфиг и БД: боевой индекс не затрагивается) и `measure_live.py`;
* **на момент W0 остались непройденными (2) и (3)**: их блокирует фоновая индекс-сессия
  (свежий `index.heartbeat.json` → `index_running() == True`, см. SPIKES §11), плюс дефицит
  VRAM. Запуск после решения по сессии (`python -m hds.cli stop`) и окна свободной VRAM.
* **macOS-замеры отложены** (§10.0): `tools/measure_rss.sh` и Metal-проба
  (`recommendedMaxWorkingSetSize`/`currentAllocatedSize`) реализуются, но не исполняются до
  появления Apple Silicon машины; критерий «рост GPU-аллокации при загрузке инстанса» входит
  в постпроектный чек-лист, а не в DoD волны.

### Проба № 2. Существующая `index.db` из Rust (главный риск плана)

Проект-пробник:

```toml
[dependencies]
rusqlite = { version = "0.37", features = ["bundled", "load_extension"] }
sqlite-vec = "0.1.9"
```

```rust
unsafe {
    sqlite3_auto_extension(Some(std::mem::transmute(
        sqlite_vec::sqlite3_vec_init as *const ())));
}
```

Вывод:

```
vec_version=v0.1.9
vec0_ok rows=1
db files=71993 chunks=612066 fts_match=4392 images_vec=33596 vec_dim=1024
knn_rows=3
FTS_AND_KNN_ON_REAL_DB_OK
```

Выводы:

1. `sqlite-vec` 0.1.9 регистрируется в `rusqlite` **статически** через
   `sqlite3_auto_extension` + `transmute` (как в собственном тесте крейта). Прямой вызов
   `sqlite_vec::sqlite3_vec_init()` **не работает** — модуль `vec0` не регистрируется
   («no such module: vec0»); эту ловушку нужно зафиксировать комментарием в коде.
2. FTS5 доступен в `rusqlite` со стандартной фичей `bundled` (SQLite 3.50.2).
3. Реальная БД (4,9 ГБ, активный WAL, БД используется работающим watcher'ом) **читается
   из Rust read-only**: работают и FTS5-запрос, и KNN-запрос с JOIN к `chunks`/`files`.
4. Версия расширения в Python-окружении — тоже **0.1.9**, формат `vec0` совпадает;
   переиндексация для чтения из Rust не нужна.

Ограничение пробы: проверены чтение реальной БД и запись в память; запись в боевую БД
(индексация) намеренно не проверялась — нельзя портить рабочий индекс.

## Приложение Б. Перечень контрактов, которые нельзя сломать

Сводный чек-лист для code review каждой волны (всё — из реального кода, не из
предположений).

**База данных**

1. Схема и индексы `files/chunks/chunks_fts/chunks_vec/images_vec/meta` — без изменений.
2. `PRAGMA journal_mode=WAL`, `synchronous=NORMAL`, `foreign_keys=ON`, `busy_timeout=30000`.
3. `meta.vec_dim`; проба размерности через `SAVEPOINT`/`ROLLBACK` **только** при
   расхождении; `DROP TABLE chunks_vec` + пересоздание — лишь при реальном несовпадении.
4. `images_vec` фиксированной размерности 512; запись через `DELETE` + `INSERT` (vec0 не
   поддерживает `INSERT OR REPLACE`), конфликты игнорируются.
5. `chunk_count` и `indexed_at` заполняются при `status='indexed'`; бэкфилл `indexed_at`
   для старых записей (`mtime + 10`).
6. Удаление данных файла: сначала `chunks_fts`/`chunks_vec` по каждому `chunk_id`, затем
   `chunks`, затем `images_vec` по `files.id` (таблицы может не быть — не падать).

**Индексация**

7. `content_hash` — Blake2b-128 (`digest_size=16`) от `str(size)` + первые/последние 256 КБ.
8. Пропуск неизменённых: `status='indexed'`, `size` совпал, `|mtime − сохранённый| < 2 с`.
9. Переезд по хэшу засчитывается, только если старого пути на диске нет.
10. `~$*` не индексируются; `exclude_dirs` — по имени компонента, `exclude_paths` — по
    границе компонента пути; регистр не важен; `\` и `/` эквивалентны.
11. Лимиты: `max_file_mb` 200 (обычные), `max_media_mb` 2500 (медиа), `max_chunks` 3000
    (обрезка с предупреждением), `--limit`.
12. Атомарность: файл либо полностью переиндексирован, либо остаётся `new`/`error`.
13. `prune` с защитой >20 % и требованием `--confirm-delete`.
14. `index.heartbeat.json` пишется во время прогона и удаляется по завершении;
    `index.stop`/`index.pause` — управление; Ctrl+C сохраняет обработанное.

**Поиск**

15. FTS: лемматизация текста и запроса одним и тем же алгоритмом; AND→OR; префикс
    последнего токена; экранирование кавычек; `bm25`; pushdown `kinds` в SQL.
16. KNN: `MATCH` + `k =` + `ORDER BY distance`, JOIN к `chunks`/`files`, фильтр `kinds`.
17. RRF: сумма `вес / (rrf_k + ранг)` по веткам (fts/vec/clip), `rrf_k` = 60, веса из
    `search.*`, округление score до 5 знаков.
18. CLIP-ветка: `rowid = files.id`, привязка к первому (минимальному id) чанку файла.
19. Сниппет: окно вокруг первого вхождения токена (включая леммы), выравнивание по
    границам предложений, `search.snippet_chars` по умолчанию 500.
20. `format_location`: путь + «, стр. N» (0 — валидная страница) + «время HH:MM:SS–HH:MM:SS».
21. Деградация: без эмбеддингов — только FTS; без CLIP — без CLIP-ветки; без реранкера —
    без реранка; предупреждения в stderr, а не исключения.

**RAG**

22. Системный промпт и требование цитат `[N]`; `max_tokens` 600; `temperature` из конфига;
    `thinking=off` → `chat_template_kwargs.enable_thinking=false`; таймаут 240 с;

24. UI `:8765`: статический `assets/ui.html` без кэша + 20 эндпоинтов `/api/*`;
