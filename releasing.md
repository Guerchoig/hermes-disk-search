# Правила выпуска релиза (releasing.md)

## Когда выпускать релиз

- после завершения функционального блока (фичи) и/или исправления существенных ошибок;
- регрессионные тесты зелёные (`python -m unittest discover -s tests`);
- `check` на реальной машине без критических проблем (`.venv\Scripts\python.exe -m hds.cli check`);
- ручная проверка сценария «спроси в чате Hermes → ответ со ссылками».

## Версионирование

SemVer: `vMAJOR.MINOR.PATCH`.
- **PATCH** — правки ошибок, не меняющие поведение;
- **MINOR** — новые фичи (UI, новые форматы, инструменты MCP);
- **MAJOR** — несовместимые изменения (схема БД без миграции, изменение API MCP, требований окружения).

Тег = имя релиза (`v0.2.0`). Ветка для выпуска — `main`.

## Порядок выпуска

1. Убедиться, что `main` зелёный и актуален: `git status` чист, `git push` выполнен.
   Архив релиза собирается через `git archive HEAD`, то есть из **закоммиченного**
   состояния: если установщик (`setup.ps1`, mac-инсталлятор) вызывает файлы,
   а они untracked (`git status` показывает `??`) — они не попадут в релиз и
   установка упадёт. Всё, на что ссылаются скрипты установки, должно быть
   закоммичено до запуска workflow.
2. Прогнать тесты локально:
   ```powershell
   .\.venv\Scripts\python.exe -m unittest discover -s tests
   ```
3. Создать файл заметок `RELEASE_NOTES_<версия>.md` в корне (что нового, исправления,
   требования к обновлению — например «требуется index --full после смены модели»).
4. Запустить workflow:
   - GitHub → Actions → **Release** → Run workflow → ввести версию (например `v0.2.0`) → Run.
   - Или CLI:
     ```powershell
     gh workflow run release.yml -f version=v0.2.0
     gh run watch   # следить за прогрессом
     ```
5. Workflow сам:
   - прогонит компиляцию и **регрессионные тесты** (job `test`, Windows; job
     `test-macos`, macOS/Apple Silicon — проверка совместимости без CUDA);
   - при успехе — соберёт **бинарные ассеты** (Rust `hds`/`hds_mcp`/`llm_host` в zip +
     sha256), **рантайм движка** (`hds-engine-runtime-*-windows-x64-cuda.zip`, sha256 по
     манифесту) и архивы исходников (Windows/macOS), создаст релиз с заметками
     (`RELEASE_NOTES_<версия>.md`, если существует, иначе авто-заметки).

   Прежние релизы и теги **не удаляются** — релизы накапливаются (policy:
   история версий сохраняется, у пользователей остаётся доступ к старым архивам).
   Поэтому выпускать версию с уже существующим тегом нельзя: `gh release create`
   упадёт на существующем теге — сначала удалите конкретный релиз/тег вручную
   (`gh release delete <тег> --yes --cleanup-tag`) и только потом перезапускайте.

## После выпуска

- Проверить страницу релиза: ассеты на месте, заметки корректны.
- Обновить `__version__` в `hds/__init__.py` (сделать это **до** запуска workflow).
- Протестировать установку с нуля по README на чистой машине/в виртуале при
  существенных изменениях (инсталляторы, схемы конфига).

## Правила good-practice

- **Не выпускать релиз с красными тестами** — job `test` блокирует выпуск автоматически.
- Заметки релиза пишутся на русском, включают: новые фичи, исправления, требования
  к обновлению (например «запустите `index --full` после обновления»).
- Ассеты релиза:
  * **бинарный Windows-пакет** `hds-<версия>-windows-x64.zip` (+ `.sha256.txt`) —
    `bin\` (Rust) + `installers\` + `runtime-manifests\` + `sidecar\` (портативный
    Python-воркер: CPython + deps + модули извлечения, джоба `build-sidecar`) +
    `assets\` + скрипты; ставится через `setup.cmd` (он же `setup.ps1`);
  * **рантайм движка** `hds-engine-runtime-windows-x64-cuda.zip` (LLM-хост + ASR;
    вместо llama.cpp, который больше не ставится);
  * **архивы исходников** `hermes-disk-search-<версия>-windows.zip` и
    `-macos.zip` (Python-эталон/legacy; mac собирается через `git archive` на macOS —
    `Compress-Archive` для него непригоден, теряет бит исполнения).
  Ad-hoc подпись копии mac-приложения выполняет инсталлятор на целевой машине
  (codesign входит в macOS, подписи нельзя закоммитить в архив).
- ONNX-модели CLIP в релиз не входят (≈850 МБ) — публикуются отдельным тегом
  `clip-onnx-v1` (`installers\publish_clip_models.ps1`), скачиваются установщиком
  (`installers\fetch_clip_models.ps1` по `runtime-manifests\clip-manifest.json`).
- Установка/обновление на Windows: `installers\install_app_version.ps1` раскладывает сборку в
  `app\<версия>\` (+ junction-ы общих `data\`/`models\`, перенос `config.yaml`, указатель
  `app\current`); обновление — `installers\update.ps1` (отдельный процесс: stop → install →
  switch → start), прошлые версии сохраняются (откат — вернуть `app\current`).
- Workflow **никогда не удаляет существующие релизы и теги** (раньше он стирал
  все прежние релизы при каждом выпуске — это поведение убрано). Следствие:
  перед повторным выпуском той же версии удалите конкретный релиз и его тег
  вручную, иначе `gh release create` упадёт на существующем теге.
- Откат: git revert коммитов, повторный запуск workflow с новым PATCH.
