## 1. Итог

Этап выполнен в основном добротно: все шесть треков (T0–T5) закрыты по одному коммиту на
шаг, **десктоп-профиль действительно не изменён**, тесты/fmt/clippy зелёные, и главное —
**заявленное в журнале подтверждается рантаймом** (см. §2). Дефекты M2, взятые в T0
(F1/F3/F4) и F2/F8 (в T4), исправлены по-настоящему.

Но **план выполнен не полностью** и есть хвосты, которые нельзя терять:

1. **`token_issue` не пишется нигде** (план §3.2 требует `token_issue`/`token_revoke`) — F1.
2. **T3/T4 не покрыты автотестами** (план §2 обещал «юнит + сокет», есть только юниты
   `hds-core`); живой прогон был, регресс-защиты нет — F5.
3. **`admin_op` пишет `status: 200` всегда** и до маршрутизации → аудит врёт — F2.
4. **`503` (max_conns) и часть `413` не доходят до клиента** — соединение закрывается с
   непрочитанными данными, клиент видит `connection reset` — F4.
5. **Хвосты M2 из прошлого ревью F5–F10 не закрыты** (PID-файлы, дубли путей, пароль в
   аргументах, снятие задачи транскрибации, плейст macOS, `access_path`) — §5.
6. **Пункт приёмки «наружу только через прокси»** обеспечивается только конфигом и
   **не проверяется кодом** — F8; полный внешний HTTPS-обход не проверен (нужен домен) —
   это честно задокументировано в §8a плана.

Критичных блокеров нет: ни одной уязвимости уровня «доступ без токена» или «утечка между
проектами» в M3 не найдено. Итоговая оценка — **принять с замечаниями**; F1–F5 и хвосты M2
уходят в трек **T0 этапа M4** (`PLAN_M4_CONCURRENCY_SLA.md`).

## 3. Находки

### F1 — [Баг/контракт] Событие `token_issue` не пишется никогда

План §3.2 (и его же §4 T2) требует событий `login_ok`/`login_fail`, **`token_issue`**/
`token_revoke`, `tool_call`, `admin_op`, `unauthorized`. Поиск по `crates/` даёт
`"token_issue"` **только в doc-комментарии** `crates/hds-core/src/audit.rs:45`; в коде
выдаётся лишь `token_revoke` (`crates/hds-cli/src/cmd/auth.rs:347`). При этом логин
**выдаёт** токен (`hds-mcp::auth::login` → `new_token` + `save_at`), но пишет только
`login_ok` (`crates/hds-mcp/src/http.rs:193`). В README/STATUS список событий тоже без
`token_issue` — то есть расхождение «план ↔ реализация ↔ док», и в аудите нет следа
выдачи токена (важно: именно токены — единица доступа).

Рекомендация: либо писать `token_issue` в `auth::login`/`handle_login` (с `user` и
префиксом хэша, без самого токена), либо явно вычеркнуть `token_issue` из плана и
документации. Первое полезнее: сейчас по аудиту нельзя ответить «когда этому
пользователю выдали токен».

### F2 — [Баг] `admin_op` в UI: статус всегда `200` и запись до маршрутизации

`crates/hds-ui/src/lib.rs:1404-1426`: событие пишется **до** `match` маршрутов, поле
`status: 200` — литерал. Живая проверка: `POST /api/does-not-exist` с админ-токеном →
ответ **404**, а в аудите — `{"event":"admin_op","path":"/api/does-not-exist","status":200}`.
То есть аудит административных операций систематически завышает результат и фиксирует
даже несуществующие маршруты. Для разбора инцидентов («кто менял доступы и что
получилось») это ложные данные.

Рекомендация: писать `admin_op` **после** маршрута, с фактическим статусом ответа
(обернуть ветку POST `/api/*`), и/или ограничить список аудируемых путей
(`/api/access/*`, `/api/index*`, `/api/watch*`, `/api/llm-*`, `/api/config/*`).

### F3 — [Несогласованность] Аудит `unauthorized` в UI без `method`/`path`/`ms`

`crates/hds-ui/src/lib.rs:1359-1372`: `method: "-"`, `path: "-"`, `ms: 0` — в UI-гейте нет
доступа к запросу. В MCP те же события пишутся с реальными `method`/`path`
(`crates/hds-mcp/src/http.rs:89-103`). Живая проверка подтверждает: в одном файле
соседствуют `{"event":"unauthorized","method":"POST","path":"/mcp"}` и
`{"event":"unauthorized","method":"-","path":"-","ip":"203.0.113.7"}`.

Рекомендация: прокинуть `method`/`path` в `ui_auth_gate` (или вызывать аудит из
`route_with_access`, где они уже есть) — тогда по логу видно, что именно пытались открыть
(`/api/access/users` vs `/`).

### F4 — [Риск/доставка] `503` (и часть `413`) не доходят до клиента: соединение рвётся

Ветки «сверх лимита» отвечают, **не читая** запрос: `max_conns` — `crates/hds-mcp/src/http.rs:389-401`
(и `crates/hds-ui/src/lib.rs:1785-1797`), `413` — после чтения только заголовков. Затем
`TcpStream` закрывается, а в приёмном буфере сокета остаются непрочитанные данные →
ОС отправляет `RST` и отбрасывает уже поставленный ответ. Живые замеры (сырой HTTP):

* `max_conns: 1` + занятый слот → клиент получает **обрыв соединения без единого байта**
  (не `503`/`Retry-After`), после освобождения слота — снова `200`;
* `POST` телом 2 КиБ при лимите 1 КиБ: у MCP ответ `413` дошёл (тело успело попасть в первый
  `read`), у UI — обрыв (тело ещё в буфере) — то есть **поведение недетерминированное**.

Практическое следствие: вместо описанного в README «короткого 503 / 413» клиент получает
сброс (Cline/curl покажут `connection reset`), а «безопасный отказ» перестаёт быть
диагностируемым.

Рекомендация: перед закрытием дочитать (и выбросить) запрос с потолком по времени/размеру
либо `shutdown(Write)` с вычитыванием входа до EOF/таймаута; закрепить сокет-тестами (F5).

### F5 — [Тесты] T3 (rate-limit) и T4 (hardening) не покрыты сокет-тестами

План §2 («Входит: Тесты (юнит + сокет)») и §5 (приёмка: проверка лимитов) требуют
проверки на живом сокете; в M2 такой тест (`ui_auth_socket_parses_authorization`) был и
дефект поймал. В M3 коммиты `f1a7dad` (T3) и `55f4d24` (T4) **не добавляют ни одного
тестового файла**; поиск по `crates/*/tests/*.rs` не находит ни `413`, ни `429`, ни
`Retry-After`, ни `forwarded`. Покрытие — только юниты `hds-core` (`net.rs`, `ratelimit.rs`),
то есть «429/413/503 на реальном HTTP» держится на ручном прогоне и легко отвалится при
следующей правке.

Рекомендация (в T0 M4): сокет-тесты по образцу `ui_auth.rs`/`ui_core.rs` — bind порта `0`,
сырой HTTP: (a) `429` + `Retry-After` на MCP и UI, (b) `413` при теле сверх лимита,
(c) `503` при `max_conns: 1`, (d) `client_ip` из XFF при `trusted_proxy: true/false`,
(e) `unauthorized`-аудит MCP/UI. Тесты на (b)/(c) обязаны ловить F4.

### F6 — [Хрупкость] «Тяжёлый запрос» на MCP определяется подстрокой тела

`crates/hds-mcp/src/http.rs:499`:
```rust
let heavy = b.contains("tools/call") && b.contains("ask_my_files");
```
Тело запроса уже разбирается как JSON в `route` (`serde_json::from_str`), а здесь оно
ищется подстрокой: ложное срабатывание возможно у любого запроса, в котором строка
`ask_my_files` встречается как данные (например, `search_local_files` с таким текстом
вопроса), и при ином форматировании. Ложный `heavy` съедает слот `max_inflight` и вернёт
`429` «too many concurrent heavy requests» на лёгкий запрос.

Рекомендация: определять тяжесть по разобранному JSON-RPC (`method == "tools/call"` и
`params.name == "ask_my_files"`), переиспользуя разбор из `route`, а не подстроки.

### F7 — [Риск] `/health` под rate-limit: живой инстанс можно принять за «чужой сервис»

Лимит применяется в `serve_request` ко **всем** путям, включая `GET /health`
(`crates/hds-mcp/src/http.rs:485-496`). Проба менеджера
(`crates/hds-cli/src/cmd/mcp_http.rs:59-67`) на любой не-2xx ответ возвращает `STATE_FOREIGN`;
тогда UI/CLI скажут «порт занят чужим сервисом» и откажутся стартовать **свой** живой
инстанс (`start` вернёт 1, в UI карточка покажет чужой сервис). Воспроизводимо, если
локальный IP-бакет исчерпан (много локальных запросов без токена, частый мониторинг
`hds mcp-http status`). Ломается ровно та диагностика, ради которой `/health` и делался.

Рекомендация: исключить `/health` из лимитов (или считать `429` от нашего приложения в
`probe` как `STATE_MCP`).

### F8 — [Приёмка] «Наружу только через прокси» не проверяется, а только подразумевается

Пункт приёмки §5 («прямой запрос к `:8787`/`:8765` снаружи невозможен; фасад не
опубликован») обеспечивается **только значениями `ui.host`/`mcp_http.host` в конфиге**:
`hds ui --host 0.0.0.0` (или `ui.host: 0.0.0.0`) публикует UI напрямую, и `hds check` об
этом не предупреждает; то же для MCP. Комбинация «слушаем `0.0.0.0` + `trusted_proxy: true`»
(подделка IP и обход IP-лимитов) не диагностируется вообще.

Рекомендация: пункт «периметр» в `hds check`/`/api/diagnostics`: host не loopback →
предупреждение с подсказкой; `trusted_proxy: true` при не-loopback host → явное
предупреждение «IP подделывается»; показать фактическое состояние `rate_limit`/`trusted_proxy`
(сейчас в диагностике есть только аудит).

### F9 — [Расхождение с §3.1] `Host` не читается, хотя объявлен в контракте

План §3.1: «`X-Forwarded-For`/`X-Forwarded-Proto`/`Host` **читаются** в `read_request` обоих
серверов». Фактически `ReqHead`/`ReqHeaders` содержат только `authorization`,
`x_forwarded_for`, `x_forwarded_proto` (`crates/hds-mcp/src/http.rs:220-224`,
`crates/hds-ui/src/lib.rs:163-177`) — `Host` не читается. Практического применения сейчас
нет (абсолютные ссылки UI строятся из `ui.host:port`), поэтому правильнее **поправить
формулировку плана** (либо прочитать `Host` вместе с W8/W10), чем держать пункт «[x]» без
реализации.

### F10 — [Мелочи]

* **F10.1.** `/health` отдаёт `version` (`{"version":"0.1.0"}` — версия крейта `hds-mcp`, не
  продукта), хотя README §«Hardening» обещает «без внутренних путей/**версий**». Для
  опознания инстанса хватает `app`; версию убрать или отдавать только локально/авторизованно.
* **F10.2.** На `429` есть `X-RateLimit-Limit`, но нет `X-RateLimit-Remaining`/`-Reset`;
  `503` шлёт жёсткий `Retry-After: 2`.
* **F10.3.** Ключ лимитов — **токен**, не пользователь: у пользователя с двумя токенами
  квота удваивается (`max_inflight` тоже пер-токен). Для квот W3 это надо менять осознанно
  (см. `PLAN_M4_CONCURRENCY_SLA.md`, T4).
* **F10.4.** `tool_call` не пишется при `access.enabled: false`, даже если `audit.enabled: true`
  (`crates/hds-mcp/src/http.rs:112-120`: `tool` вычисляется только под `env.enabled`) —
  десктоп с включённым аудитом «не видит» вызовы инструментов.
* **F10.5.** 404-ответы эхоят запрошенный путь (`{"error":"not found","path":…}`) — пользы
  нет, безопаснее не эхоить.
* **F10.6.** В `read_request` обоих серверов нет read-timeout на сокете: «медленный» клиент
  держит поток (и слот `max_conns`) бесконечно; стоит выставить таймаут чтения запроса.
