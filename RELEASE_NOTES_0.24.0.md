# hermes-disk-search 0.24.0 — база меток v2 и анонимная зона (фаза A1)

**Дата:** 17.11.2026 · **База:** 0.23.1 · **Ветка:** `agent-privacy-zone`

> Первая фаза «ИИ-агент в анонимной зоне», где меняется продуктовый код
> анонимизации. Главное для пользователя: **база меток создаётся заново**
> (старая переименовывается в `.bak`), а карточка и `hds anon` работают как
> раньше — метки уровня 0 остались прежнего вида.

## Что нового

1. **База меток v2 — одна база, два уровня** (`sidecar/hds_anonymize/vault.py`,
   схема ровно TR-1.2). Уровень 0 — сущности и исходные значения (их видят
   карточка «Анонимизация» и `hds anon`); уровень 1 — метки проекта, номера
   которых не выводятся из глобальных и не связывают проекты между собой.
   «Объединить метки» оставляет у младших меток псевдонимы, поэтому уже
   выпущенные файлы продолжают деанонимизироваться.
2. **Морфология** (`morph.py`): словоформы склеиваются по `norm_key`
   («Иванову Ивану Ивановичу» = «Иванов Иван Иванович»), порождаются падежи,
   метка получает суффикс `[PERSON_3|дат]` — только при однозначном разборе,
   иначе без суффикса и с пометкой «проверить» (в A0 «в лоб» — 19,7 % форм).
   В именах файлов суффикса нет (символ `|` в Windows запрещён).
3. **`keep_terms` (D19)** — список «не анонимизировать»: согласованный с владельцем
   состав продуктов 1С (1С:БП/БП, 1С:ЗУП/ЗУП, 1С:УТ/УТ, 1С:УНФ/УНФ, 1С:КА/КА,
   1С:ERP/ЕРП, 1С:УПП, 1С:ДО/ДО, 1С:Документооборот, 1С:УХ, 1С:ERP УХ,
   1С:Розница/РТ, 1С:WMS, 1С:TMS, 1С:ТОИР, 1С:ИТС, 1С:ЭДО, 1С:БСП,
   1С:Fresh/Фреш), прочие продукты проекта, термины и коды `REQ-…` (`re:`-шаблон).
   Стартовый список встроен; файл `sidecar/hds_anonymize/keep_terms.example.yaml`
   расширяет его без правки кода (`--keep-terms`, `hds anon keep add`). Префикс
   `cs:` включает регистрозависимое сравнение (`ДО` ≠ «до», `КА` ≠ «ка»);
   компоненты составных названий (`ERP`, `ЗУП`) тоже «свои» — NER режет их на части.
4. **Режим `mode: "agent"`** в файловых актах (TR-7.4): метки проекта с
   падежными суффиксами, метаданные вычищаются (DOCX и XLSX: автор, последний
   редактор, заголовок, описание), в свойства файла пишется маркер
   `hds-agent/<P>/<artifact_id>`, **оригинал не меняется** (в т.ч. исправление
   «слипшихся» ФИО — только в образе). Картинки тела DOCX (абзацы и таблицы) и
   картинки листов XLSX заменяются метками `[IMAGE_n]`, байты изображений и их
   связи вымываются из пакета; `agent.images: keep` оставляет их (не рекомендуется).
5. **Текстовые образы `pdf`/`pptx`/`mpp` (D18)**: `hds_extract` извлекает текст,
   `anonymize_text` ставит метки проекта, результат — `<имя>.<ext>.md` с
   разметкой страниц/слайдов. Образ только для чтения.
6. **Office-инструменты (TR-3.5)**: `office_read` (абзацы/таблицы/листы/слайды),
   `office_edit` (`replace_text`, `set_cell`, `add_row`, `add_column`,
   `insert_paragraph`, `delete_paragraph`; формулы и форматы XLSX сохраняются),
   `office_create` (docx из markdown, xlsx из таблиц, pptx из слайдов).
7. **Новые RPC воркера**: `anonymize_text`, `text_image`, `label_for_value`,
   `vault_snapshot`, `vault_rev`, `merge_entities`, `vault_drop_project`,
   `keep_terms`, `office_*`; файловые акты принимают `project_id` и `mode`.
   `hello.capabilities` перечисляет их и сообщает `schema_version: 2`.
8. **CLI**: `hds anon agent`, `text-image`, `snapshot`, `keep`, `merge`;
   `deanon --project P` подставляет формы по падежным суффиксам.

## Ломающие изменения

* **Старая база меток не переносится** (D4, TR-1.3). При первом запуске файл
  схемы v1 переименовывается в `anonymize.db.v1-<YYYYMMDD-HHMMSS>.bak` и
  создаётся пустая база v2. Метки не мигрируют: файлы, анонимизированные
  0.23.x, этой версией **не деанонимизируются** — держите `.bak`, если пары
  нужны.
* `mapping_store.py` удалён; доступ к базе — только через `vault.py` (TR-1.1).
  Внутренние вызовы `MappingStore` заменены; внешние RPC сохранены.

## Фаза A2 — индекс и `disk-search` по анонимной зоне (18.11.2026)

Поиск и индекс переключаются на анонимную зону целиком (D9): отдельный корень,
проектные токены, фильтр по проекту на маршруте агента и предупреждение об
отставании индекса.

1. **Корень индекса = `agent.root`** (TR-4.1). При `agent.enabled: true` индексатор
   и служба слежения **игнорируют** `index.roots` и обходят только
   `<agent.root>\P<NNNN>\workspace`; проект файла — имя каталога (`P0001`), а не
   имя папки проекта. Служебные `agent-config`, `agent-state`, `.hds-agent` и
   `_conflicts` исключены неявно (их нет ни в ETA, ни в предупреждении об
   отставании). Явные `--roots` в этом режиме игнорируются с предупреждением.
   Страница настроек показывает «корни заданы агентом», поле и кнопка сохранения
   заблокированы, `POST /api/roots/save` отвечает `409`.
2. **`hds agent init`** (TR-4.2): останавливает `hds watch` (сигнал `index.stop` и
   ожидание снятия `watch.lock`, до 60 с), удаляет `index.db` вместе с
   `-wal`/`-shm` и выход прежней карточки анонимизации (`anonymize.output_dir`),
   создаёт пустую базу и строит индекс заново. Команда идемпотентна, удаляемое
   перечисляет до удаления, без `--yes` спрашивает подтверждение, а в
   неинтерактивном запуске отказывается. Флаги: `--root DIR` (подмена
   `agent.root` без записи в файл) и `--no-index`.
3. **Маршрут агента `POST <mcp>/agent/<P>`** (TR-4.3, TR-4.4): токен проекта
   (хэш sha256 в `data\agent\secrets.json`, выдаёт `hds agent token <P>`, plain
   печатается один раз; без `--ttl-days` — бессрочный). Неверный, просроченный
   токен или чужой проект → `401`; при `agent.enabled: false` маршрута нет
   (`404`). Контекст запроса **всегда** `projects = [P]` — независимо от
   `access.enabled`, поэтому FTS, векторы и CLIP фильтруются по своему проекту
   (инвариант I5). На маршруте публикуются только `search_local_files` и
   `index_status`; `ask_my_files`, `start_indexing`, `stop_indexing`,
   `reindex_path` недоступны (вызов → `unknown tool`). Инструкции `initialize`
   на этом маршруте объясняют метки и предупреждение о неполной выдаче.
4. **Метки в FTS — одно слово** (TR-4.6). Единый разбор метки вынесен в
   `hds_core::labels` (его же переэкспортирует `hds_anonymize::protocol` — второй
   регулярки нет). При индексации и при перестройке FTS (`hds reindex-fts`) метка
   заменяется токеном `xperson3x`, а лемматизатору отдаётся текст без меток;
   текст фрагмента и векторная ветка получают исходный текст с меткой как есть.
   Запрос нормализуется так же, поэтому `[PERSON_3]`, `[PERSON_3|дат]` и
   `[PERSON_3|род,мн]` — один токен, а `[PERSON_30]` — другой. Слово «person» в
   запросе фрагменты с метками больше не находит.
5. **Отставание индекса** (TR-4.7). Новый `hds_index::lag::project_lag` считает по
   проекту: всего файлов, проиндексировано, в очереди, ошибки и признак
   первичного построения. Критерий «проиндексирован» — запись в `files` с тем же
   `content_hash` (blake2b-16, как у конвейера) и успешным статусом, с быстрым
   путём «размер совпал и mtime не старше 2 с» (критерий `unchanged`).
   `index_status` на маршруте агента отвечает JSON по проекту, а
   `search_local_files` добавляет к выдаче предупреждение «N файлов проекта ещё не
   проиндексированы…» со списком до 10 недавно изменённых файлов.

**Что осталось за пределами A2:** реестр артефактов с полем
`indexed: pending|done|error` (TR-7.2) и панель «Файлы проекта» — фаза A4/A5;
в A2 отставание считается по файловой системе и `index.db` (вопрос В-7).

### Решения владельца по A2 (18.11.2026)

| # | Вопрос | Решение |
|---|---|---|
| В-7 | как считать `pending` до появления реестра TR-7.2 | **подтверждено**: в A2 — по ФС + `index.db` (критерий `content_hash`), поле `indexed: pending\|done\|error` и переключение `index_status` на реестр — в A4 |
| В-8 | срок жизни токена проекта | **бессрочный по умолчанию** (`expires: 0`); `--ttl-days` остаётся как явная опция |
| В-11 | переменная `HDS_AGENT_SECRETS` | **остаётся продуктовой** (как `HDS_CONFIG`/`HDS_ROOT`), а не только тестовой |
