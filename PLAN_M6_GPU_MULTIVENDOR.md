## 2. Границы M6

**Входит:** раскладка ролей по картам (`gpu.devices` + `llm_server.<role>.device`),
спайк «CUDA+Vulkan в одном `llm-host`» с честным фолбэком, VRAM-бюджет и вытеснение
**по каждой карте**, пресеты/автодетект раскладки, `hds check` с картами и ролями,
рантайм-приёмка стендом, доклад.

**Не входит:** балансировка одной модели по нескольким картам сверх того, что даёт
`manual_devices_csv` (split) — проверяем, но не развиваем; AMD-smi как отдельная
зависимость (остаёмся на DXGI/движке); внешний чат (сделан в M5); анонимизация (W9);
реальная проверка Apple Silicon — **нет железа** (только подготовка/доклад, хвост).

## 3. Технические решения (контракты)

### 3.1. Конфиг раскладки (по §8.1, обратная совместимость обязательна)
```yaml
gpu:
  device_index: 1            # КОМПАТ: «одна карта на все роли» (как сейчас)
  devices:                   # НОВОЕ: раскладка по картам (сильнее device_index)
    - { index: 1, roles: [chat] }               # NVIDIA (CUDA)
    - { index: 2, roles: [embedding, rerank] }  # AMD (Vulkan)
  # llm_server.<role>.device: 2   — альтернативная форма: карта у роли
```
- `index` — **наш** индекс (`device.rs`: 0 = CPU, 1 = первый ускоритель движка) —
  тот же смысл, что у `device_index`; резолв в `manual_devices_csv` — существующий.
- Приоритет: `devices[].roles` / `llm_server.<role>.device` **сильнее** `gpu.device_index`;
  роли, которых нет ни там, ни там, берут `device_index`.
- Валидация (fail-fast с числами, не молча): индекс вне диапазона найденных ускорителей;
  одна роль на двух картах; неизвестная роль в `roles`; пустой `devices` при заданном
  `device_index` (>0) — warn, поведение прежнее.
### 3.2. Резолв раскладки (реестр/хост)
- `plan_role` получает устройство роли из раскладки: `DeviceSelection::Csv(bridge_index)`
  вместо общего `selection_from_config_index(config.gpu.device_index, …)`.
- Планировщик печатает backend карты роли (`CUDA`/`Vulkan`/`CPU`) в `llm-host status`
  и в `PlannedInstance::summary` — это ключевое свидетельство приёмки.
- Недоступная/несуществующая карта у роли — **явная ошибка роли** (`RolePlan::Failed`
  с числами: «карта 2 не найдена, найдено 1 ускоритель: …»), не молчаливый фолбэк на CPU
  (`allow_cpu=false` сохраняем для GPU-ролей).

### 3.3. VRAM по картам (бюджет и вытеснение)
- Бюджет, fit-гейт и вытеснение считаются **для карты роли** (`bridge_device_index` роли),
  а не для «целевого» устройства: `bind_device_probes` уже даёт пробу на карту, в т.ч. через
  DXGI (AMD/Intel); нет пробы — «нет замера» (как сейчас), решение по числам движка.
- `reserve_mb` / `external_vram_mb` применяются к каждой карте (документируем явно).
- Вытеснение — в пределах карты: роли другой карты не вытесняются чужой нехваткой VRAM.
- На одной карте арифметика должна совпасть с текущей (проверяем замером до/после).

### 3.4. Пресеты и автодетект (W4, без магии)
- Пресеты: `1 мощная NVIDIA` (все роли на карту 1); `AMD+NVIDIA` (chat → карта с CUDA,
  embedding/rerank → Vulkan-карта); `Apple Silicon` (все роли Metal) — для macOS.
- Автодетект (по умолчанию **выключен**): предлагает раскладку по бэкенду/свободной VRAM,
  печатает её и требует явного включения; любая раскладка видна в `hds check` и логе.

## 4. Треки

### T0. Спайк «CUDA+Vulkan в одном `llm-host`» — 1,5–2 дн (первый шаг!)
- [ ] Проверить, перечисляет ли наш движок Vulkan-устройства: `llm_host devices` на текущей
      сборке (`-Backend cuda`); если нет — собрать/получить сборку с Vulkan
      (`build_bridge.ps1 -Backend vulkan` либо backend-DL) в копии рантайма
      (`tools\parity\out\engine-*`), боевой каталог не трогать.
- [ ] Два инстанса одновременно: chat на CUDA + embedding на Vulkan; проверить
      `create/load/unload`, стабильность `bridge_device_index`, отсутствие падений/паралича.
- [ ] Замеры: `tools/parity/out/m6_spike_*.json` (устройства, VRAM по картам, латентности
      embedding/rerank), отчёт в `tools/parity/SPIKES.md`.
- [ ] **Фолбэк при неудаче:** режим «одна карта на все роли» + явный warn в `hds check`
      («Vulkan-бэкенд недоступен/нестабилен — раскладка не применена»), документируем.
- Критерий выхода: получен ответ да/нет с числами; без него остальные треки не начинаем.

### T1. Конфиг-контракт `gpu.devices` + валидация — 1 дн
- [ ] `hds-llama::config`: парсинг `gpu.devices[]`/`llm_server.<role>.device`, приоритеты,
      обратная совместимость `gpu.device_index`.
- [ ] Валидация из §3.1 (числа в сообщениях); юнит-тесты на каждое правило.
- [ ] `hds check`: пункт `gpu_roles` — карта ↔ роли, backend карты, свободная VRAM по картам,
      warn на недоступную карту/двойное назначение; `config.example.yaml` — образец.

### T2. Per-role раскладка в реестре/хосте — 1–2 дн
- [ ] `registry.rs`: устройство роли из раскладки; `PlannedInstance` несёт
      `bridge_device_index` + backend для статуса/логов.
- [ ] `host.rs`: печать раскладки при старте (роль → карта/backend), честные ошибки роли.

### T3. VRAM-бюджет и вытеснение по картам — 2–3 дн
- [ ] `host.rs`/`gate.rs`/`budget.rs`/`dispatch.rs`: бюджет и fit-гейт по карте роли;
      вытеснение в пределах карты; печать VRAM **по картам** в `llm_host status`.
- [ ] Поведение на одной карте — без изменений (сравнение с числами M4/M5: SLA 3 прогона,
      fit-гейт, «нет замера» вместо догадок).
- [ ] Тесты: юнит на расчёт бюджета по карте (фейковые пробы), регрессия на одно-карточный путь.

### T4. Пресеты и автодетект — 1 дн
- [ ] Пресеты «1 мощная NVIDIA» / «AMD+NVIDIA» / «Apple Silicon» (конфиг-пример + `hds check`
      подсказка), ручное подтверждение раскладки.
- [ ] Автодетект (выключен по умолчанию): предлагает раскладку по backend/свободной VRAM,
      печатает её с числами; включение — явным ключом.

### T5. Рантайм-приёмка — 1–1,5 дн
- [ ] Стенд `load5.py` на раскладке «CUDA+Vulkan» (или фолбэке): 5 одновременных
      `ask_my_files` → SLA ≤ 5 мин на прогон, **≥3 прогона**; отчёты
      `tools/parity/out/m6_load_*.json`.
- [ ] Свидетельство реального использования карт: VRAM/латентности по каждой карте
      (лоб резидента + статус), а не только итоговый ответ.
- [ ] Десктоп-профиль: `hds check` ok, поведение не изменено (боевой конфиг — desktop).

### T6. Доклад — 0,5 дн
- [ ] `STATUS.md` (блок M6), `README.md` (раздел «Несколько карт и вендоров», пресеты,

## 5. Приёмка
- [ ] T0: спайк даёт **ответ с числами** (Vulkan виден/не виден; CUDA+Vulkan одновременно
      работают/нет) и зафиксированный фолбэк, если «нет».
- [ ] Раскладка: роли реально на назначенных картах — `llm_host status`/`devices`
      (`backend=CUDA|Vulkan`) + VRAM по картам; роль на недоступной карте → явная ошибка с числами.
- [ ] Бюджет/вытеснение по картам: роли другой карты не вытесняются; на одной карте числа
      совпадают с текущими (SLA-прогоны M5 не разъезжаются: max ≤ 300 с).
- [ ] `gpu.device_index` (компат) и десктоп-профиль не изменены; `hds check` — пункт
      `gpu_roles` с картами/ролями/числами; секретов не печатаем.
- [ ] `cargo test --workspace` зелёный; `cargo fmt --all --check`,
      `cargo clippy --workspace --all-targets -- -D warnings` — чисто.
- [ ] Рантайм-проверки на живых сценариях (не только юниты): стенд T5, `llm_host status`,

## 7. Риски
| Риск | Митигация |
|---|---|
| Движок не грузит Vulkan в нашей сборке (`-Backend cuda`) | T0 первым шагом: проверка перечисления устройств + сборка Vulkan в копии рантайма; при неудаче — фолбэк «одна карта» и явный warn |
| CUDA+Vulkan в одном процессе нестабильны | T0 спайк (create/load/unload, латентности); фолбэк — две роли на одной карте или отдельный процесс на карту (решение по числам, не «на глаз») |
| Раскладка по картам ломает бюджет/вытеснение | Сравнение чисел на одной карте до/после (регрессия M4/M5), юнит-тесты на расчёт по карте |
| AMD-карта = iGPU (общая память) с иной моделью VRAM | Всё решаем по пробам (NVML/DXGI) и числам движка; «нет замера» — честное сообщение, не догадка |
| Apple Silicon нельзя проверить на этой станции | Этап принимается без живой проверки Metal; хвост явно переносится (машина с Mac) |
| Пресеты/автодетект дают «умный» выбор, который ломает SLA | Автодетект выключен по умолчанию, любая раскладка печатается с числами и подтверждается вручную |
