## 2. Границы M4

**Входит:**
- **T0 — хвосты ревью** (`M3_CODE_REVIEW.md` §3 и §5) — закрыть до новой функциональности.
- **Конкурентность БД:** `journal_mode=WAL` + `busy_timeout` + read-only соединения
  читателей; один писатель (инвариант + тест); стресс-прогон «5 чтений + индексация».
- **Слоты чата под SLA:** `llm_server.parallel` 5–6 с расчётом VRAM существующим бюджетом,
  **явная** ошибка при нехватке (не молчаливая деградация — решение заказчика 29.09.2026),
  подобранный `ctx_per_slot` для RAG; фиксация в `config.example.yaml`/README.
- **Очередь и fair-share по пользователю:** серверная очередь тяжёлых RAG с приоритетом по
  пользователю (round-robin между пользователями, FIFO внутри), таймаут ожидания, метрики
  очереди; ключ лимитов — **пользователь**, а не токен.
- **Квоты:** предел одновременных RAG на пользователя (переносится с токена), частота — на
  пользователя; индексные задачи — приоритет ниже пользовательских.
- **Диагностика конкуренции:** слоты/очередь/время ожидания в `hds check` и
  `/api/diagnostics` (расширение пунктов M3).
- **Нагрузочная приёмка:** 5 одновременных `ask_my_files` → **p95 ≤ 5 мин**, отчёт.
- Тесты (юнит + сокет + стресс), обновление README/README_SERVER_MULTIUSER/STATUS и
  `PLAN_SERVER_MULTIUSER.md` §9.

**Не входит (M5+; фиксируем явно, чтобы не потерять):**
- **Внешняя чат-модель** `chat.provider: remote` (W9/**Э6**) — хвост Э2, названный в
  `PLAN_SERVER_MULTIUSER.md` §9 («осталось из Э2 — отправка во внешний API»). В M4 — только
  **задел**: контракт ключей (§3.5). Реализация — M5; это же и «ключевой рычаг SLA», если
  замеры M4 покажут, что 12 ГБ не тянут 5 слотов (см. §7).
- GPU multi-vendor (Э5/W4), управление службами/токенами из UI (Э7/W10), пакеты
  (Э8/Э9/W6/W7), эксплуатация `healthz`/бэкап/обновление (Э10/W8), общая нагрузочная
  приёмка Э11 (в M4 — только конкуренция RAG).
- **Десктоп-профиль не меняем:** очередь/квоты выключены, лимиты/аудит — как в M3
  (выключены по умолчанию); `profile: server` меняет только дефолты.

## 3. Технические решения (контракты)

### 3.1. Слоты чата и VRAM
- Слоты задаются `llm_server.parallel` (дефолт профиля `server` — **5**; `desktop` — как
  сейчас, `1`). Контекст слота — `llm_server.chat.ctx_per_slot` (для RAG — подобрать:
  16384…32768; KV считается `kv_cache_mib(meta, n_ctx, n_parallel, kv_bits)`).
- Перед стартом роли — расчёт `estimate_need_mib` + `check_fit(free, need, reserve)`:
  «модель + KV×parallel + compute-буфер + reserve» против свободной VRAM. **Не хватает —
  явная ошибка с числами** (МиБ нужно/свободно) и подсказкой «снизить `parallel`/`ctx_per_slot`»;
  молчаливая деградация запрещена (решение заказчика).
- В `hds check`/`/api/diagnostics` — фактическое число слотов и занятая/свободная VRAM.
- Значения по умолчанию и результаты замеров — в `config.example.yaml` и README
  (числа, а не «на глаз»).

### 3.2. Очередь и fair-share по пользователю
- Очередь живёт **в MCP-процессе** (`hds-mcp`), перед вызовом тяжёлого инструмента
  (`ask_my_files`), вместо нынешнего «сразу 429»:
  - ключ пользователя — из Bearer-токена (`AuthCtx.user`); без токена (desktop/stdio) —
    пользователь `local`;
  - политика: **round-robin между пользователями**, FIFO внутри пользователя; опция
    `queue.policy: rr | fifo`; персональный приоритет — опционально в `access.yaml`.
- Конфиг: `queue: { enabled, max_depth, wait_timeout_sec, policy }`.
  Дефолты: `server` — `enabled: true`, `max_depth: 20`, `wait_timeout_sec: 300`;
  `desktop` — `enabled: false` (поведение как сейчас).
- Ответы при переполнении/таймауте: `429` (очередь полна) / `503` (таймаут ожидания) с
  `Retry-After` и понятным текстом в `hint`; отмена клиентом освобождает место (проверять
  живость соединения / `gpu.abandoned_request_sec`).
- Слоты `max_inflight` (M3) остаются: они ограничивают **исполнение**, очередь — ожидание.
- Метрики (в `/api/diagnostics`, `hds check`, лог): глубина очереди, ожидание p50/p95,
  число отказов, «кто кого ждёт» (пер-пользователь).
- Ограничение (документируем): очередь — в MCP-процессе; `hds ui` (админский `ask`)
  лимитируется своими лимитами M3. Общая очередь на оба процесса — вне M4 (при
  необходимости — лимит на прокси/Э10).

### 3.3. Квоты и приоритеты
- Ключ лимитов и квот меняется с токена на **пользователя**: `user:<login>` (валидный
  токен) → `ip:<addr>` (иначе). Пер-токенные лимиты — опция `rate_limit.per_token: true`.
- Новые ключи: `rate_limit.max_inflight_per_user` (дефолт 2 на 5 пользователей),
  `rate_limit.requests_per_min_per_user` (дефолт — как `requests_per_min`).
- Индексация: пользовательские задачи всегда выше индексных (`gpu.policy: query_priority`
  + `pause_index_on_query` уже есть); добавить проверку, что тяжёлый RAG **не** ждёт
  индексного писателя БД (T1) и наоборот (индекс уступает).
- Отказы квот — те же `429` + `Retry-After` + `hint` («per-user concurrency limit»),
  отдельное событие аудита не вводим (аудит фиксирует `tool_call` со статусом).

### 3.4. БД под конкурентность
- При `connect` (все соединения): `PRAGMA journal_mode=WAL`, `PRAGMA busy_timeout=<ms>`
  (дефолт 5000), `PRAGMA synchronous=NORMAL` (WAL; обоснование — в комментарии + README).
- Читатели (MCP/UI/CLI/поиск) — **read-only** соединения; писатель — только конвейер
  индексации/watcher (`open_rw` vs `open_ro`).
- Ключи: `db: { busy_timeout_ms, journal_mode, read_only_conns }` (дефолты — серверные,
  desktop — прежнее поведение, WAL тоже допустим, но проверяем совместимость).
- Тест/стресс: 5 параллельных чтений + писатель → нет `SQLITE_BUSY`/«database is locked».
- Пометка для Э10: бэкап — только `VACUUM INTO`/`.backup` (WAL нельзя копировать файлом
  «на горячую»).

### 3.5. Задел под внешнюю чат-модель (не реализуем в M4)
```yaml
chat:
  provider: local          # local | remote  (реализация — M5/Э6)
  base_url: "https://api.example.com/v1"
  api_key: ""
  model: "gpt-4o-mini"
```
- Контракт фиксируем текстом (README §«Слоты и SLA» + этот раздел), чтобы не менять
  конфиг дважды; при `remote` (M5) `llm-host` не держит chat-роль в VRAM — это и есть
  «рычаг SLA» на слабом железе (W3, W9).

## 5. Приёмка M4 (черновик)

- **SLA:** 5 одновременных `ask_my_files` (5 пользователей) → **p95 ≤ 5 мин**, без 5xx, без
  «database is locked», без «молчаливой» деградации; отчёт с числами.
- **Слоты/VRAM:** `llm_server.parallel` подобрано замером; при нехватке VRAM — **явная** ошибка
  с числами и подсказкой (проверено уменьшением свободной VRAM/увеличением `parallel`).
- **Fair-share:** «жадный» пользователь (несколько параллельных RAG) не блокирует остальных —
  проверено тестом/нагрузкой (ожидание пер-пользователь распределено).
- **Квоты:** превышение пер-пользовательского предела → `429`+`Retry-After`+`hint`;
  два токена одного пользователя **не** удваивают квоту.
- **Очередь:** переполнение → `429`, таймаут ожидания → `503`; клиент видит коды (а не обрыв —
  регресс-тест на F4); метрики очереди видны в диагностике.
- **БД:** WAL включён (видно в `PRAGMA journal_mode`), `busy_timeout` работает; читатели read-only,
  писатель один; стресс «5 чтений + индексация» без блокировок.
- **Обратная совместимость:** `profile: desktop` — поведение как в M3 (очередь/квоты выключены,
  лимиты/аудит выключены); `cargo test --workspace` зелёный; `fmt` и `clippy -D warnings` чисто.
- **T0 закрыт:** все пункты §4 T0 (кроме T0.9 — вопросы заказчику) выполнены и покрыты тестами;
  хвосты M2 (F5–F10) закрыты; хвост Э2 (внешняя модель) **явно** перенесён в M5 и записан в
  `STATUS.md`, чтобы не потерялся.

## 6. Порядок работ и коммиты

По зависимостям, один коммит на шаг (в T0 — по одному коммиту на находку/группу):

1. **T0** — `fix(audit): …`, `fix(ui): …`, `fix(http): …`, `fix(service): …`, `test(http): …`,
   `fix(check): …`, `chore(config): …`.
2. **T1** — `feat(db): WAL + busy_timeout + read-only connections`.
3. **T2** — `feat(llmhost): chat slots (parallel) + VRAM fit gate`.
4. **T3** — `feat(queue): per-user queue and fair-share for heavy RAG`.
5. **T4** — `feat(quotas): per-user inflight/rate limits`.
6. **T5** — `test(load): 5x ask_my_files acceptance (p95)`.
7. **T6** — `docs(server): concurrency and SLA (M4)`.

После каждого шага — `cargo test --workspace` + рантайм-проверка (правило этапа: сеть/лимиты/
конкуренция проверяются на живом сценарии, а не только юнитами).

## 7. Риски

| Риск | Митигация |
|---|---|
| `parallel: 5` не влезает в 12 ГБ (или p95 > 5 мин) | замеры T2 до включения дефолта; фолбэк — `parallel: 2–3` + очередь; если SLA недостижим локально — внешняя чат-модель (M5/Э6) как «рычаг», фиксируем это явно в STATUS |
| Рост очереди → «зависшие» запросы и таймауты MCP-клиента (300 с) | `wait_timeout_sec` < клиентского таймаута; при таймауте — `503`+`Retry-After`; метрика ожидания в диагностике |
| Fair-share нечестен из-за round-robin при разной длине RAG | политика `rr`+FIFO внутри; при необходимости — «бюджет времени» на пользователя; метрика p95 пер-пользователь |
| WAL ломает существующие сценарии (бэкап копированием, сетевые диски, старые БД) | включать WAL с проверкой `journal_mode` в тесте; бэкап — `.backup`/`VACUUM INTO`; откат ключом конфига |
| Read-only соединения ломают бэкфилл/CRUD `db.rs` | явное разделение `open_ro`/`open_rw` + тесты CRUD на rw-путь |
| Очередь только в MCP-процессе: UI-`ask` вне неё → несправедливость под нагрузкой | документируем; при необходимости — очередь в общем месте (файл/сокет) или лимит на прокси (Э10) |
| Тесты конкуренции нестабильны (тайминги, GPU) | помечать `#[ignore]`/скриптами, как `pipeline_parity`; приёмка — отдельным прогоном с отчётом |
| Замеры нагрузки требуют GPU → мешают резидент/чужие процессы | `cline-rules/dev-machine.md`: останавливать резидент, после — вернуть (`llm_host run`/задача Планировщика) |
