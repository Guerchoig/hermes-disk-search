# RELEASE_NOTES v0.18.0 — совместная работа: доступ и проекты, серверный профиль, периметр, SLA, тонкий клиент (M1–M9)

> Релиз-этап: закрыта подсистема **совместной работы** (этапы M1–M9 дорожной карты
> `PLAN_SERVER_MULTIUSER.md`): доступ с проектами, серверный профиль и службы, сетевой
> периметр, конкурентность и SLA ≤5 мин, внешний чат, несколько карт одного семейства,
> управление из UI, пакеты установки сервера и клиента. Дополнительно: **новый ассет** —
> офлайн-рантайм движка под **Vulkan** (для машин без NVIDIA) и правки релизной приёмки.
> Rust-проверки зелёные: `cargo fmt --check`, `clippy -D warnings`,
> `cargo test --workspace` (89 наборов, 0 падений).

## Новое: доступ и проекты (M1)

* **Проекты**: корни индексации получили проект (`index.roots` → `files.project`), поиск,
  цитаты и MCP-инструменты фильтруются по проектам пользователя (тесты на утечку).
* **Учётные записи и токены**: пароли Argon2id, авто-токены в `data/access.yaml`
  (`data/access.example.yaml` — образец в репозитории), `hds user`, `hds token`, `hds login`.
* **Авторизация**: при `access.enabled` MCP-сервер и UI требуют `Bearer` (UI принимает и
  `?token=` в URL серверного режима), индексация — только для админа.
* **UI**: карточка «Доступ» (пользователи/проекты/токены).

## Новое: серверный профиль и службы (M2)

* Профиль `profile: desktop|server`; каталог состояния `state_dir`
  (`%ProgramData%\hermes-disk-search`, macOS — `/Library/Application Support/…`;
  `HDS_ROOT` сильнее всего): БД, `access.yaml`, pid/логи/heartbeat.
* Службы: `hds service run|install|uninstall|start|stop|status <watch|mcp-http|ui|llm-host>`
  — Windows SCM (автостарт + авторестарт), macOS LaunchDaemon.
* Пакеты: `installers/install_server.ps1` и `install_server.command`; UI в серверном
  профиле headless (`run_ui.ps1` не открывает браузер), хосты/порты берутся из конфига.

## Новое: сетевой периметр (M3)

* Образцы reverse-proxy (`installers/proxy/{Caddyfile,nginx.conf}`): наружу только `/mcp` и
  `/ui`, фасад `:8010–:8012` не публикуется; ключ `trusted_proxy` (без него заголовки
  прокси игнорируются — подделать IP нельзя).
* **Аудит**: `data/logs/audit.jsonl` с ротацией; события `login_ok`/`login_fail`/
  `unauthorized`/`tool_call`/`admin_op`/`token_revoke`; включён в серверном профиле.
* **Rate-limit**: token-bucket по токену/IP, `429` + `Retry-After`, отдельный строгий лимит
  на `/auth/login`, `rate_limit.max_inflight` на тяжёлые запросы.
* **Hardening**: `http.max_body_kb` → `413` без чтения тела, `http.max_conns` → короткий
  `503`, единый JSON ошибок `{error,hint}`.

## Новое: конкурентность и SLA ≤5 мин (M4)

* **Очередь тяжёлых RAG-запросов** вместо мгновенного `429`: `queue.policy: rr|fifo`,
  `queue.max_depth`, `queue.wait_timeout_sec`; переполнение → `429`, не дождался слота →
  `503`, обрыв клиента освобождает место. Плюс пер-пользовательский предел
  `rate_limit.max_inflight_per_user` (жадный пользователь не забирает все слоты).
* **БД под конкурентность**: `db.busy_timeout_ms`, `db.journal_mode`, `db.read_only_conns`,
  раздельные соединения писателя/читателей, PRAGMA-факты в `hds check`.
* **Слоты чата**: `llm_server.parallel` (server — 5, desktop — 1) реально доходит до
  инстанса движка; шлюз движка переведён на разделяемую генерацию (chat/embeddings/rerank
  параллельно, управление кластером эксклюзивно).

## Новое: внешний чат, несколько карт, управление из UI (M5–M7)

* **M5 — `chat.provider: remote`**: чат через внешний OpenAI-совместимый API (TLS-клиент,
  только исходящие), локальные модели при этом освобождают VRAM.
* **M6 — несколько карт одного семейства**: `gpu.devices: [{index, roles}]` (или
  `llm_server.<role>.device`), пресеты `gpu.preset`/`gpu.autodetect`, бюджет VRAM и
  вытеснение **по карте**, whisper по картам, пункт `gpu_roles` в `hds check`. Vulkan-бэкенд
  движка берётся только из нашего дерева (чужие `ggml-vulkan.dll` несовместимы по ABI).
* **M7 — администрирование из UI**: карточки «Службы» (состояние + запуск/остановка) и
  выдача токена; API `/api/services`, `/api/access/token/new`, CLI `hds token new`.

## Новое: пакеты установки и тонкий клиент (M8–M9)

* **M8 — серверный пакет**: `install_server.ps1`/`install_server.command` с параметрами
  (неинтерактивная установка), генерация конфига, бутстрап админа, обновление/откат
  серверного профиля (`installers/update.ps1 -Profile server`, `-RollbackTo`,
  `-ListVersions`, `-WhatIf`).
* **M9 — тонкий клиент** (Cline без Hermes): `hds cline-sync --server-url … --token …`
  (токен также читается из `HDS_CLINE_TOKEN`), мастеры `setup-client.ps1`/`setup-client.cmd`
  и `installers/install_client.command`, тонкая сборка `installers/build_client_release.ps1`
  (в пакете только `bin\hds` + правило/скилл + мастеры; «тяжёлые» части отвергаются).
  Живой цикл проверен: ноутбук → внешний сервер с Bearer.

## Новое: офлайн-рантайм движка под Vulkan

* В релиз добавлен ассет `hds-engine-runtime-windows-x64-vulkan.zip` — тот же рантайм
  движка, что и CUDA-вариант, но с Vulkan-бэкендом. Нужен для установки **без интернета**
  на машинах без NVIDIA (AMD/Intel): обычный установщик и так выбирает CUDA/Vulkan сам по
  машине (`fetch_engine_runtime.ps1 -Backend auto`), поэтому оба ассета — только для офлайна.

## Исправления и релизная обвязка

* **Очередь (F11+F12)**: мгновенное обслуживание больше не считается ожиданием
  (`waited_ms == 0`) — метрики `p50/p95` не засоряются «ожиданием 1 мс» от каждого
  быстрого запроса; и потолок ожидания проверяется **до** выдачи слота, поэтому заявка,
  стоявшая в очереди, получает обещанный `503`, даже если слот освободился ровно в момент
  дедлайна (раньше гонка `release ↔ дедлайн` подменяла `503` на исполнение).
* **Sidecar**: обрушенный `.venv` без `pyvenv.cfg` больше не выбирается как интерпретатор
  воркера (лаунчер падал с «failed to locate pyvenv.cfg»); поставка (`sidecar\python`)
  по-прежнему в приоритете, а macOS-раскладка поставки (`sidecar/python/bin/python3`)
  теперь находится — раньше искали только `python.exe`, и на macOS воркер не подхватывался.
* **Сборка под Linux/macOS**: `hds service run` вызывал windows-only
  `service_run_platform` вне `#[cfg(windows)]` (`E0425`) — на не-Windows роли, как и
  задумано, запускаются напрямую; в macOS-ветке `install_macos` строка плейста
  передавалась в `format!` после перемещения (`E0382`). Ветка `server-multiuser` до этого
  релиза в CI не прогонялась — эти дефекты ловились только на ubuntu/macOS-джобах.
* **БД под конкуренцией**: в `open_rw` `PRAGMA busy_timeout` ставится **первым** — до
  `PRAGMA journal_mode`, который берёт блокировку БД; иначе подключение падало с
  «database is locked», не дожидаясь освобождения (на ubuntu это ловилось сокет-тестами
  очереди: «держатель слота» отдавал слот раньше потолка ожидания).
* **CI-детерминизм сокет-тестов очереди**: держатель блокировки БД вынесен в **отдельный
  процесс** — внутри одного процесса SQLite отдаёт `SQLITE_BUSY` без вызова busy-handler,
  и «держатель слота» отпускал слот раньше потолка ожидания (на Ubuntu тесты падали, на
  Windows проходили). Каждый шаг сценария оставляет трассу (время + снимок очереди) в
  сообщении об ошибке.
* **Release CI** (`RELEASING.md`): новая джоба `check-version` (тег обязан совпадать с
  `__version__`), **оба** Windows-рантайма движка (CUDA + Vulkan) стали блокирующими,
  публикация идемпотентна (повторный запуск перезаливает ассеты, релизы не удаляются),
  при ручном запуске тег прибивается к собранному коммиту, `rust.yml` теперь прогоняет
  и ветку `server-multiuser`.

## Требования к обновлению

* Штатное обновление поверх 0.17.x: распаковать архив и запустить `setup.cmd`/`setup.ps1`
  (или `installers\update.ps1`). Переиндексация **не требуется**, кроме одного случая —
  если включаете **проекты** (M1): проекты привязываются к файлам при индексации, поэтому
  после настройки проектов нужен прогон `hds index` (полный) для их проставления.
* Серверный профиль: включение — по `README_SERVER_MULTIUSER.md` §2–§3 (админ, токены,
  службы); обновление серверной установки — `installers\update.ps1 -Profile server`
  (окно обслуживания: службы останавливаются, при неудаче — автоматический откат).
* После обновления перезапустите `llm_host` и MCP-сервер (или службы), чтобы подхватился
  новый код и значения по умолчанию (очередь, лимиты, аудит — они включаются профилем).
* Новые ключи конфига (`queue`, `rate_limit.max_inflight_per_user`, `db.read_only_conns`,
  `gpu.devices`, `access.*`, `trusted_proxy`, `audit.*`) имеют безопасные значения по
  умолчанию: десктопное поведение остаётся прежним, серверное включается профилем
  `profile: server`.
